### 核心工作原理

1. 用 Tree-sitter 解析代码为 AST（抽象语法树）
2. 提取节点（函数、类、导入）和边（调用、继承、测试覆盖）
3. 存储为 SQLite 图数据库（`.code-review-graph/` 目录）
4. 通过 MCP 协议暴露 30 个查询工具给 AI 助手
5. AI 助手只读取图返回的相关文件，而非全仓扫描

### 关键数据（官方基准）

| 指标 | 数值 |
|------|------|
| Token 节省中位数 | ~65x（全仓 vs 图查询） |
| Token 节省最大值 | 376x（fastapi 仓库） |
| Impact F1 均值 | 0.693（13 个 commit） |
| Flow detection 召回率 | 33%（JS/Go 较弱） |
| 搜索质量 MRR | 0.35 |
| 增量更新速度 | ~2.5s（3000 文件项目，两文件改动） |

## 三、与 junshi-app 适配度评估

### 评分总览

| 维度 | 评分 | 说明 |
|------|------|------|
| NestJS 装饰器识别 | **3.5 / 5** | 能识别 `@Controller`/`@Injectable`/`@Module`，但无 NestJS 专项 resolver |
| React Native 组件 | **4 / 5** | TSX/JSX 组件树解析成熟，`<Component />` 生成 CALLS 边 |
| Monorepo 支持 | **4.5 / 5** | 支持 multi-repo registry、daemon、tsconfig alias |
| 增量更新价值 | **5 / 5** | 最成熟能力，~2.5s 增量 re-index |
| **综合** | **4.25 / 5** | |

### NestJS 模块/装饰器识别（3.5/5）

**支持点：**
- Tree-sitter 原生支持 `.ts`/`.tsx`
- `flows.py` 的 `_FRAMEWORK_DECORATOR_PATTERNS` 包含 `Controller|Module|Injectable|Guard|Pipe`
- 能将带装饰器的节点视为框架入口候选

**限制：**
- 无 `nestjs_resolver.py`（有 `spring_resolver.py` 和 Laravel 专项边）
- DI 注入关系、module imports/exports、dynamic module 不完整
- 官方承认：**JavaScript and Go flow detection needs work**

### React Native 组件（4/5）

**支持点：**
- `_extract_jsx_component_call()` 将 `<Component />` 转为 CALLS 边
- tsconfig/jsconfig path alias 解析
- screens → components 依赖图直接可用

**限制：**
- 不理解 navigation 配置、hook 约定、platform-specific split
- UI state/dataflow 是结构近似，非运行时行为模型

### Monorepo 支持（4.5/5）

**支持点：**
- 默认按 repository root 建图，支持 `--repo <path>`
- multi-repo registry 与 daemon
- tsconfig alias 解析

**注意：**
- 更擅长"一个 repo 下多目录代码图谱"
- 不等于"深度理解业务上强隔离的 poly-architecture monorepo"
- apps/ 与 runtime/ 的 HTTP API 边界不会自动验证

### 增量更新（5/5）

**这是最有价值的一项，前提是仓库进入真实开发阶段。**

- watch mode、hooks、daemon 持续更新图谱
- `detect-changes --brief` 与 `update --brief` 面向开发流
- 3000 文件项目两文件改动 ~2.5s

## 四、风险与局限

### 1. 时机风险：现在上，收益太小

当前代码基数几乎为零（apps/ 和 runtime/ 下 0 个非 .gitkeep 源代码文件），图构建、MCP 接入、团队学习成本已发生，但产出可能只是"形式上很高级"。

### 2. 语言栈贴合度风险

junshi-app 核心是 TS（RN + NestJS），而 CRG 官方承认 JS/Go flow detection 仍弱。在本项目中更像：
- 结构依赖/影响面工具：可用
- 业务执行流权威地图：暂时别信满分

### 3. 小仓库/小改动收益不稳定

官方公开：小单文件改动时 graph context 可能比直接读文件更贵。

### 4. 误报风险

impact analysis 倾向保守，会带来 false positives。

### 5. 工具链可靠性风险

MCP / watch / update 相关问题近期仍有 bug 报告，不是"装完就忘"的零维护基础设施。

## 五、实际效果预判

### 对当前 junshi-app：现在太早

- 仓库是"架构蓝图仓库"，不是"代码仓库"
- 装上后大概率只能告诉你"代码很少 / 图很稀 / 没什么可 review 的"
- 当前阶段不如 STRUCTURE.md + rg 搜文档

### 对未来的 junshi-app：有价值，但别神化

**最有用的场景：**
1. 改 runtime/domain 一个实体，想知道波及哪些引擎逻辑、接口层、测试
2. 改 apps/api 某个 service/module，想定位受影响 controller/tests
3. 新人接手时，问"认证链路怎么走"
4. 做大重构时，快速看到模块耦合最重的文件

**触发条件建议满足任意几个再试点：**
1. apps/api 和 apps/mobile 都进入真实开发
2. 仓库出现持续的跨模块 PR
3. 开发中已明显感受到 Claude Code 经常"读太多无关文件"
4. PR review 开始出现"影响面漏看"的痛点

## 六、结论与建议

### 结论

**对未来的 junshi-app，它可能是有价值的 AI review/navigation 增强器；对今天的 junshi-app，它还太早，短期收益撑不起接入和维护成本。**

### 建议

**不建议现在就把 code-review-graph 当成 junshi-app 的标准开发基础设施。**

更合适的做法：**等真实 TS 多模块代码长出来后，再做一次 1 周试点。**

试点时：
1. 优先在 React Native / TSX 部分验证收益（JSX component edge 最容易出效果）
2. NestJS 部分把期待值放在"结构感知"而不是"框架语义还原"
3. 不要把它设为所有人必装
4. 不要立刻接入 CI gate
5. 先把它当"增强型本地导航工具"
