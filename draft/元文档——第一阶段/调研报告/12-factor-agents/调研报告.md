## 二、12-Factor Agents 仓库概览

### 2.1 基本信息

| 项目 | 内容 |
|---|---|
| 仓库 | https://github.com/humanlayer/12-factor-agents |
| 作者 | Dex Horthy（HumanLayer 创始人） |
| Stars | 25.4k |
| Forks | 1.9k |
| 贡献者 | 15 人 |
| 许可证 | 代码 Apache 2.0，内容 CC BY-SA 4.0 |
| 定位 | 构建可靠 LLM 应用的原则集合，不是框架 |

### 2.2 核心主张

> Agent 不应被理解为完全自主、无限循环的黑盒系统；更可靠的做法是把它视为确定性软件流程中的一个小型决策组件。

作者认为：
1. Agent 最终可以拆解为 4 个普通软件组件：Prompt、Switch statement、Accumulated context、For loop
2. LLM 负责有限范围内的决策，确定性代码负责执行和控制流
3. Prompt 和上下文都是应用代码的一部分，不应交给黑盒框架
4. 小而聚焦的上下文总是优于不断增长的完整历史

### 2.3 12 条原则速览

| # | 原则 | 核心主张 |
|---|---|---|
| 1 | Natural Language to Tool Calls | LLM 选择动作并填写参数，确定性代码执行 |
| 2 | Own Your Prompts | 不要把 Prompt 工程外包给框架 |
| 3 | Own Your Context Window | 应用自己决定什么信息进入上下文 |
| 4 | Tools Are Just Structured Outputs | 工具调用本质是结构化 JSON 输出 |
| 5 | Unify Execution State and Business State | 尽量把执行状态和业务状态统一为一个事实来源 |
| 6 | Launch/Pause/Resume with Simple APIs | Agent 应像普通程序一样提供生命周期 API |
| 7 | Contact Humans with Tool Calls | 把"联系人工"建模为结构化工具调用 |
| 8 | Own Your Control Flow | 应用掌握工具调用后的继续/暂停/审批逻辑 |
| 9 | Compact Errors into Context Window | 把错误格式化后反馈给模型，但限制重试 |
| 10 | Small, Focused Agents | 构建职责单一的小型 Agent |
| 11 | Trigger from Anywhere | 从 Slack/邮件/短信/事件等任意渠道触发 |
| 12 | Stateless Reducer | 把 Agent 建模为无状态归约器 |
| +13 | Pre-Fetch Context | 高概率需要的数据应确定性预取 |

## 三、逐因子深度分析——与学业军师的对照

> 本节逐条分析 12 Factor，结合学业军师仓库的客观事实，标注"直接适用"、"需改造适用"或"不直接适用"。

### Factor 1：Natural Language to Tool Calls

**原文要点：** LLM 输出带 `intent` 的结构化对象，确定性代码根据 `intent` 执行。

**学业军师现状：**
- 正文 §6.1 已定义"首尾调用"——判断引擎在产品循环入口和输出时各调用一次
- 正文 §6.3 定义了 10 项最小运行时状态，但未细化到工具调用层级
- runtime/engine/ 下有 duty_loop、evidence、planning、safety 等占位目录，无实现

**对照判断：**
- ✅ **直接适用**：学业军师的判断引擎"首尾调用"与 Factor 1 的"自然语言到结构化工具调用"天然同构——判断引擎在进入时输出静态路由、在输出时输出动态调用，本质就是结构化决策
- ⚠️ **需细化**：当前元文档停留在"判断引擎调用"这一概念层，尚未定义具体的 intent 类型（如理解处境、定策、规划、复盘等对应的结构化输出）

### Factor 2：Own Your Prompts

**原文要点：** Prompt 是一等代码资产，应用应拥有最终 Prompt 的构成权。

**学业军师现状：**
- runtime/engine/prompt/ 占位目录存在，无实现
- 元文档定义了判断引擎的职责边界，但未规定 Prompt 的工程化管理方式
- 调研报告（判断引擎）对比了 LangGraph/AutoGen/CrewAI/MetaGPT 的 Prompt 管理方式

**对照判断：**
- ✅ **直接适用**：学业军师的产品判断引擎、学生交互层、异常处理层都需要各自的 Prompt，且 Prompt 的质量直接影响判断准确性——必须从实现阶段就将 Prompt 作为可版本化、可测试、可迭代的资产
- ⚠️ **需设计**：当前元文档未规定 Prompt 的管理策略（版本控制、A/B 测试、回归评估）

### Factor 3：Own Your Context Window

**原文要点：** 应用自己决定什么信息进入上下文、以什么结构进入、何时删除或压缩。

**学业军师现状：**
- 正文 §6.5 已定义上下文治理双层架构（工作会话 + 持久记忆）
- 正文 §6.5 定义了三种触发条件（任务完成、上下文阈值、时间边界）
- 正文 §7.3 进一步细化上下文治理原则
- 决策登记 D-011 第 5 项确认了记忆蒸馏归档、信息继承结构化事实

**对照判断：**
- ✅ **高度对齐**：学业军师已通过 D-011 确认了上下文治理的核心原则，且调研报告（上下文治理与会话切换）已对比了 LangGraph/HabitatAgent 等框架的实践——这是学业军师与 12-factor 最强的共识点
- ⚠️ **需实现设计**：元文档定义了"做什么"（双层架构、触发条件、记忆蒸馏），但 12-factor 补充了"怎么做"的工程细节——特别是上下文序列化格式（XML/JSON）、事件类型定义、上下文压缩策略

### Factor 4：Tools Are Just Structured Outputs

**原文要点：** 工具调用本质是 LLM 输出的结构化数据，用带判别字段的 JSON 表示。

**学业军师现状：**
- 决策登记 D-005 定义了内外循环
- 正文 §6.3 列出了 10 项运行时状态
- 但未定义工具类型、参数 schema 或输出格式

**对照判断：**
- ✅ **直接适用**：学业军师的判断引擎输出（静态路由/动态调用）天然适合用结构化 union 类型表示
- ⚠️ **需设计**：需要为判断引擎、学业资产操作、证据处理、安全检查等定义结构化的工具/意图类型

### Factor 5：Unify Execution State and Business State

**原文要点：** 把执行状态和业务状态统一为同一个事实来源。

**学业军师现状：**
- 正文 §6.3 定义了 10 项最小运行时状态，分会话级和持久级两类
- 正文 §7.2 进一步细化了状态生命周期
- 但尚未定义这些状态在技术层面如何统一存储和恢复

**对照判断：**
- ✅ **原则一致**：学业军师的"统一线程事件"理念与 Factor 5 高度契合
- ⚠️ **需实现设计**：需要确定"线程/事件"作为状态统一载体的具体数据结构

### Factor 6：Launch/Pause/Resume with Simple APIs

**原文要点：** Agent 应提供启动、查询、暂停、恢复的简单接口。

**学业军师现状：**
- 决策登记 D-011 定义了状态转移三原则（必须有触发、可追溯、不可逆需确认）
- 但未定义技术层面的生命周期 API

**对照判断：**
- ✅ **直接适用**：学业军师的状态转移原则天然需要生命周期 API 来实现
- ⚠️ **需实现设计**：API 设计需结合学业军师生特有的"学生确认"、"家长授权"、"安全暂停"等场景

### Factor 7：Contact Humans with Tool Calls

**原文要点：** 把"联系人工"建模为结构化工具调用或事件。

**学业军师现状：**
- 决策登记 D-009 定义了 A-E 五个主动性等级
- D 代表"对外沟通或执行必须预览并由有权主体确认"
- E 代表"不得由 AI 单独或静默完成"
- 正文 §6.4 定义了异常降级三层模型（L1/L2/L3）

**对照判断：**
- ✅ **高度对齐且更复杂**：学业军师的人工介入场景远比 12-factor 的"部署审批"复杂——涉及学生确认、家长授权、专业转介、安全边界四类不同的人工介入，每类有不同的权限和流程
- ⚠️ **需细化**：需要为每类人工介入定义结构化的请求/响应 schema、权限判断、状态恢复

### Factor 8：Own Your Control Flow

**原文要点：** 应用掌握工具调用后的继续/暂停/审批/重试逻辑。

**学业军师现状：**
- 正文 §6.1 定义了内外循环
- 决策登记 D-005 定义了异常边界
- 但控制流的具体分支逻辑未细化

**对照判断：**
- ✅ **直接适用**：学业军师的三层降级模型（L1/L2/L3）本质上就是控制流的不同分支——L1 继续、L2 暂停并请求学生参与、L3 暂停并进入安全边界
- ⚠️ **需细化**：需要为每个控制流分支定义具体的继续/暂停/恢复条件

### Factor 9：Compact Errors into Context Window

**原文要点：** 把格式化后的错误反馈给模型，限制重试次数，达到阈值后升级。

**学业军师现状：**
- runtime/domain/error_chain/ 占位目录存在
- 决策登记 D-005 提到"证据不足、冲突或过载时降低判断强度"
- 但错误处理的具体策略未定义

**对照判断：**
- ✅ **直接适用**：学业军师的错误链（error_chain）目录规划与 Factor 9 的错误上下文化理念一致
- ⚠️ **需设计**：需要定义错误类型、格式化策略、重试上限、升级路径（学生参与→安全边界）

### Factor 10：Small, Focused Agents

**原文要点：** 构建职责单一的小型 Agent，控制在 3-10 步。

**学业军师现状：**
- runtime/engine/ 下规划了多个子模块：duty_loop、evidence、memory、planning、safety、skills、subagents、understanding、workflows
- 这些模块的划分方向与"小型专注 Agent"理念一致

**对照判断：**
- ✅ **理念一致**：runtime/engine/ 的模块划分（义务环、记忆、证据、规划、安全等）天然对应小型专注 Agent 的方向
- ⚠️ **需验证**：每个子模块是否应在实现阶段作为独立 Agent 运行，还是作为确定性函数组合——12-factor 明确推荐前者

### Factor 11：Trigger from Anywhere

**原文要点：** 从 Slack/邮件/短信/事件等任意渠道触发 Agent。

**学业军师现状：**

### Factor 12：Stateless Reducer

**原文要点：** 把 Agent 建模为无状态归约器。

**学业军师现状：**

**学业军师现状：**

- ⚠️ **需设计**：需要定义预取清单、预取时机、预取结果的缓存策略

## 四、代码实现分析——可复用模式

### 4.1 技术栈参考

12-factor-agents 的模板使用：
- TypeScript + Node.js
- BAML（Boundary ML）进行结构化输出
- Express 5 作为 HTTP 层
- Zod 作为数据校验
- HumanLayer 作为人工交互层
- 文件系统状态存储（可替换为 Redis/SQLite/PostgreSQL）

**对学业军师的参考：**
- 学业军师计划使用 NestJS + TypeScript（API）和 React Native + TypeScript（移动端），语言栈一致
- BAML 的结构化输出理念值得参考，但具体实现需根据学业军师的技术选型调整
- Zod 的数据校验模式可以直接借鉴

### 4.2 Thread/Event 统一模型

12-factor-agents 的核心代码模式：

```typescript
class Thread {
  events: Event[]  // 统一存储所有事件
}

class Event {
  type: string     // 事件类型
  data: any        // 事件数据
}
```

关键设计：
- 用户输入、工具调用、工具结果、人工回应全部进入同一个 `events` 数组
- `serializeForLLM()` 将事件转换为 XML 风格的上下文
- 恢复时只需加载线程，无需恢复额外状态

**对学业军师的参考：**
- 这一模式与学业军师的"最小运行时状态"（10 项）高度兼容
- 学业军师可以定义自己的 Event 类型体系（理解处境、定策、规划、行动、复盘、证据处理、安全检查等）
- 事件统一模型天然支持"可追溯"的状态转移三原则

### 4.3 Agent Loop 控制流

```typescript
async function agentLoop(thread: Thread) {
  while (true) {
    const nextStep = await determineNextStep(serializeForLLM(thread));
    thread.events.append(nextStep);

    switch (nextStep.intent) {
      case "request_clarification":
        await saveAndPause(thread);  // 暂停，等待人工
        return;
      case "fetch_data":
        const result = await fetchData(nextStep);
        thread.events.append(result);  // 继续
        break;
      case "high_risk_action":
        await requestApproval(nextStep);  // 暂停，等待审批
        return;
      case "done":
        return;
    }
  }
}
```

**对学业军师的参考：**
- 学业军师的"首尾调用"可以嵌入类似的 switch 分支
- 三层降级模型可以直接映射为控制流分支：L1 → 继续执行、L2 → 暂停并请求学生参与、L3 → 暂停并进入安全边界
- 硬底线（AI 不得修改规则/不可逆状态）可以在 switch 中通过 `default` 分支拦截

### 4.4 错误处理模式

```typescript
let consecutiveErrors = 0;

while (true) {
  try {
    const result = await handleNextStep(thread, nextStep);
    thread.events.append(result);
    consecutiveErrors = 0;  // 成功清零
  } catch (e) {
    consecutiveErrors++;
    if (consecutiveErrors < 3) {
      thread.events.append({ type: "error", data: formatError(e) });
      // 继续循环，让模型修正
    } else {
      // 退出、重置上下文、升级人工
      break;
    }
  }
}
```

**对学业军师的参考：**
- error_chain 目录可以实现类似的错误追踪和升级机制
- 错误格式化策略需要考虑学生用户的可理解性（不能把原始堆栈给学生看）
- 升级路径：AI 自我修正 → 请求学生参与 → 请求家长/专业支持 → 安全边界

## 五、社区反馈——值得警惕的问题

### 5.1 标准化 vs. 灵活性的张力

社区持续讨论的核心争议：哪些内容应该标准化（MCP 工具描述、输出 schema），哪些应保留给应用自由优化。

**对学业军师的启示：**
- 学业军师不需要参与这个通用框架层面的争议
- 但需要在自己的产品内部建立明确的工具/意图类型标准——这是 Factor 2（拥有 Prompt）和 Factor 4（结构化输出）的直接要求

### 5.2 缺少完整生产案例

社区最大的不满之一："原则很好，但缺少真正的生产案例。"

**对学业军师的启示：**
- 这恰恰说明 12-factor-agents 的价值在于原则和模式，不在于可直接复用的代码
- 学业军师应该用自己的产品实现来验证这些原则在教育场景的适用性
- 不应该等待社区提供"完整案例"后再行动

### 5.3 人工交互协议（A2H）

12-factor-agents 的草稿中定义了 Agent-to-Human 协议（A2H），但 OpenAPI 文件为空，尚未标准化。

**对学业军师的启示：**
- A2H 的设计思路（结构化人工请求、审批、澄清、多渠道）直接适用
- 但学业军师的人工介入场景更复杂（学生/家长/专业支持/安全边界），需要自定义协议，不能直接套用 A2H

### 5.4 Evals 和测试

社区持续要求加入 evals、TDD 和行为测试。

**对学业军师的启示：**
- 决策登记 D-010 已定义了四轴阶段门槛
- 但"产品能力"轴的验证需要具体的 eval 方法论——12-factor-agents 的社区讨论可以作为输入
