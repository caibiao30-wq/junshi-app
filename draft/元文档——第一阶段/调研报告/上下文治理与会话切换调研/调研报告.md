# AI Agent 上下文治理与会话切换调研报告

> **调研日期：** 2026-08-24  
> **调研目的：** 为学业军师产品设计会话切换机制提供行业实践参考  
> **调研范围：** 开源框架（LangChain/LangGraph、AutoGen、CrewAI、MetaGPT）；垂直领域（法律、医疗、金融、地产）  
> **资料性质：** 官方文档、公开代码和论文中的机制与行为记录；横向判断另行标注为“调研推断”  
> **效力限制：** 本报告是调研材料，不是产品决策、正式规格或隐私/安全承诺。论文中的实验结果、项目中的实现声明和公开产品行为不能直接等同于生产验证。

## 一、总判断

1. **分层上下文是最稳妥的共同方向。** 应将可丢弃、可限长的 working/session context 与跨会话、需要来源/版本/权限/删除治理的 durable memory 分开。LangGraph 的 checkpointer/store、HabitatAgent 的四层记忆以及医疗研究中的 dual-memory 都支持这一方向。
2. **会话边界和长期记忆边界不是同一个概念。** LangGraph 以 `thread_id` 确定会话；长期记忆可放在 user/org 等 namespace 中。用户更换 thread 后，不会自动获得长期信息，除非显式从 Store 读取。
3. **摘要和压缩是有损写入。** 必须保留来源、时间、置信度或验证状态，并允许回看原文；完整历史即使能装进 context window，也会带来注意力分散、延迟和成本上升。
4. **“记忆被注入模型”不等于“用户能看见并控制记忆”。** 各框架提供的事件、source/private scope、日志或屏幕展示主要是 API、隔离或运行可观测性，不自动形成终端用户的同意、查看、编辑、删除和审计流程。
5. **高风险垂直领域的共同下限是三件事。** RAG 用于时效和证据访问，验证门用于限制错误写回，窗口/TTL/数量阈值用于控制成本和上下文污染；三者单独都不能保证正确性、隐私或合规。

## 二、开源框架

### 2.1 LangChain/LangGraph

- **短期记忆：** 等同于 thread-scoped graph state；checkpointer 按 `thread_id` 保存每一步 checkpoint，可恢复对话、暂停并进行人机协同，也可在故障后续跑。
- **长期记忆：** Store 中的 JSON 文档，按自定义 namespace/key 保存，能够跨 conversational threads 使用，并支持语义搜索和过滤；实际应用通常同时使用短期记忆和长期记忆。
- **会话边界：** 由 `thread_id` 决定。长期记忆不局限于 thread，可以使用 user/org 等 namespace；同一用户切换 thread 后，只有显式从 Store 读取，才会获得长期信息。
- **长对话治理：** 不是自动提供“无限记忆”。完整历史可能超出 context window；即使能够装下，也会导致注意力分散、延迟和成本上升。官方建议通过删除、截断、摘要等方式管理消息。
- **长期记忆组织：** 有 profile 和 collection 两种思路。profile 在文档不断变大时可能更新出错；collection 通常召回更高，但需要处理删除、更新、搜索、跨条目关系和完整上下文丢失。官方明确指出 long-term memory 是复杂且没有一刀切方案的问题。
- **写入时机：** 可以走 hot path 或后台。hot path 立即可用并可通知用户，但会增加延迟和复杂度，也可能影响记忆质量；后台写入能降低主请求延迟，但需要决定触发频率，更新不及时会使其他 thread 暂时拿不到新记忆。
- **生产持久化：** 应使用 Postgres、SQLite 等持久化方案；checkpoint 长期累积会增加延迟和存储成本，需要清理或保留策略。
- **用户可见性边界：** 概念层提到 hot-path 写记忆时可以通知用户，但文档没有把通知、编辑、删除和同意流程作为默认 UI 或策略。因此不应把 LangGraph Store 当作现成的用户隐私/可见性治理层。

**来源：** 见《参考来源索引.md》§一第 1—2 项：LangChain Memory 与 LangGraph Persistence。

### 2.2 Microsoft AutoGen（AgentChat 0.4）

- **Memory 协议：** 可扩展协议包括 `add`、`query`、`update_context`、`clear`、`close`。典型用法是 RAG：在具体步骤前查询数据库，再把结果加入 agent 的 `model_context`。
- **基础实现：** `ListMemory` 按时间顺序维护条目，并把最近记忆追加到上下文。
- **持久化向量记忆：** 有 `ChromaDBVectorMemory` 示例，可配置 `persistence_path`、`k` 和 `score_threshold`；也有 RedisMemory，以及 Mem0Memory 的云端/本地后端。
- **状态保存：** Agent/Team 状态可以通过 `save_state`/`load_state` 保存或载入字典；AssistantAgent 的主要状态是 `model_context`。
- **历史长度限制：** 默认 AssistantAgent 使用 `UnboundedChatCompletionContext`，把完整历史发送给模型；也可以使用 `BufferedChatCompletionContext` 按条数限制，或使用 `TokenLimitedChatCompletionContext` 按 token 数限制。
- **用户可见性边界：** “可观测”主要体现为事件/API 能力，例如 `MemoryQueryEvent`，不等于默认展示给终端用户。

**来源：** 见《参考来源索引.md》§一第 3 项：AutoGen AgentChat Memory。

### 2.3 CrewAI（v1.15.17）

- **统一记忆接口：** 统一的 `Memory` 类替代旧的 short-term、long-term、entity、external 分立 API；可独立使用，也可供 Crew、Agent、Flow 使用。
- **任务前后流程：** `memory=True` 时，任务完成后自动抽取离散事实并保存，任务开始前召回并注入 prompt。Crew 内的 agent 默认共享记忆，也可以为 agent 设置 scoped view。
- **层级与隔离：** 使用 hierarchical scopes，例如 `/customer/acme`、`/agent/researcher`；private memory 只有 source 匹配时才可召回。
- **召回排序：** 按 semantic similarity、recency decay、importance 加权；默认权重分别为 `0.5`、`0.3`、`0.2`，recency half-life 为 30 天。
- **记忆整形：** `extract_memories` 把长文本拆成原子事实；相似度 `≥0.85` 时触发 LLM consolidation，可执行 keep/update/delete/insert_new；`remember_many` 批内相似度 `≥0.98` 时，对后项静默去重。
- **后台写入：** `remember_many` 通过后台线程进行非阻塞写入；`recall` 会自动 `drain_writes`。
- **隐私限制：** 记忆内容会发送给配置的 LLM，用于 scope、categories、importance、query analysis 和 deep recall 等处理。官方建议敏感数据使用本地 LLM，或确认供应商合规。
- **用户可见性边界：** user visibility 主要是 API 级能力，不是默认终端 UI；需要另外建立用户查看、编辑、删除和审计层。

**来源：** 见《参考来源索引.md》§一第 4 项：CrewAI Memory。

### 2.4 MetaGPT

- **基础 Memory：** 短期记忆由每个 Role 的 `self.rc.memory` 保存其 observe 到的 `Message` 列表；`get(k)` 返回最近 `k` 条，`k=0` 返回全部，检索方式主要是 recency。
- **存储边界：** 核心 Memory 类是进程内的 `list[Message]`，并按 `cause_by` 建立索引；没有数据库或向量持久化后端。进程重启或新 Role 不应假设可以恢复旧记忆。
- **论文中的自改进：** 新项目开始前总结上一项目的反馈，写入 long-term memory，并用于更新角色的 constraint prompt；当前限制是摘要优化只改变角色约束，不改变结构化通信接口。
- **用户可观察性：** 人可以发起、观察和停止运行，屏幕或日志展示自然语言操作。

**来源：** 见《参考来源索引.md》§一第 5—6 项：MetaGPT 文档与论文。

## 三、垂直领域

### 3.1 法律：ChatLaw

- Legal Assistant 通过预定义法律知识图谱收集和补齐用户事实，持续提问，直到节点足够完整；Researcher 检索最新法律法规和相似案例。
- 其形态是“会话内结构化上下文 + 外部 RAG”，不是明确的跨会话长期记忆产品。
- 论文记录了相互矛盾的保存诉求：一部分用户不希望敏感咨询被存储或泄露，另一部分用户希望保留记录，以便案件持续支持。
- 论文没有给出成熟的用户 retention、删除、导出和可见性控制。
- 已知限制包括幻觉（捏造法条、使用过时法律/案例）、恶意输入和并发计算资源压力。

**来源：** 见《参考来源索引.md》§二第 1 项：ChatLaw。

### 3.2 医疗：Agent Hospital / MedAgents

- **Agent Hospital：** 从错误答案反思出自然语言 principle，验证成功才保留，失败则丢弃；按语义 top-k 检索。
- **经验数量：** 最优示例是 top-4 experiences 加 top-3 medical cases；继续增加案例会引入无关信息并扰乱推理。
- **适用边界：** 重点是模拟训练和经验演化，不是患者真实生产档案的 session、persistence 或 privacy 协议。
- **MedAgents：** 主要治理机制是会话内多专家协作，属于 zero-shot/training-free；没有跨会话用户记忆或持久化存储。

**来源：** 见《参考来源索引.md》§二第 2—3 项：Agent Hospital 与 MedAgents。

### 3.3 金融：FinMem

- 采用分层消息处理，吸收分层金融数据，并按可调认知跨度保留关键信息。
- 记忆分为 working memory 与 layered long-term memory，按重要性和新近度组织层次。
- 没有跨用户会话边界、用户查看/编辑/删除、隐私同意或审计接口。
- 实验性能不能直接证明生产级金融 agent 的安全或合规。

**来源：** 见《参考来源索引.md》§二第 4 项：FinMem。

### 3.4 地产/住房：HabitatAgent（最直接覆盖上下文治理）

- **四层记忆架构：**
  - conversational memory：最近 5 轮，TTL 24 小时；
  - entity memory：中期实体加权列表；
  - bias memory：长期偏好/厌恶，权重范围 `[-1,1]`；
  - retrieval memory：7 天推荐房源 ID 滚动缓存，用于去重和多样化。
- **轻量状态：** 为解决 5 轮窗口造成的早期信息碎片化，可选维护 context-aware state；每轮摘要显著约束和实体，并用 Add/Update/Relax 更新。
- **验证门控记忆：** 只有经过验证的回答才更新长期用户记忆；主验证阈值是 factual score `≥0.85` 且 entity score `≥0.90`。
- **检索：** 采用自适应 vector+graph/GraphRAG；只有复杂关系约束才路由到图检索。
- **审计与用户控制边界：** 论文称工作流“auditable”，推荐带证据引用，但没有说明终端用户是否能查看、修改、删除四层记忆，或撤回某条偏好。

**来源：** 见《参考来源索引.md》§二第 5 项：HabitatAgent。

## 四、横向判断（调研推断）

> 本节是基于前述公开资料的横向归纳，不是任何框架或论文的官方承诺，也不直接构成学业军师产品决定。

### 4.1 分层是共识

最稳妥的边界是：**working/session context（可丢、可限长）与 durable memory（跨会话、需来源/版本/权限/删除）分开**。LangGraph 的 checkpointer/store、HabitatAgent 的四层记忆、医疗论文的 dual-memory 都支持这一分层方向。

### 4.2 摘要/压缩是有损写入

必须保留来源、时间、置信度或验证状态，并允许回看原文。LangGraph 官方已明确 profile 更新可能出错、collection 可能丢关系；AutoGen/CrewAI 更偏向边界、抽取和去重，而不是默认滚动摘要。

### 4.3 “记忆被注入模型”不等于“用户能看见/控制记忆”

AutoGen 的 `MemoryQueryEvent`、CrewAI 的 source/private/events、MetaGPT 的日志/屏幕属于可观测或隔离原语，不自动形成终端用户同意、查看、编辑、删除流程。

### 4.4 垂直高风险领域的共同下限

RAG 解决时效和证据访问，验证门解决错误写回，窗口、TTL 和数量阈值解决成本与污染；三者都不能单独保证正确性、隐私或合规。

## 五、对会话切换问题的直接参照

- 会话切换首先应改变 working/session context 的边界；是否带入 durable memory 取决于显式 namespace、权限和读取动作，不能因为用户身份相同就默认把全部历史带入新会话。
- 会话内状态恢复与跨会话记忆召回是两类动作：checkpoint/state 用于恢复中断流程，Store/vector/long-term memory 用于有边界地召回可复用信息。
- 上下文压缩、摘要、抽取和去重都可能损失原文关系或造成错误写回，因此来源、时间、验证状态、版本和回看原文的路径不能被压缩步骤一并丢弃。
- 可观测事件、日志和内部 scope 不能替代终端用户对记忆的查看、编辑、删除、撤回、同意和审计控制；这些能力需要独立治理。
