# 现场记录细则

本文件服务 `interview-transcriber`。它把现场缓冲转成可回溯的 `02_访谈记录.md`，不替代主技能的状态判定、用户确认或语义保真核验。长论证的定义、证据层级和推理边界引用主技能方法学：`../interview-workflow/references/reasoning-methodology.md`；本文件只补充现场记录的执行规则，不复制该方法学。若引用缺失或冲突，暂停相关单元并回报主技能。

## 0. 全量健康核对（每次增量写入前的强制第一步）

每次新增、修正或处理任何记录增量，先读取并核对**整份** `02_访谈记录.md`，不得只检查主技能点名的段落。目标文件不存在时先核对完整模板，再进入首批写入。核对流程：

1. **读整份**：按文件原顺序读完所有 `## 阶段`、`### 问题`、待确认与待验证、记录变更。
2. **逐维检查**：
   - 单元完整性：每个问题都有问题、回应、确认状态、原始定位、记录授权；
   - 结构层级：`## 阶段` → `### 问题` 层级与推进顺序清楚，无横向扁平化；
   - 长论证保真：论证是否被压缩、拆散或改成要点清单；前提/条件限定/反例/证据等级/修正链/未决项是否保留；
   - 状态：六态准确，未被升级；
   - 授权与定位：记录授权可核、原始定位可回溯；
   - 三态回溯：报告→记录→原始底稿链条可复核；
   - 重复/冲突/版本边界：重复问题、重复定位、来源/状态/授权冲突、记录变更无法说明增量或修正关系。
3. **分类与回报**：按“结构缺失 / 保真疑点 / 状态问题 / 授权问题 / 定位问题 / 重复或冲突 / 版本边界”输出结论，区分**阻塞**与**可安全修正**。
4. **定点最小修正或暂停**：可安全修正的，只在本次授权范围内做最小定点修复，不重排全文件、不删除早期表述、不扩大授权；无法确认来源或会改变用户含义的，保留原文、停止受影响单元并回报主技能，不猜测、不覆盖。

可运行 `python3 scripts/record_gate.py --full <02_访谈记录.md>` 辅助结构检查；脚本只报结构/字段/版本边界/重复定位问题，长论证、授权与三态回溯须人工语义核对。局部请求（只让改某单元）不豁免本全量核对。

## 1. 写入前的门控

写入前逐项确认：

- 主技能已经给出访谈阶段、问题范围和写入目标；
- 受访者的原问答已经在当前阶段完成共识撮合；
- 受访者明确允许本范围进入记录；
- 每个单元都有可复核的原始定位；
- 主技能已经提供或确认六态状态；
- 保密、不记录、超出授权范围的内容已从写入批次中排除。

“请为我作答”只允许采访者代拟，不等于受访者确认；沉默、没有反对或接口错误也不等于记录授权。

## 2. 一次问答全量转写

一次问答可以整体进入一个问题单元，前提是问题边界清楚、回应完整、授权覆盖且原始定位可回溯。问题只做最小整理：保留必要的前提、语境、对象、时间范围和回答要求。回应应近乎逐段保留可见内容，只修正明显错别字、标点、断句和排版。

不要把下列内容删掉或改成摘要。以下共同构成长论证的保真链：

- 主张、依据以及从依据到结论的推理链；
- 事实细节、例证、数字和实际经历；
- “如果……”“除非……”“目前……”等限定条件；
- 反例、失败路径、犹豫、保留意见和尚未解决的部分；
- 后来对自己前一句话的补充、收回或修正。

原回答中的“可能”“我认为”“大概”“暂时还不能确定”“需要验证”等词是证据的一部分，不能为使文字更肯定而删除。

## 3. 推理链与未决项

记录者不补齐原答缺失的论证环节；原答没有说明依据、推理、限定或反例时，标明“原答未说明”。未决项单列并保留状态、缺口和影响：`[待确认]` 指需要受访者或授权者确认，`[待验证]` 指需要运行、反馈或现实证据；二者都不得改写为确定结论。

## 4. 多轮同题合并

同一个问题在多轮中展开时，合并的目标是减少机械重复，不是压缩思想。只有当各轮主题相同、授权相同且合并后仍能回溯时才合并。

建议在一个单元内按时间顺序保留轮次标签：

```markdown
**回应**：

**第一轮回应（消息 051）**：
<完整原答>

**随后补充（消息 052）**：
<完整补充>

**后续修正（消息 055）**：
<完整修正，并说明其替代早期哪一处>
```

若两轮改变了问题边界，或同一轮包含两个独立决定，应拆分问题单元。若合并会让读者误以为早期观点从未存在，应拆分或保留明确的“早期表述/后续修正”标签。机械重复只有在完全没有新增事实、理由、限定或状态且不改变顺序时才可删除。

## 5. 保留观点演进

后续表述替代早期表述时：

1. 保留早期可见内容，不静默覆盖；
2. 早期单元或段落标 `[已被修正]`；
3. 单独保留后续表述及其定位；
4. 后续状态按主技能证据填写，不自动变成 `[确认采纳]`；
5. 在“待确认与待验证”或“记录变更”说明修正关系。

只有受访者明确确认的内容才可标 `[确认采纳]`。采访者认为“听起来已经确定”不是确认依据。

## 6. 代拟、授权与保密

采访者代拟必须在回应正文中明确标记，例如：

```markdown
> **采访者代拟（按受访者既有立场拟的草稿，不代表用户已确认）**：
> <代拟内容>
```

代拟单元使用 `[专业建议·代拟]`，必要时同时列入“待确认”。受访者后来确认时，保留代拟来源和确认定位，再由主技能决定是否改为 `[确认采纳]`。

“记录授权”字段至少说明：

- 授权者；
- 授权发生的消息、轮次或时间；
- 授权覆盖的具体问题/段落；
- 保密、匿名化或不记录要求；
- 本次未写入的内容及原因（如有）。

保密内容不应通过引用、摘要、定位片段或变更说明间接泄漏。可保留不泄密的占位说明，例如“该段按授权不写入”。

## 7. 原始定位纪律

定位必须让另一位读者能返回底稿找到原文。优先使用：

- `原始底稿.md#消息-051`；
- `原始底稿.md#消息-051-053`；
- `访谈日志/2026-09-09.md#段落-12`；
- 经批准的消息 ID、时间戳和段落范围组合。

“见上文”“本轮”“访谈中提到过”不是充分定位。合并多轮时，要覆盖全部相关消息，而不是只写最后一轮定位。定位冲突时暂停该单元并回报主技能，不用猜一个地址。

## 8. 增量版本

每个阶段末只处理新增缓冲或明确授权的修订，不重写整个文件。文末“记录变更”至少记录：

```markdown
## 记录变更
- 版本：v<编号> / <日期或轮次>
- 本次增量：新增或修订的问题编号、消息范围
- 用户确认：已确认 / 待确认 / 未取得确认（写明依据）
- 未写入与原因：保密、未授权、定位缺失或冲突
```

若历史内容已经被用户确认，不要因新一轮补充而删除；用增量注明新增、修正和状态变化。若无法判断新内容是否覆盖旧内容，保守地并列保存并标记待主技能裁决。

## 9. 交付检查

脚本门禁只能检查字段形状，交付前还要人工确认：

- 写入前已对整份记录做全量健康核对并回报分类结论；
- 问题顺序与访谈阶段一致；
- 回应没有被总结、截断或补造隐藏推理；
- 观点修正可见且顺序正确；
- 代拟、用户原答、采访者复述彼此可区分；
- 状态和授权证据一一对应；
- 原始定位可以回溯，三态回溯链条完整；
- 待确认/待验证没有被阶段摘要遮蔽；
- 重复、冲突与版本边界已核对，未越出本次授权范围做全局改写。

最后运行：

```bash
python3 scripts/record_gate.py --full <02_访谈记录.md>
```

脚本通过只表示结构字段合法，不表示用户已经确认内容，也不替代保真语义审查。脚本的输出（尤其保真类警告）与人工语义核验结果须分开回报主技能。
