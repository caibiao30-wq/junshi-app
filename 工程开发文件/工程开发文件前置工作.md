# 学业军师工程开发文件前置工作

> **性质**：P3 执行宪章，交给下一轮 Claude Agent Teams 使用。它指导“学业军师工程代码开发总文件 + 派生专业文件”的起草、互辩、裁决与验收；不是最终工程规范、产品设计或技术实现，不生成运行代码。
>
> **状态**：执行规则已确认；未标为“已锁定”的事项不得被本文件或下一轮团队擅自决定。

## 1. 目的、读者与成功标准

### 1.1 目的

把现有取证、辩论与裁决材料转化为下一轮可执行的工作入口，确保下一轮团队：

1. 先补足产品自持硬边界和工程可落地语义，再写规范；
2. 真实互辩而非并行拼稿；
3. 把产品 `WHAT`、工程机制 `HOW`、候选组件事实和待用户决定分开；
4. 交付可回溯、可验收、可进入后续工程代码阶段的规范文档包。

### 1.2 读者

- 下一轮团队主控、总协调、各专题起草人、辩论人和质检人；
- 用户（最终产品责任与关键门的裁决者）；
- 后续维护规范和实现代码的 Agent。

### 1.3 成功标准

下一轮结束时，读者应能回答：工程文件写了什么、没有写什么、每项依据是什么、哪些仍须用户决定、怎样验证，以及在什么条件下必须停止。

## 2. 输入边界与不可越权事项

### 2.1 允许输入

按证据权重使用：

1. 用户明确判断与终局访谈；
2. 已确认采纳的访谈结论；
3. 三份开发指导 PDF 的逐字事实；
4. `_证据包.md`、辩论/反驳稿、`_共识.md`、候选名单和本目录 `CLAUDE.md`；
5. 外部组件的官方仓库、许可证、版本、依赖、构建和运行证据（仅用于候选准入）。

输入必须保留来源文件、页码/行号、状态和取得时间；材料之间冲突时不得静默合并。

### 2.2 工程文件范围

只落实**学生端产品本体**。云端、B 端、后端、机构管理、教师售后仅在说明学生端闭环依赖时提及，不写成学生端工程规范内容。学生是现实材料的唯一必要承接者；终局访谈已取消教师批注、评分、评语、意见、评价及学生转述教师意见作为产品输入或效果裁判，历史材料须标为已被修正。

### 2.3 不得替用户决定

以下事项必须成为用户门；没有用户明确决定，下一轮只能写问题、选项、影响和验证计划：

- 回滚单元、版本语义、错误补偿和业务回滚边界；
- 首版学段/年龄、首要学科、典型任务、首版对象及核心字段；
- 教师回流是否存在、回流内容和权责；
- 本地 Agent 的语言、运行形态和部署边界；
- 云端模型机构/API 供应商、成本、稳定性与数据条款；
- CRDT 是否采用及同步的最终状态语义。

## 3. 六类文件的性质与互斥关系

## 4. 下一轮团队：真实互辩顺序与职责

### 4.1 工作顺序

不得把专题并行拼成终稿，必须按以下门控顺序：

1. **启动与取证复核**：主控确认输入版本、状态标签、用户门和本文件边界；证据审计人抽查引用闭合。
2. **专题独立拆解**：产品边界/责任、数据证据/审计、状态/回滚、编排/运行、组件/技术栈、验证/风险各自提出候选方案、反例、缺口和停止条件。
3. **第一轮交叉质询**：每个专题至少由非本专题成员质疑 `WHAT`、`HOW`、依据等级、失败后果和越权风险。
4. **第二轮往返互驳**：原提案人逐条回应；不能回应的降为待验证或上报用户门。涉及 G1/G2、G3/G7/G10/G11 或 V-07 的争议不得由起草人单方收敛。
5. **收敛与用户门**：总协调形成必改/应改/待拍板/待验证矩阵，逐项提交用户；未拍板项不能伪装成规范要求。
6. **分层起草**：先写总文件，再由专题起草派生文件；每份文件注明完成定义、验收标准、实际证据和未验证边界。
7. **反向审查**：质检人只读审查引用、状态、边界、互相链接、重复权威和硬停条件；发现问题退回专题，不自行补决策。
8. **交付门**：主控汇总实际验证结果、剩余用户门与回溯索引，呈用户验收。

### 4.2 角色职责

- **用户/主控者**：产品责任、用户门和最终争议裁决者；不由 Agent 代签。
- **总协调**：拆任务、维护唯一状态表、安排互辩、升级冲突、控制范围和交付顺序；不得以协调权替用户决策。
- **产品边界辩论人**：审查学生端责任、学生控制、教师回流、首版对象与产品 `WHAT`。
- **数据/状态/回滚辩论人**：审查证据模型、G1/G2、合法状态机、版本与影响传播；不得自行确定回滚语义。
- **编排/运行辩论人**：审查 Agent 责任契约、调用/交接、失败语义、G10 和本地运行边界。
- **组件/技术栈审查人**：只报告候选机制和 HOW，执行许可证、范围、本地运行与替换验证；不得宣布采用。
- **验证/风险审查人**：建立 G1/G2/G3/G7/G10/G11 与 V-07 的验证证据矩阵，检查安全、可回退和验收可行性。
- **专题起草人**：仅在用户门通过后写对应规范章节，保持证据和状态标签。
- **质检人**：只读检查，不修改产品判断，不替缺口补写事实。

### 4.3 通信、任务与用户门

每项任务必须有：负责人、输入版本、输出文件/章节、依赖、状态、验收动作、升级对象。通信消息使用“结论—状态—依据—影响—请求动作”格式；争议逐条引用，不用“大家同意”代替记录。

用户门的通过条件是：给出选项、产品影响、工程影响、反例、所需证据和建议；用户未明确通过时标记“待拍板”，暂停依赖该决定的写作。升级路径为：专题成员 → 总协调 → 用户。

## 5. 状态规则与缺口处理

所有结论逐条标注：`事实`、`用户明确判断`、`确认采纳`、`团队推断`、`候选`、`暂定`、`待验证`、`待确认`、`待拍板`、`已被修正`或`未取到`。

- **必改**：已由证据/用户门证明不补齐就无法安全、可追溯或可验收；必须写入规范或明确阻断，并写“为何必改/不改后果”。
- **应改**：有充分依据且明显提高可执行性，但不应冒充产品决定；可在资源允许时纳入。
- **待拍板**：涉及产品责任、最终语义、范围或不可逆选择；先呈用户，未通过不得落为规则。
- **待验证**：可通过代码、运行、许可证、平台或真实任务验证；须写验证动作、证据、负责人和通过阈值。

G1（业务回滚语义）与 G2（审计字段及防篡改）属于当前承重缺口：可先写问题结构和确定性承载要求，但不能发明业务定义。V-07 是本轮必须纳入验证矩阵的编号：下一轮启动时先从已批准的验收/验证材料核对其完整定义、来源、责任人和通过阈值；若无法核对，V-07 标为“待确认”并触发硬停，不得擅自扩写其含义。

## 6. P3 准入硬门与七类硬停

### 6.1 P3 准入硬门

进入规范起草前必须同时满足：

1. 输入材料版本和证据索引已核对；
2. 学生端边界、终局教师反馈修正和单实例/本地权威原则已显式写入；
3. G1、G2 的产品语义缺口与工程承载边界已分层；
4. G3 合法状态机、G7 外部信源边界、G10 编排责任、G11 首版对象均有处理状态；
5. V-07 已核对定义，或已明确列为待确认用户门；
6. 每项候选组件均有 HOW/WHAT 分离记录和准入负责人；
7. 团队成员、通信、任务、用户门和停止升级路径已确认；
8. 外部指导文件优先级已锁定为 `agent-framework.pdf` &gt; `22365_19_Agents_v8.pdf` &gt; `a-practical-guide-to-building-agents.pdf`，但每一条采纳仍须逐项门禁，不能因优先级自动变成产品决策。

### 6.2 七类硬停

任一情形出现即暂停相关写作并上报，不静默补齐：

1. **证据硬停**：关键结论没有可回溯来源，或外部信源只有推断；
2. **状态硬停**：事实、候选、确认、待验证或已被修正混写；
3. **产品语义硬停**：G1/G2、首版对象、教师回流或其他用户门未决却被写成确定规则；
4. **权限安全硬停**：无法证明确定性校验、不可逆拦截、审计完整性或越权隔离；
5. **范围责任硬停**：把云端/B 端/后端、教师主观评价或组件能力写入学生端本体责任；
6. **组件准入硬停**：许可证、依赖、范围、本地运行、迁移、替换退出或实际验证缺失；
7. **验收一致性硬停**：完成定义/验收标准/实际证据/未验证边界缺一，或 V-07 无法核对、互辩未完成、链接/状态表不闭合。

## 7. 产品 WHAT 与候选 HOW

先回答“学业军师必须对什么负责、对象是什么、何时允许发生、失败后果是什么”（WHAT），再回答“哪个框架、协议或库能承载其中哪一段机制”（HOW）。外部指导文件只提供工程方法和机制事实，不能定义客观证据、唯一状态源、权限确定性、审计链、业务回滚或学生责任。

### 7.1 候选名单维护

`_候选组件名单.md` 是候选登记表，不是采用清单。每个候选必须记录：名称/版本/来源、能力单元、拟承载 HOW、不能承载的 WHAT、许可证与商业范围、依赖维护状态、目标平台、本地离线/恢复表现、数据和权限边界、迁移与替换路径、验证证据、处理建议（复用/改造/受控整合/隔离/暂缓/放弃/自建）及状态。

准入顺序遵循 0.5→1：复用 → 改造 → 受控整合 → 必要重构 → 最后自建。五类门禁逐项通过：产品责任、能力适配、运行可靠、安全治理、替换退出。代码或文档“声称支持”不等于本地运行通过；许可证未核、目标范围不明、无法在目标环境运行、无法迁移/替换或移除后产品本体不成立，均不得进入首版采用结论。候选名单的增删改须保留日期、依据、状态和回溯来源。

## 8. 执行力手册级与技术设计级的分界

本文件是**执行力手册级**：规定谁在何时读什么、做什么、交付什么、怎样互辩、何时停、谁裁决。下一轮规范交付才进入**技术设计级**：在用户门通过后定义对象字段、状态迁移、接口契约、编排模式、失败/重试/取消、验证样例和实现约束。

执行手册不得偷渡数据库表、API、模型供应商、语言或最终状态机；技术设计不得绕过本文件的证据、状态、权限、范围和用户门。任何技术设计级提议若改变产品 WHAT，退回产品辩论和用户门。

## 9. 规范交付验收指标

下一轮交付必须满足：

- 总文件和每份派生文件均有目的、范围、输入、输出、责任、完成定义、验收标准、实际证据、未验证边界；
- 100% 结论有状态标签，100% 关键结论有文件+页码/行号或运行证据；
- G1/G2 有明确的产品语义待决项、工程承载边界和阻断条件；
- G3/G7/G10/G11 与 V-07 均有状态、责任、验证动作和用户门（如适用）；
- 每个 Agent/工作流关系标注 routing、并行、orchestrator-workers 或顺序 workflow，并写清失败、超时、冲突、取消、重试语义；
- 候选组件全部完成 HOW/WHAT、许可证/范围、本地运行、迁移和替换记录；
- 学生端与云端/B 端/后端边界无越界，教师主观反馈无回流为默认证据；
- 规范可从一条单学科/单任务最小闭环读通，并具备 L1 机制测试与 L2 故障注入的验收入口；
- 通过 Markdown 格式检查、链接检查、交叉引用检查和只读质检；未执行项如实列出。

根 `CLAUDE.md` 单线化已确认：以工程开发为当前主线，移除 SVC 对本工作流的现行约束；但历史 SVC 材料只作历史承接和溯源，不得删除其历史事实，也不得重新成为本工程规范权威。
