## 0. 架构视角的总体判断（先给结论）

证据包把「五项产品自持硬边界」（客观证据模型 / 唯一状态源与生命周期 / 权限与确定性强制 / 证据审计链 / 业务回滚语义）确认为产品自持、三份外部信源对它们全部 `[未取到]`——这一点我完全认同，**但正因如此，工程前置最大的风险不是"框架不够"，而是"产品自持边界自身还没到可开工颗粒度"**。从工程可实现性看，五个自持边界里，有四个（回滚语义、合法状态机、审计防篡改、确定性强制项清单）都停在"原则已确认、字段/迁移/实现细节未成文"，而技术栈又全 `[暂定]`。**原则层已足够、规范层欠颗粒度、实现层零锁定**，三者之间存在承接断档。这是本报告的总主线。

## 1. 业务回滚语义完全未成文（最缺成文定义的自持硬边界）

- **①问题陈述**：证据包 G1 已确认为最缺项——三份外部信源（MS checkpoint/恢复、GOOG T7、OAI p26/p31）全部 `[未取到]` 业务级回滚单元/版本/错误补偿；访谈仅枚举「底层设施含回滚」，未成独立语义专题。**工程上这是死穴**：没有「回滚单元」定义，就无法确定版本语义；没有版本语义，就无法写审计"迁移前后"；没有错误补偿，就无法处理"回滚一个判断对象时其下游规划/任务/资产引用"。
- **②证据依据**：`_证据包.md` ④ G1（L260）；[MS] p790/p854-855「checkpoint 恢复/重置」=技术级、非业务回滚（T7 L167）；[GOOG]/[OAI] T7 全 `[未取到]`；[上下] 门禁7「先定义业务语义再选 Temporal/LangGraph 等机制」（L166）；[工开CLAUDE] L49「不冒充为恢复/重放」。
- **③状态标签**：`[事实]`（未成文）+ `[用户明确判断]`（硬边界须自持）。
- **④分类**：**必改**。
- **⑤不改后果**：起草团队将无法写「派生·数据模型 / 状态机 / API」三件专业文件中的回滚章节；或退而用 checkpoint/重放冒充（[上下] §8.3 明确列为"屎山入口"，L73）；或把回滚外包给框架——三条全部违反已锁定的硬边界。没有回滚单元，G3 状态机与 G2 审计链也连带无法闭合。

## 2. 主控/专项/横向域责任契约未成文，编排确定性设施无法落地

- **①问题陈述**：证据包 G10 确认「主控军师与专项 Agent 分工边界/调用规则/判断权/责任归属」`[待确认]`（[访1] L3796-3810）。工程视角：这是编排的**地基**——总军师/学科军师/专项/横向域的"唯一主责、输入输出、交接、冲突裁决"若只是角色名，[上下] §8.3 已明确"用命名替代真实责任契约=屎山入口"。没有逐 Agent 的责任契约（输入/输出/状态/权限/后果），编排确定性设施（T4「谁在何时可调用谁、读什么、写什么、交接是否合法，由底层校验」）就无从编码。
- **②证据依据**：`_证据包.md` T5（L134-138）结构已确认但"编排状态机待实现"；[上下] §4.1「谁何时可调用谁…具体编排状态机未定」（T5 L57）；[上下] §8.3 L214；[工开CLAUDE] 准入门清单最后一步「最小 Agent/工作流编排 + 每条关系标注 routing/并行/orchestrator-workers/顺序 + 失败语义」（L88）。
- **③状态标签**：`[待确认]`（用户/访谈未决）+ `[用户明确判断]`（门禁5 要求各定唯一主责）。
- **④分类**：**必改**（作为进入编排状态机成文的前置门）。
- **⑤不改后果**：编排状态机、会话↔责任域绑定、交接包（访2 3-2 已定义交接包结构但缺 Agent 侧契约承接）全部悬空；团队要么先用角色名占位（屎山），要么等边界却阻塞后续全部编排文件。此 `[待确认]` 是进入 T5 成文的硬门。

## 3. 合法状态机未成文（G3），而它是确定性强制的核心载荷

- **①问题陈述**：证据包 G3 确认——具体状态迁移表、触发阈值、每对象状态机名称与迁移条件 `[待确认]`（[访2] L937/L1439、[访3] L177）。工程视角：**T4 的"状态迁移合法性由确定性代码强制"本质上就是把状态机编译成代码**。状态机不先成文，迁移合法性校验、非法迁移拦截、候选/生效分离就都没有可实现的输入。访谈已给大量"禁止"（候选不能直接写成生效、任务生成≠任务完成、无确认不升级）但未给"允许的合法迁移集合"。

- **③状态标签**：`[待确认]` + `[用户明确判断]`（硬边界自持）。
- **④分类**：**必改**。
- **⑤不改后果**：确定性强制（硬边界之一）无载荷可挂；状态迁移校验只能靠 Agent 自律（违反 T4）；候选/生效分离退化为约定而非强制；审计"状态迁移前后"字段无法填。

## 4. 技术栈全 `[暂定]` 与「确定性强制项清单」之间的顺序风险

- **①问题陈述**：证据包 G6 确认 Flutter/Dart、SQLite/SQLCipher、Fastify 等全部 `[暂定]`，须原型验证后才 `[确认采用]`（[访3] L3700-3712）；而确定性强制（T4 强制项清单）依赖具体栈承载。**存在顺序风险**：若先锁栈再定强制项，则强制项会被栈能力反向塑造；若先定强制项再锁栈，则"强制项→机制承载"映射要到栈验证后才可写。证据包/工开CLAUDE 已给方向（门禁7「先定义业务语义再选机制」），但**没给确定性强制项的技术无关定义层级**。
- **②证据依据**：`_证据包.md` G6（L265）；T4（L119）外部信源仅"方向一致但均 [未取到] 学业军师级确定性校验"；[上下] §4.5「12-factor 未讨论、LangGraph 依赖运行图而非确定性策略层」（T4 L51）；[工开CLAUDE] L62「单一权威状态源、避免多框架/状态层叠加」。
- **③状态标签**：`[待验证]`（栈）+ `[确认采纳]`（机制后置原则）。
- **④分类**：**必改**（定一个技术无关的「强制项→承载机制候选」对照表，作为锁栈的验收口径）。
- **⑤不改后果**：锁栈时没有"该栈能否承载确定性强制"的验收标准，原型验证（L3700）会漏掉最关键的硬边界承载检验；或强制项设计被某一暂定栈反向绑架。

## 5. 证据/审计链防篡改成文不足（G2），SQLCipher 加密≠防篡改

- **①问题陈述**：审计链已确认"字段完整防篡改"原则，但**审计字段表与篡改防护实现细节未成文**（G2）。工程要点：暂定栈里的 SQLite/SQLCipher 解决的是"静态加密"（rest 加密），**不解决"防篡改"**（防已授权进程内的篡改/防日志被改）。要在 SQLite 上实现可证伪的审计链（哈希链/追加式 append-only 账本/单调序号），是**产品自建项**，三份外部信源只给运行时可观测/日志（[MS] 中间件、OpenTelemetry、Final Transcript），全部无签名/账本机制。
- **②证据依据**：`_证据包.md` G2（L261）；T6（L153）[MS]/[GOOG]/[OAI] 均无"审计字段防篡改/证据链签名/防篡改账本"；[访2] 3-1 审计字段表（L147）已列字段但未成"防篡改"设计；[访3] 7-5「审计记录自身须完整、防篡改」（L142）。
- **③状态标签**：`[待验证]`（实现细节）+ `[用户明确判断]`（硬边界自持）。
- **④分类**：**应改**（起草须在数据模型/安全专业文件里给出「审计字段表 + 篡改防护设计」）。
- **⑤不改后果**：防篡改沦为口号；审计链被框架日志冒充（违反硬边界）；撤回/删除留痕的"保留必要审计关系但不继续在被禁用途下使用"（[访3] 7-5）无落地载体。

## 6. 外部信源引用边界（G7）未成文，起草有过度依赖 agent-framework 的风险

- **①问题陈述**：三份外部信源对五项硬边界全部 `[未取到]`，只给"机制候选"。但 agent-framework.pdf 被列为「主/工程权威（唯一遵循第一位）」。工程风险：**起草团队可能把 MS 框架文档当成产品架构权威**，用它反向定义学业军师的机制选择——这违反"用框架/SDK 反推产品责任=Don't"（[上下] 门禁1）。需成文一条"引用边界"：外部信源=机制菜单（HOW 的候选），产品硬边界=语义自持（WHAT 的裁决）。
- **②证据依据**：`_证据包.md` G7（L266）；[上下] §5「Microsoft/Google 两份外部信源不影响产品自持硬边界结论」（T9 L140）；[工开CLAUDE] L23「任何外部文档/框架/SDK 都不能替代产品自持硬边界」；门禁1 L52。

## 7. 多代理冲突裁决/优先级语义只有名义、没有确定性仲裁协议

## 9. 开发指导优先级链的可执行性：MS「主/工程权威」与暂定栈 Dart/TS 的落差

## 10. 首版确定性强制的最小集未定（MVP 强制项 vs 全量强制项）

- **②证据依据**：`_证据包.md` T4（L106 强制项清单）；T8 首版=单学科/单任务最小闭环（L182-183）；[访3] 7-1「至少强制项」（L106）；[上下] §8.2(1)「先做最简单可验证闭环」。
- **③状态标签**：`[确认采纳]`（强制项全集）+ `[待验证]`（首版最小子集取舍）。
- **④分类**：**待你拍板**。

## 二、你最想提请辩论组争辩的 3 个工程问题

1. **业务回滚语义的工程载体**：回滚单元/版本语义/错误补偿，该落成「对象级版本快照 + 下游引用重定向」还是「事件溯源 + 补偿」，还是「SQLite 事务 + 应用层补偿」？在"先定义语义再选机制"（门禁7）与技术栈全暂定的夹缝里，起草应给到什么颗粒度才算"可开工"？

2. **确定性强制项 vs 技术栈的先后**：五大自持硬边界的确定性强制，哪些能由 SQLite/Flutter/Dart/TS 原生承载（DB 约束/触发器/类型系统）、哪些必须自建（哈希链审计、状态机迁移校验、业务回滚补偿）？是先锁栈再验承载，还是先定"强制项→承载机制候选"对照表再锁栈？顺序不同，验收口径完全不同。
