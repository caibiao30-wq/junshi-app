# 学业军师工程开发目录总则

> 本文件是 `工程开发文件/` 目录的总则：划定**前置研究层**与**工程规范交付层**的边界，确立「工程开发总文件 + 派生专业文件」这套开发标准工程规范文档包的撰写、审查与验收纲纪，并给出进入工程代码阶段前的**准入门**。上层约束以根 `CLAUDE.md` 为**上位仓库宪法**，本总则不得与其冲突；冲突时以根 CLAUDE 为上位。

## 材料分层：前置研究层 vs 工程规范交付层

前置研究层与工程规范交付层**分离，不混用、不越级**：

- `访谈资料/`（含 `draft/`）：学业军师的产品设计与构思来源，不是工程规范。
- `调研报告/`：外部取证与研究证据，不是工程规范。
- `工程开发文件/` 中的 `_证据_*`、`_候选草稿_*`、`_候选组件名单*`、`_批判_*`、`_反驳_*`：**前置研究产物，不是规范包**。
- **候选草稿、候选名单、证据、批判、反驳均不是规范包**；**批判与反驳是辩论输入而非裁决**，任何批判 / 反驳条目不因被写入本目录即成为已定规范，不自动进入规范包。
- 本目录内容不反向被 `mate/`（已删除）、历史 `STRUCTURE.md` 或任何已被取代的旧规则限制。

## 规范包与交付

- 后续交付物是**工程规范总文件 + 派生专业文件**（架构、数据模型、API、模块规格、技术栈、验证标准、部署边界等）。
- 每个派生文件带「完成定义 — 验收标准 — 实际证据 — 未验证边界」；不满足就停在当前层，不为保持进度向后堆文档。
- 单一权威状态源；避免同时叠加多个框架 / 状态层 / 记忆系统。

## 执行力手册级 vs 技术设计级

- 本目录工程文件达到**执行力手册级**：判据、责任、边界、阶段门、验收标准**成文**，可直接支撑工程代码实现。
- **技术设计级**（具体实现细节）后置于工程代码阶段，不在本目录预先锁定。
- **候选机制不得承载产品 WHAT**：候选草稿 / 候选名单只承载「机制 / 如何」的候选，不承载「产品内容 / WHAT」；产品 WHAT 由产品 / 用户裁决，不由候选机制或工程推断决定。

## 开发指导文件优先级（唯一遵循，已锁定）

工程代码开发**唯一**遵循以下开发指导文件，按优先级：

1. `agent-framework.pdf`（主 / 工程权威）
2. `22365_19_Agents_v8.pdf`（次）
3. `a-practical-guide-to-building-agents.pdf`（OpenAI 官方工程方法论）

以下仅作**参考层 / 外部资料**，不作架构依据、不反向定义学业军师本体：

- `12-factor-agents`：原则清单（状态统一、人审门、小而聚焦、可运维）仅借鉴。
- LangGraph / LangChain 官方：仅外部资料参考、优先级最低；是否纳入首版待研究验证，不作既定选择。

**外部指导文件的优先级已锁定，但组件采纳强度不自动锁定**：外部指导文件对通用工程原则（编排、人审门、工作流判断等）的权威，不自动延伸到对具体组件 / 框架的采纳强度；组件是否进入首版按「外部组件准入门」单独评估。

## 0.5→1 开发路径（百分百遵循）

- 全产品复用改造原则：**拼接缝合改造 ＞ 重构 ＞ 自建**；凡已存在、能验证、与产品目标相容的开源项目 / 模块 / 工具 / 协议优先纳入复用、改造、重构、整合候选，只有都不适合才自建。
- 每个能力候选按「外部组件准入门」评估：产品责任 / 能力适配 / 运行可靠性 / 安全治理 / 替换退出 / 集成验收，逐项过，决定复用 / 改造 / 整合 / 隔离 / 暂缓 / 放弃 / 自建。
- 第一交付不是完整产品，而是**单学科 / 单任务最小闭环 + L1/L2 验证包**，之后才逐步扩展。

## 范围边界

- 工程文件只落实学业军师**学生端产品本体**。
- 云端 / B 端 / 后端仅在闭环语境下「提及」，其内容**不纳入**本目录工程文件。

## 产品自持硬边界（不可外包）

学业军师产品层的以下硬边界由**产品自持**，不外化给任何外部文档、框架或 SDK：

- 客观证据模型（外部证据与内部证据的字段、边界与来源）；
- 唯一状态源与生命周期（候选 / 生效 / 暂停 / 回退 / 失效 / 撤回 / 删除 与合法迁移）；
- 权限与确定性强制（证据字段完整性、状态迁移合法性、不可逆拦截由确定性代码强制，不靠提示词）；
- 证据 / 审计链（每个判断 / 规划 / 行动 / 修正可回溯到客观证据或内部真实记录，审计字段完整防篡改）；
- 业务回滚语义（回滚单元、版本语义、错误补偿由产品层定义，不冒充为恢复 / 重放）。

## 状态与证据规则

- 每条结论标注状态：事实 / 用户明确判断 / 专业建议 / 候选 / 待验证 / 待确认。
- **不把用户待拍板事项写成已决定**：涉产品责任 / 学生控制权的裁决标记 `[待用户拍板]`，在工程规范层不擅自决定。
- 不把推断、候选、阶段性材料写成已确认事实；不因「有用」就定为首版。
- 工程文件由访谈记录进化而来，不另立与访谈相悖的设计；如与访谈冲突，暂停并报告，不自行裁决。

## 读写纪律

- 默认只读；新建文件须明确授权；不覆盖既有文件。
- 写入前核对目标、授权、来源、状态与影响范围，遵循最小变更原则。
- **候选草稿 / 候选名单 / 证据 / 批判 / 反驳不因本总则而改动**；它们作为辩论输入与证据存留，裁决权不在起草方。

## 准入门清单（工程文件 → 工程代码阶段）

进入工程代码实现前，须**逐项满足**以下清单；未通过不得进入业务实现。顺序即依赖顺序。

```text
1. 产品责任与范围（锁死最高责任 / 非责任 / 外部关系）
  ↓
2. 客观证据 / 内部证据模型（字段与边界成文）
  ↓
3. 唯一状态源与生命周期（合法迁移 + 候选 / 生效分离）
  ↓
4. 权限、确定性拦截、审计字段
  ↓
5. 单学科单任务最小闭环样例
  ↓
6. L1 机制测试 + L2 故障注入
  ↓
7. 最小 Agent / 工作流编排（每条关系标注 routing / 并行 / orchestrator-workers / 顺序流程 + 失败语义）
  ↓
8. 再扩展学科、多代理、终端
```

**步骤 2–4 拆「已定结构 / 待用户拍板」两栏**：

| 步骤 | 已定结构 | 待用户拍板 |
|---|---|---|
| 2. 客观证据 / 内部证据模型 | 客观证据与内部证据的字段、边界与来源由产品自持成文（硬边界 #1） | 字段表与来源颗粒度等产品语义由产品 / 用户裁决 |
| 3. 唯一状态源与生命周期 | 候选 / 生效 / 暂停 / 回退 / 失效 / 撤回 / 删除 与合法迁移机制由产品自持成文（硬边界 #2） | 「允许的合法迁移集合」与触发阈值（`[访2]` L937 待确认）由产品 / 用户裁决 |
| 4. 权限、确定性拦截、审计字段 | 权限与确定性强制、证据字段完整性、不可逆拦截由确定性代码强制（硬边界 #3）；审计字段完整防篡改原则（硬边界 #4） | 审计字段表与防篡改实现细节（G2）、首版最小确定性强制集取舍由产品 / 用户裁决 |

**硬停门（任一未达即停，不静默补齐）**：

- **架构符合性门**：工程规范须与其所依赖的上层约束（访谈、外部指导文件、根 CLAUDE）符合，不引入与之相悖的设计。判据在工程规范总文件中成文。
- **V-07 质量门**：进入工程代码阶段的质量关卡，判据在工程规范总文件中成文（本次未定义，待成文）。
- **G1 业务回滚语义**（回滚单元 / 版本 / 错误补偿，硬边界 #5）：未成文，不得进入工程代码实现。
- **G2 证据审计防篡改**（审计字段表 / 篡改防护实现细节，硬边界 #4）：未成文，不得进入工程代码实现。

任一步骤「完成定义 / 验收标准 / 实际证据 / 未验证边界」任一缺失，即视为未达门，应停止并回报，不静默补齐。
