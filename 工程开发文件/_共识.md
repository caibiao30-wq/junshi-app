## 二、已锁定决定(5 轮 18 项,均为 [用户明确决定])

### 角色与产出
1. 主控角色：用户为主控,我(CEO)负责编排/委派/质检；[已定] 我**全权裁决**执行与方向,分歧我裁、关键项呈用户备案。
2. 产出形态：开发标准工程规范文档包(总文件+派生专业文件)，不上层设计、不直接生成可运行代码。
3. 工作文件定位：代理团队执行/协作宪章，`工程开发文件/工作文件.md`，**执行力手册级**——下一执行团队照单可开工。
4. 交付内容：工作文件 + 根 `CLAUDE.md`(彻底移除 SVC,改单线工程开发)+ `工程开发文件/CLAUDE.md`；**含下一团队首次启动清单**。
5. 三层关系：规则不掺执行、任务不越权改规则、单向可溯(工作文件只引用执行、不重定义;CLAUDE.md 不含执行细节)。

### 证据与起草原则
6. 只基于仓库既有事实起草,不主观臆想；PDF 用 `pdf` 技能、文档用 `md-writing` 技能。
7. 开发指导优先级(已修订)：唯一遵循 agent-framework.pdf(主)>22365(次)>OpenAI guide；12-factor-agents 仅参考层;LangGraph/LangChain 仅外部参考、0.5-1 候选待研究。
8. 范围边界：工程文件只落实学生端产品本体；云端/B端/后端仅闭环「提及」不纳入。

### 辩论与探究
9. 辩论授权：**可挑战已锁定决定**；推翻项标「待你拍板」，不自动生效。
10. 辩论形态：多轮互辩收敛(三视角先独立批判→往返互驳→收敛)；最激烈、以挖根为要。

### 不足清单与效力
11. 清单效力：分层——「必改」=硬约束、「应改」=参考、「待你拍板」=先呈用户,未拍板不视为生效。
12. 生效机制：不足清单=下一团队**开工前置门禁**，开工前逐项回应(采纳/驳回+理由)，由用户把关。
13. 状态标注：强制逐项标注(事实/用户判断/团队推断/待验证/待你拍板)，缺标不得过门。

### 团队与协作
14. 写权限：分工各司其职——各环代理写自己中间产物(证据包/不足清单/辩论记录)；起草代理写最终三件；质检只读。
15. 汇报结构：代理间可多轮互发协作；最终结论、共识、分歧逐级汇我(CEO)综合与裁决后再呈用户。
16. 停止条件：工作文件写**硬停条件**(证据不足/冲突未解/验收不可行/权限不清)，触发即暂停上报；升级路径=代理→我→用户。
17. 冲突处理：辩论发现与访谈/已确认门禁冲突时，由我(CEO)裁决后备案。

### 产出结构与验收
18. 产出结构：TOC + 状态总表 + 证据定位索引；三份文件编号排序 + 相对路径互引。
19. 质检判据(量化硬指标)：①每条结论可回溯来源；②状态标注覆盖率 100%；③每必改项有「为何必改+不改后果」论证；④与三层模型/已锁定决定一致；⑤下一团队照单可开工。
20. 备份回滚：升级两份 CLAUDE.md 前先 git 快照，可一键回滚。

### 规模护栏
21. 成本护栏：辩论≤3 视角×≤2 轮、总代理≤10、每阶段明确停止条件，质量不减、成本可预期。

## 三、执行方式(团队与阶段)

阶段顺序(每阶段过门):
1. **取证** `evidence`：只读调阅全部事实材料(含 3 PDF via pdf 技能)，产 `_证据包.md`(来源引用、事实/推断分层)。
2. **辩论** 3 批评代理(critic-product / critic-arch / critic-risk)：多轮互辩，产出各自缺陷报告。
3. **综合** `synthesizer`：合并为「不足与必改清单」(必改/应改/待你拍板 分层)。
4. **起草** `工作文件起草`+`CLAUDE.md 升级`：写三份交付(含不足清单章节、启动清单、TOC/总表/证据索引)。
5. **质检** `qc`：按量化硬指标判过/否。
6. 升级前对两份 CLAUDE.md 做 git 快照。

用户验收门：证据包 →(审)→ 不足与必改清单 →(审)→ 终版三件 →(审)。三环均需用户把关后才进下一环。

## 四、明确不做
- 不生成可运行代码、不做上层设计。
- 不把推断/候选写成事实；必改项未经用户逐条拍板不自动生效。
- 不越过阶段门；任一硬停条件触发即暂停上报，不静默补齐。
