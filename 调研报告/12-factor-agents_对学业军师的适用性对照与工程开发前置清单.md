# 12-factor-agents 对学业军师的适用性对照与工程开发前置清单

> 文档状态：主体初稿。编写时间：2026-09-14。
> 用途：为学业军师从"访谈确认"进入"代码工程"阶段前，提供外部方法论对照、不成熟处诊断、修进方向与前置门禁，避免进入工程后堆砌屎山。
> 证据边界：本报告的外部信源为一手取证；MS/Google 两份待补，已在对应节如实标注。涉及学业军师内容的，均来自 `02_访谈记录.md`（方向 0–13）已确认项；未确认/未验证处单列，不冒充事实。

## 0. 一句话结论

**12-factor-agents 对学业军师是有价值的"清单式参考"，但绝不是充分参考，更不能反向定义学业军师本体。** 它覆盖"状态统一→可恢复、人工确认门、小而聚焦 agent、可运维"等原则，对长期运行 agent 产品有直接启发；但它偏单 agent + 工具调用范式，**没有覆盖多代理编排、严格状态机、证据/审计链、业务回滚、数据本地化、确定性保证**——而这几项恰恰是学业军师必须在产品层自建的硬边界。学业军师真正的工程准备，应在"产品责任与契约先立"上用功，而非"复用什么框架"上优先。

## 2. 12-factor-agents 是什么（一手，与经典 12-factor 的区别）

- **是什么**：一份"方法论清单（针对 agent 的 12 条全新定义）+ 最小代码模板（packages/create-12-factor-agent）+ 从零实战教程（workshops）"的仓库，**不是可 import 的生产框架**。
- **关键澄清**：它**借用 "12-factor" 品牌与清单形式**，但内容是针对 agent 的**全新 12 条**，**并非**把经典 12-factor（Codebase/Deps/Config…）映射到 agent。经典 12-factor 的目标是"可移植、可部署、可运维的 Web 服务"，而它转为"如何把一个 agent 产品模块化、可测试、可运维"。
- 许可证：Apache-2.0（内容另为 CC BY-SA 4.0）；star 25.8k；TypeScript；创建 2025-03-30。

## 3. 12-factor-agents 对学业军师有直接价值的部分

以下因素（一手确认）对"把学业军师做成可运维、可测试、可恢复、有边界的长期产品"有直接启发，**可并入学业军师的方向 7/8 工程边界**：

| 12-factor 因素（针对 agent） | 价值 | 与学业军师对应 |
|---|---|---|
| 状态统一 / 可恢复 | 状态有明确边界与生命周期，运行可恢复 | 方向 6/7：状态模型、候选与生效分离、暂停/恢复 |
| 人工确认/批准门 | agent 在关键处等待人审，不擅自行动 | 方向 3/6：重大事项须学生/责任方确认，候选不生效 |
| 小而聚焦的 agent | 每个 agent 职责单一、可测试 | 方向 1/6：术业有专攻、专项 Agent 唯一主责 |
| 可运维/可观测 | 运行可观测、可排障 | 方向 7：审计、观测、回滚 |
| 错误自愈 / 边界 | agent 错误有处理路径，不越界 | 方向 7：失败阻断、不归咎学生、产品内部消化 |

**能复用的**：这些"原则层"思想。**不能复用的**：它的具体实现（模板、SDK、文件系统状态存储），因为学业军师的多代理结构、证据/审计/本地数据语义与之不同，不能反向定义。

## 4. 学业军师当前不成熟处（对照外部方法论 + 02 访谈确认）

> 以下"不成熟"指：访谈已确认边界但**尚未在工程层面落地 / 尚缺具体实现细节**的部分。它们不是缺陷本身，而是**进入代码前必须补强的点**。

### 4.1 多代理编排（最大缺口，外部方法论普遍覆盖不足 + 学业军师结构最复杂）
- 学业军师是「总军师 + 学科军师 + 专项 Agent + 横向责任域」的多代理结构（方向 6 Q6-4），比 12-factor-agents 的单 agent 复杂得多；
- 12-factor-agents、OpenAI/Anthropic 主要讲单 agent 或简单多 agent；**学业军师的跨学科调度、优先级、交接、冲突裁决**无现成方法论直接套用 → 必须产品层自建编排契约。
- **不成熟点**：谁在何时可调用谁、读什么、写什么、交接是否合法——方向 7 已确认"由底层确定性设施约束"，但**具体编排状态机未定**。

### 4.2 证据/审计链
- 学业军师以客观真实证据驱动（方向 3 Q3-8）；12-factor-agents / LangGraph 均**未覆盖**证据链、审计、不可抵赖；
- **不成熟点**：外部证据（排名/成绩/试卷/作业）→ 判断 → 规划 → 行动 → 反馈 → 资产的全链回溯，需产品层定义字段与存储，无外部组件可直接给。

### 4.3 业务级回滚语义
- 12-factor-agents、LangGraph 均无业务级版本回滚；Temporal 有恢复但无业务回滚（01 取证）；
- **不成熟点**：学业军师的方向 7 已确认"业务回滚须产品层定义"，但**回滚的具体单元、版本语义、错误补偿**未实现细节。

### 4.4 数据本地化 / 单实例
- 学业军师 = 一个实例服务一个学生、本地权威数据、云端仅模型 API（方向 6/8）；
- 12-factor-agents 未覆盖本地权威数据；LangGraph 的 checkpoint 存储需评估是否符合本地优先；
- **不成熟点**：本地数据模型、加密、同步、迁移的具体实现。

### 4.5 确定性强制（不靠 Prompt）
- 学业军师方向 7 硬边界：高影响/权限/证据由确定性代码强制，不靠提示词；
- 12-factor-agents 未讨论；LangGraph 依赖运行图而非确定性策略层；
- **不成熟点**：把"证据字段完整性、状态迁移合法性、不可逆拦截"落到确定性设施的具体规则，未实现。

### 4.6 首版范围与依赖拓扑
- 方向 9 已给三带清单与依赖拓扑（0契约→1地基→2数据认知→3主链→4收口防护），但**具体实现顺序与验收证据**待落。
- 12-factor-agents 的"模块化小概念拼进现有产品"思路与此一致，可参考其"小而聚焦"去拆学业军师部件。

## 6. 学业军师工程开发前置清单（Do / Don't）

> 目标：进入代码工程前定死契约，避免屎山。每项标明当前状态。

### 门禁 1：产品责任门禁（先于任何代码）
- **Do**：锁死最高责任（学业规划）、非责任、外部关系（学生为唯一承接者、取消教师主观反馈）。
- **Don't**：用框架/SDK 反推产品责任；把"能不能做"当"该不该做"。
- 状态：✅ 访谈已确认（方向 1/6/13）。

### 门禁 2：对象与数据契约
- **Do**：定义证据（外部=排名/成绩/试卷/作业等客观实体；内部=行动/检验）、判断、规划、任务、行动、反馈、记忆、资产的字段与边界。
- **Don't**：把对象统称"记忆/用户数据"；外部/内部证据混淆。
- 状态：✅ 边界已确认，字段待成文细化。

### 门禁 3：状态与生命周期契约
- **Do**：定状态（候选/生效/暂停/回退/失效/撤回/删除）与合法迁移；候选与生效分离。
- **Don't**：模型输出直接改状态；状态迁移无校验。
- 状态：✅ 已确认，触发阈值待实现。

### 门禁 4：权限与确定性控制
- **Do**：列出必须由代码强制的项（证据字段、状态迁移、不可逆拦截、Agent 不改规则、自生长不越界）。
- **Don't**：把关键边界交给 Prompt/Agent 自律。
- 状态：✅ 已确认。

### 门禁 5：Agent 责任与编排
- **Do**：为总军师/学科军师/专项/横向域各定唯一主责、输入输出、交接、冲突裁决。
- **Don't**：多 agent 各自为政、无统一规划责任。
- 状态：✅ 结构已确认，编排状态机待实现。

### 门禁 6：证据与审计链
- **Do**：每个判断/规划/行动/修正可回溯到客观证据或内部真实记录；审计字段完整防篡改。
- **Don't**：把模型推断、学生自述冒充客观事实；删除历史不保留回溯。
- 状态：✅ 原则已确认，字段与存储待实现。

### 门禁 7：错误/暂停/重试/幂等/回滚
- **Do**：先定义业务语义（何时暂停、哪些幂等、失败如何处理、回滚单元），再选 Temporal/LangGraph 等机制。
- **Don't**：先堆机制再找语义；副作用不幂等导致重复。
- 状态：✅ 原则已确认，机制选型待验证。

### 门禁 8：评测与验收分层
- **Do**：L1 机制、L2 故障安全、L3 真实使用、L4 教育效果分开；每个关键点标当前层。
- **Don't**：用机制评测冒充教育效果。
- 状态：✅ 已确认。

### 门禁 9：外部组件准入
- **Do**：每能力按 复用/改造/整合/隔离/暂缓/放弃/自建 决定；过 5 类门禁（产品责任/能力适配/运行可靠/安全治理/替换退出）。
- **Don't**：因"能用"就进首版；组件反向定义产品。
- 状态：✅ 已确认。

### 门禁 10：本地/云端/多端边界
- **Do**：本地权威数据、云端模型 API、同步/迁移/私域分发协议。
- **Don't**：本地数据≠本地模型；把云端当第二数据源。
- 状态：✅ 已确认，具体技术待验证。

### 门禁 11：首版范围与依赖拓扑
- **Do**：按方向 9 三带清单 + 依赖拓扑推进（0契约→1地基→2数据认知→3主链→4收口防护）。
- **Don't**：先堆组件再找责任；为了复用而复用。
- 状态：✅ 已确认。

### 门禁 12：工程停止条件
- **Do**：契约不清、状态不清、权限不清、验收不可执行时，**停止代码实现**并回报，不静默补齐。
- **Don't**：为赶进度降低证据门槛、把"确认"当"已实现"。
- 状态：✅ 已确认（方向 0 Q0-2 上报门、Q0-5 重验门）。

## 8. 多份权威指导文件的横向启示

本节补入已取得的一手材料：Anthropic 官方《Building effective agents》（2024-12-19）、OpenAI 官方《A practical guide to building agents》（34 页 PDF，文件未标日期/版本）、LangGraph 官方 Persistence/README/多代理文档，以及 `humanlayer/12-factor-agents` 仓库快照。详细逐源取证见 `调研报告/_tmp_anthropic_openai.md`、`_tmp_langchain.md` 和 `12-factor-agents_仓库调研.md`；临时文件是取证底稿，不替代本报告判断。

### 8.1 共同结论与分工

| 来源 | 它最有价值的部分 | 不能替学业军师解决的部分 |
|---|---|---|
| 12-factor-agents | 状态、恢复、人审门、小而聚焦、面向产品的工程清单与模板 | 多代理责任语义、证据系谱、严格状态机、业务回滚、本地权威数据、确定性保证 |
| Anthropic | 先简单后复杂；区分 workflow 与 agent；routing、parallelization、orchestrator-workers、evaluator-optimizer；工具文档/测试；环境 ground truth；停止条件 | 没有学业证据模型、业务回滚、数据驻留和确定性责任层 |
| OpenAI | single-agent、manager、decentralized 三种编排；分层 guardrails；人工介入类型；eval；隐私/提示词泄漏防护 | 没有足够的状态机、业务回滚、数据本地化和学业领域证据语义 |
| LangGraph | checkpoint 持久化、interrupt 暂停恢复、状态化执行、图式编排、多代理分工的可实现机制 | 框架机制不是产品语义；默认序列化、重执行副作用、业务回滚和教育效果仍需产品层定义 |

**综合判断**：这些文件可以共同支撑“如何把 agent 工程做稳”的方法，但没有任何一份能够直接定义学业军师。应采用“原则借鉴 + 机制复用 + 产品语义自持”的三层关系：原则可吸收，通用机制可验证后复用，学业规划/证据/资产/权限/回滚/效果责任不可外包。

### 8.2 对学业军师的直接修正

1. **先做最简单的可验证闭环，再增加代理数量**。Anthropic 明确建议从简单提示和综合评估开始，仅在简单方案不足时增加多步 agent 系统；这要求学业军师先用一个受控单学科、单任务闭环验证产品责任，而不是先实现总军师、学科军师和大量专项 Agent 的全拓扑。
2. **把“多 Agent”拆成可被验证的编排模式**。学业军师的总军师→学科军师→专项 Agent 不是一句拓扑图，而应先判断每一条调用关系属于 routing、并行、orchestrator-workers，还是明确的顺序 workflow；每种模式分别定义输入、输出、失败、超时、冲突、取消和重试语义。
3. **把工具/Agent 接口当作产品边界**。Anthropic 强调 agent-computer interface 的工具文档与测试；对应到学业军师，每个 Agent/工具必须声明唯一主责、可读证据、可写对象、输出状态、影响范围、权限和失败处理，不能只写 prompt。
4. **把环境事实写入闭环，而不是让模型自证**。Anthropic 要求 agent 在每步从环境取得 ground truth；学业军师应把学生提交的客观材料和产品内真实行动/检验结果作为可核验事实，模型解释只能是判断候选，不能成为事实源。
5. **把停止条件提前设计**。最大迭代次数、预算、超时、证据不足、版本不一致、权限不足、冲突和不可逆风险都应成为确定性停止/降级条件，而不是异常发生后临时加 if。
6. **生产期减少无必要的抽象层**。Anthropic 明确提醒框架适合起步，生产期可以减少抽象层、回到基础组件；学业军师应避免同时叠加多个 Agent 框架、多个状态层和多个记忆系统，先确定单一权威状态源与适配边界。

### 8.3 当前最危险的“屎山入口”

- 先选 Flutter、LangGraph、Temporal 或某个底座，再反推学业对象和状态语义；
- 用“总军师/学科军师/专项 Agent”命名替代真实责任契约；
- 同时维护会话状态、Agent 状态、规划状态、记忆状态和数据库状态，却没有唯一权威源；
- 用 checkpoint/重放机制冒充业务回滚；
- 用 trace、日志或模型自评冒充证据审计和教育效果；
- 把教师反馈或外部协作者当作默认输入，违背方向 13 已确认的现实边界；
- 把“候选生成”“用户看见”“用户点击”“任务完成”“能力形成”混为一个成功状态；
- 先实现全学科、多端、云端售后和自进化，再寻找第一个可复现的核心闭环。

### 8.4 进入代码前的新增硬门禁

在原有 12 项门禁之外，增加以下 6 项，未通过不得进入业务实现：

| 门禁 | 进入代码前必须交付 | 否则的后果 |
|---|---|---|
| 最小闭环门 | 一个单学科/单任务的输入—客观证据—判断候选—规划裁决—任务—行动—检验—回流样例 | 代理拓扑先行，无法证明产品责任 |
| 编排模式门 | 每条 Agent 关系标记为 routing/并行/orchestrator-workers/顺序流程，并有失败语义 | 多 Agent 变成互相调用的黑箱 |
| 单一状态源门 | 对证据、判断、规划、任务、行动、反馈、资产分别规定唯一权威存储和状态所有者 | 状态漂移、重复写入、无法恢复 |
| 副作用门 | 外部调用、写入、提交、通知的操作 ID、幂等键、重试和补偿规则 | 重试造成重复行动或重复入账 |
| 评测门 | L1/L2 测试集、失败注入样例、通过阈值、回归基线和停止条件 | 只能凭演示和主观感觉迭代 |
| 删除/退出门 | 学生数据撤回、删除、导出、停止使用及其下游影响规则 | 删除后仍被检索，形成隐性污染或合规风险 |

### 8.5 推荐的代码前交付顺序

```text
产品责任与范围
  ↓
客观证据/内部证据模型
  ↓
唯一状态源与生命周期
  ↓
权限、确定性拦截、审计字段
  ↓
单学科单任务最小闭环样例
  ↓
L1 机制测试 + L2 故障注入
  ↓
最小 Agent/工作流编排
  ↓
再扩展学科、多代理、终端和售后
```

每一步都必须有“完成定义—验收标准—实际证据—未验证边界”；不满足就停在当前层，不为保持进度而向后堆代码。

## 9. 报告结论与后续

1. 12-factor-agents 可作为产品化工程检查表和初始模板，但只能放在“参考层”，不能作为学业军师架构依据。
2. Anthropic/OpenAI 用于校正复杂度、编排模式、工具接口、人工介入、guardrails 和 eval；LangGraph 用于验证 checkpoint/interrupt 等机制是否适配；这些都不能替代学业军师的证据、状态、权限和业务回滚语义。
3. 学业军师当前最不成熟的不是“缺少某个框架”，而是已确认产品原则尚未被压缩成可执行、可测试、唯一权威的工程契约。
4. 代码工程的第一交付不应是完整产品，而应是可复现的单学科/单任务最小闭环及其 L1/L2 验证包；之后才逐步扩展。

本报告属工程准备参考，不替代 `00/01/02` 作为产品工程方案权威依据。
