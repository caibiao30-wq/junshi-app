# mate 元文档仓库重构研讨报告

> **定位：** 本报告是计划书「任务 2 — 报告一」的交付物，基于 Hermes、OpenClaw、DeepTutor、OpenMAIC 四份独立调查取证报告与当前 `mate/` 与 `STRUCTURE.md` 的实际目录事实，对 `mate/` 三层多编结构做压力测试与重构建议。
>
> **结论先行：** `mate/` 当前作为「唯一产品法源 + 全量元文档 + 顶层战备部署区」的三重定位存在边界过载：一层（十编三层）组织相对清晰，但其与 `docs/` 派生规范、`STRUCTURE.md` 目录真源、`.claude/` 开发侧之间缺少一处「实现责任边界」与「派生闸门」的单一权威登记，且已出现「STRUCTURE 记 5 编 vs 实际三层十编」的可定位漂移。重构方向是：**mate 只承载可追溯到法源的定义、机制与验证陈述；派生文档、工程配置与代码实现边界收口到单一接口矩阵；目录真源与正文编章真源以 mate/README 与 STRUCTURE 的同步改期为权威，不允许两边各自维护一份编目**。

## 3. 压力测试：用四份外部报告反推「最小但完整」的工程元文档闭环

四份报告的共性组件清单（来源结论→推断）：

| 工程环节 | 证据指向 | 代表来源 |
|---|---|---|
| 配置层 | 配置与环境变量分离、schema 版本化、优先级可查 | OpenClaw `.env.example`/schema 版本化；OpenMAIC `feature-flags.ts`+DATABASE_URL 前置 |
| 提示词与人格 | 人格/约束/开发指令分层，prompt 缓存边界受控 | Hermes `SOUL.md`/`AGENTS.md`/`prompt_caching.py` |
| 工具与技能 | 工具注册、权限审批、schema 清洗、技能分层 | Hermes `tools/registry.py`/`approval.py`；DeepTutor `tool_dispatch.py` |
| 记忆与上下文 | 多层记忆、检索、状态持久化、快照 | DeepTutor L1/L2/L3；OpenClaw memory 快照化 |
| 任务编排 | 在线交互/定时/研究批处理分离 | Hermes `cron/`/`batch_runner.py`/`delegate_tool.py` |
| 模型策略 | 运行时选型、回退、成本/并发配额 | OpenClaw runtime selection；OpenMAIC 并发与配额 |
| 数据流 | 会话、排队、租约、心跳 | OpenMAIC session/worker/lease |
| 接口契约 | 外部入口、DSL、前后端边界 | OpenMAIC `@openmaic/dsl`；B1↔B2 HTTP 契约 |
| 安全与隐私 | 权限、路径、schema、数据最小化 | Hermes `path_security.py`；OpenMAIC 隐私诊断 |
| 测试/部署/运维 | 容器、平台配置、qa、遥测、回滚 | OpenClaw `docker-compose.yml`/`fly.toml`；OpenMAIC 回滚 |

**推断：** 一个可持续开发的 Agent 产品，其「最小但完整」的工程闭环，不在仓库某一目录内，而是分散在四个域：产品定义与边界（本体）、运行机制（循环/记忆/工具/编排）、工程实现（接口/数据/部署/运维）、治理与验证（测试/发布/风险）。`mate/` 作为「唯一产品法源」，其职责是把前三者的「定义与机制陈述」固定下来，把「实现细节」交给下游派生。

## 4. 对 mate 三层多编结构的查缺补漏

以十编三层为基准，对照四份报告逐项压测（事实缺口用「□」标出）：

- **T3 学业规划与教育闭环**：职责清晰，但「循环/状态机」类机制（如义务环九步）缺少对应「调度与生命周期」的单一登记入口，可能与 T6 状态、T4 能力编排职责交叠。**建议：** 明确「运行循环」主责在一编，其余编只引用不复制（对齐 Hermes 将在线/定时/批处理分离的做法）。
- **T4 Agent 核、判断与能力编排**：与 T9 工程架构的「能力编排/工作流」存在边界模糊。**建议：** 定义 T4=运行机制层的行为编排，T9=治理闸门层的实现承载，两者以接口矩阵登记。
- **T5 证据、资产与可靠性**：覆盖证据驱动，但与「工具/技能」「记忆」的边界在十编中无独立「工具设计」编，工具与技能职责落在何处需显式指定（四份报告均把 tools/skills 列为独立能力）。
- **T6 状态、记忆与上下文运行**：与 T5 资产存在天然交叠；多层记忆（事件/认知/方法）的检索与快照机制建议参照 DeepTutor L1/L2/L3 与 OpenClaw 快照化在正文明确。
- **T7 角色、权限与安全边界**：覆盖安全，建议补「数据最小化/隐私诊断」面（Hermes path_security、OpenMAIC 隐私诊断）。
- **T9 工程架构、数据与智能底座**：为十编中承接「实现边界」的入口，但当前正文多为定义陈述；**关键缺口**：缺一处把「派生文档、代码、部署」指向的唯一权威登记（OpenMAIC 的 feature-flag 前置与 OpenClaw 的 schema 版本化提示：配置与能力开关应有版本与状态登记）。
- **T10 验证、发布与工程运营治理**：覆盖验证/发布/回滚；**缺口**：测试方案、部署方案、运维方案是否落正文、还是仅留「派生闸门」指针，当前边界需显式写清。

**共性缺口归纳（候选建议）：** 十编对「工具设计」「模型策略」「数据流与接口约定」「测试方案」「部署方案」「运维方案」多数只以「派生闸门」指向，未在正文固定「本编是否承载、还是仅登记指针」——这会导致后续工程文档找不到唯一上游。应在 00 接口矩阵中为这些工程环节逐一登记「上游编 + 派生闸门 + 状态」。

## 5. mate 应保存什么、不应保存什么

**应保存（定义/机制/验证陈述）：**
- 产品本体、价值与最高边界（T1）、服务对象与范围（T2）；
- 学业闭环、Agent 运行循环、判断与能力编排（T3/T4）；
- 证据、状态、记忆、上下文、权限、交互等运行机制（T5–T8）；
- 工程架构、数据与智能底座的定义与派生闸门（T9）；
- 验证、发布与运营治理门槛（T10）；
- 术语、待确认、预留、变更历史、断言来源等登记（附录）。

**不应放入 mate（候选建议）：**
- **具体字段、Schema、Prompt、代码、测试与部署配置**（`mate/README.md` 已明确排除）——应入 `docs/` 派生规范或代码库；
- **外部研究材料的全文**——只保留结论与来源指针，材料本身归档别处；
- **候选/预留/目录占位**——不得从目录存在推断为已实现或已决策；
- **过程草稿与一次性工作记录**——入 `draft/` 或工作日志，不进法源。

## 7. 与 STRUCTURE.md、docs/、.claude/ 的边界与同步机制

- **mate(法源) vs STRUCTURE(目录真源)：** mate 定义「是什么/做什么」，STRUCTURE 定义「目录怎么摆」。两者不得各自维护一份编目——应以 mate/README 的三层十编为「编目真源」，STRUCTURE 只登记目录路径并回链，不再重复编目清单（现状 v2.4 重复了「5编」描述，是漂移根因）。
- **mate vs docs(派生规范)：** docs 记录「由元文档派生的正式执行性规范」，须记录上游元文档版本、继承决策编号、状态与验证方式；mate 不复制 docs 正文，docs 不得反向决定产品本体（沿用现有效力顺序与「未 locked 不作唯一验收依据」）。
- **mate vs .claude(开发侧)：** .claude 只服务开发共创，禁止存放产品 Prompt/技能正文；产品技能/hooks/workflows/subagents 仅位于 `runtime/engine/`。四份报告的工具/技能/编排面应在 runtime 落地，mate 只登记其「责任与闸门」。
- **同步机制（候选）：** 引入「派生前核对」：任何从 mate 派生 docs/工程文档前，先查 00 的登记表，确认上游编与闸门；任何 mate 编目改期，同步改 STRUCTURE 与附录E，形成可追溯链（对齐迭代更新原则）。
