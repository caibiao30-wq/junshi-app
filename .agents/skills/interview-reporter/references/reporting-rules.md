# 记录到报告的正式化规则

本规则服务 `interview-workflow` Phase 4。报告的任务是让读者更容易阅读和回溯记录，不是替记录做摘要、决策或补证据。

长论证的推理方法依据（前提/条件/反例/证据等级/修正链/未决项的界定、灵活形式选择、证据与现实边界）引用主技能 `interview-workflow/references/reasoning-methodology.md` 的「报告」相关小节；本文件只落实为记录→报告的正式化细则，不复制其正文，也不在产物中显性挂名。

## 1. 输入、证据和停机

- 唯一内容证据是同一访谈目录下的 `02_访谈记录.md`；报告必须在文件头明确写出该路径或文件名。
- `00_访谈约定.md`、`01_调查取证.md`、原始底稿和其他材料可帮助理解目录或定位，但不能作为报告新增内容的证据。
- `02_访谈记录.md` 缺失、问题回应缺失、原始定位为空、或同一问题的状态发生无法解释的冲突时，停止写报告并回报主技能，列出缺失或冲突位置。
- 记录信息不足以支撑正式表述时，不猜测；保留原有措辞，并标为 `[待确认]` 或 `[待验证]`，同时进入对应清单。

## 2. 什么可以改

可以做最小的编辑，使记录可独立阅读：

- 整理总目录、章/节导航和标题层级；
- 把问题标题改成简洁、专业的标准化问题，但不得改变问题范围；
- 修正明显错别字、标点、断句和 Markdown 格式；
- 统一同一概念的术语，但保留记录中的限定词；
- 为段落补最小的连接语、来源标签和上下文提示；
- 合并完全相同、无新信息、且不改变观点顺序和状态的机械重复。

任何改写都应能回到记录中的对应段落，不要用“更专业”作为新增判断的理由。

## 3. 什么不能改

以下内容构成保真边界：

- 不把长篇论述改写成一句结论、摘要或要点清单；
- 不删除理由、事实、例证、限定、反例、失败路径、犹豫和自我修正；
- 不改变观点出现顺序、因果关系、条件范围或确认状态；
- 不把采访者代拟变成用户原话，也不把采访者的连接语伪装成用户判断；
- 不把“可能”“我认为”“暂待验证”“尚存争议”等表达改成确定语气；
- 不静默删除已被后续内容修正的早期表述，早期内容保留并标 `[已被修正]`；
- 不生成记录中没有的产品能力、用户事实、工程实现或因果解释；
- 不用报告的摘要、结论或其他报告段落互相证明。

## 4. 长答案的处理

对每条长篇回应，先按原记录顺序保留完整论述，再做格式整理。可以拆成多个段落、加小标题或加来源标签，但拆分后仍要看见事实或判断、理由和推理过程、例证与限定、反例与失败路径、犹豫与自我修正。

用长论证的六类零件清单比对每条长回应，缺一即不完整：

- **前提**：这段论证依赖的假定与条件；
- **条件与限定**：在什么范围/情景下成立、不成立的边界；
- **反例与例外**：什么情况会推翻或削弱它；
- **证据等级**：事实 / 来源判断 / 推断 / 待验证 各归各位，不混写；产品机制、推理推断不能自证；
- **修正链**：早期表述如何被后续内容修正，演进轨迹可见；
- **未决项**：尚未想透或须验证的部分，单列保留。

零件可用小标题、段落或列表呈现，但**不能用摘要、结论总览或表格替代长论述本身**；记录对该项未提供信息时写明「记录未提供」，不补造。

报告的“阶段结论”只能作为导航，不能替代问题单元中的完整回应。无法确认是否可删时，保留原文信息，不做压缩。**摘要不是长论证**：不得把一段长论证压成一句话结论或要点清单后当作完整回应。

## 5. 状态与代拟表达

使用共享状态判据，状态贴在具体问题、回应或判断上：

- `[用户明确判断]`：用户自主表达的事实、观点或决定；仍保留原有限定词。
- `[确认采纳]`：归纳或代拟后，用户明确确认或明确沿用；应说明确认依据。
- `[专业建议·代拟]`：采访者代拟的专业回答、候选或暂定方案；不是用户观点。
- `[已被修正]`：后续内容替代了早期表述；早期内容保留，后续状态另列。
- `[待确认]`：用户尚未拍板，或确认指向不清。
- `[待验证]`：需要运行、真实样本、反馈或长期实践验证。

“请为我作答”只授权代拟，不等于确认。用户沉默不等于确认。确认只覆盖用户明确指向的内容，不自动覆盖同段扩展。

`[确认采纳]` 才可进入报告主体的用户结论；`[专业建议·代拟]`、`[待确认]`、`[待验证]` 必须在边界和清单中显式保留。状态证据不足时取更保守状态。

## 6. 章、节、目录和导航

报告采用正式章/节结构，以保持与访谈记录的顺序完全对应、可回溯：

- **章 = 阶段**，固定映射：第一章=阶段 0，第二章=阶段 1，第三章=阶段 2，第四章=阶段 3，第五章=阶段 4，第六章=阶段 5。
- **节 = 问题**，节号用 `1.1`、`3.2` 等（章号.问题序），标题保留原始问题编号，例如 `3.1 问题 2-1：<主题>`。
- 正文前必须给**总目录**，列全部章、节和文末区块；正文按章→节展开。
- 每个节按以下顺序组织：

```markdown
## 3.1　问题 2-1：<主题>

**标准化问题**：<在不扩大范围下整理后的问题>

**回应与论证**：
<完整保留记录回应，只做正式表达和结构整理>

**确认状态**：[状态]

**记录定位**：`02_访谈记录.md#问题-2-1`
```

保持记录中的访谈阶段和问题推进顺序。总目录可列出完整六章骨架，但正文只写有真实记录内容的章/节；没有记录内容的章不要编造回应。阶段/章导航可用锚点链接，但链接文字和标题必须一致。

## 7. 结论总览、结论边界与清单

**结论总览**位于正文前，用于让读者先看到全报告四类状态的概览；它只能导航，不得替代正文节内的长篇回应、论证或限定。

**结论边界**位于正文之后，用于进一步说明报告能证明什么、不能证明什么，并与文末待确认/待验证清单形成完整汇总：

- 已确认：只列 `[用户明确判断]` 或 `[确认采纳]` 的内容，保留限定词；
- 专业暂定：列 `[专业建议·代拟]`，不可写成用户决定；
- 待确认：列 `[待确认]`，并写清需要谁确认什么；
- 待验证：列 `[待验证]`，并写清需要什么运行、样本或现实反馈。

待确认/待验证清单必须能回到具体问题单元和记录定位；不要只写泛化风险。清单项目不应被阶段摘要遮蔽。

## 8. 回溯索引

每个报告问题单元至少有一条回溯索引，形成：

```text
报告位置 → 02_访谈记录.md 中的问题/段落 → 原始底稿中的消息、路径或锚点
```

记录没有原始底稿定位时，不补造定位；明确写“记录未提供原始底稿定位”，并回报主技能。索引中的“报告位置”应能让读者实际找到报告章节，不使用空值、`待补` 或笼统的“全文”。

## 9. 完成前的停机与交接

写作完成后先运行 `scripts/report_gate.py <03报告.md> <02记录.md>`。脚本通过只表示结构门槛通过，不表示语义保真已自动证明。再将以下事项交给主技能或 `interview-qc`：长答案逐段比对、状态升级检查、重复与术语统一、最终定稿状态。
