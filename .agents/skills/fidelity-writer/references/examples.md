## 示例一：完整保留方案论证

### 用户任务

> 把这段方案讨论整理成正式文档。要求：保留完整的论证过程和每个理由，不要压缩成结论，被否掉的观点也要保留它为何被否的依据。

### 输入材料

> # 关于是否引入缓存层的方案讨论（原始记录）
>
> 我们几个讨论了很久到底要不要在查询服务前面加一层缓存。一开始大家倾向加，因为线上查询延迟平均 200ms，有些用户已经在抱怨。A 说加一个 Redis，命中率大概能到 80%，延迟能压到 20ms 以内，收益很明显。
>
> 但 B 反对。B 的理由是：缓存引入了数据一致性成本。我们的业务里有相当一部分查询是强一致的——比如账户余额、库存扣减，这些一旦读到脏数据会出事故。B 说如果只给弱一致查询加缓存，那又要维护一套“哪些查询可以缓存”的白名单，这个维护成本长期看可能比省下来的延迟还高。B 的结论是：与其加缓存，不如先把查询本身优化——目前有几个查询是典型的 N+1 问题，索引也没建全。
>
> C 后来补充了一个折中：先只对“读多写少、且允许弱一致”的报表类查询加缓存，其余不动。C 认为这样能把风险圈住，收益也能先拿到一部分。C 也说这个方案仍然没有解决白名单维护的问题，只是把范围缩小了。
>
> 最后我们没有当场定论。A 承认强一致那块确实不该碰，B 也承认报表类查询加缓存是低风险的，C 的白名单维护成本观点大家也认可。但目前一致的意见是：把“是否加缓存”和“先做查询优化”绑定成一个决策来做，不单独上缓存。N+1 问题和索引问题要不要立刻排期，还没确认。

### 合格输出

```markdown
# 关于是否引入缓存层的方案讨论

## 一、讨论背景

我们围绕是否要在查询服务前面增加一层缓存，进行了较长时间的讨论。

讨论开始时，大家倾向于引入缓存，原因是线上查询延迟平均为 200ms，已经有一些用户对此表示抱怨。A 提议增加 Redis，并判断缓存命中率大概能够达到 80%，查询延迟能够压缩到 20ms 以内，因此认为收益比较明显。

## 二、关于引入缓存的反对意见

B 对引入缓存表示反对。B 的理由是，缓存会引入数据一致性成本。

我们的业务中有相当一部分查询要求强一致，例如账户余额、库存扣减等场景。这些数据一旦读到脏数据，就可能造成事故。

B 进一步指出，如果只为弱一致查询增加缓存，就需要维护一套“哪些查询可以缓存”的白名单。从长期来看，这套白名单的维护成本可能高于缓存所节省的延迟成本。

基于上述理由，B 的结论是：与其增加缓存，不如先优化查询本身。目前有几个查询存在典型的 N+1 问题，索引也没有建立完整。先处理这些查询层面的问题，可能是更合适的方向。

## 三、折中方案

C 后来补充了一个折中方案：先只针对“读多写少、且允许弱一致”的报表类查询增加缓存，其他查询暂时不做改动。

C 认为，这样可以把风险控制在较小范围内，同时先获得一部分收益。

C 也指出，这个方案仍然没有解决白名单维护问题，只是把需要维护的范围缩小了。

## 四、讨论后的共识与未决事项

最后，讨论没有当场形成最终定论。

A 承认，强一致场景确实不应该接入缓存。B 也承认，对报表类查询增加缓存属于低风险方案。对于 C 提出的白名单维护成本问题，大家也表示认可。

目前形成的一致意见是：将“是否增加缓存”和“是否先进行查询优化”绑定为一个决策来处理，而不是单独上线缓存。

至于 N+1 问题和索引问题是否要立即排期，目前还没有确认。
```

### 核验重点

- 没有删除 A、B、C 的理由、取舍或方案局限。
- “大概”“可能”“没有确认”等状态没有被改成确定结论。
- 新增标题只用于定位，不改变原来的论证顺序。
- “讨论没有当场形成最终定论”与后面的阶段性共识同时保留，未强行消除表面张力。

## 示例二：保留不确定性与限定词

### 用户任务

> 润色下面这段论述，尽量少改，保留原文所有的限定词、不肯定语气和“暂待验证”这类状态标记。

### 输入材料

> # 关于“组织是否适应 AI 协作”的一点思考（草稿）
>
> 我认为，组织对 AI 协作的适应速度，可能比多数人预想的要慢，但也可能比预想快——这两个方向目前都缺乏足够证据，暂待验证。有几个观察点能说明一些趋势：一是，新工具在落地时普遍会遇到“已有的流程已经跑顺了，凭什么改”的惯性；二是，越是信息密集型的工作，越可能先被 AI 渗透，但这只是我的初步印象，尚存争议；三是，领导者对 AI 的态度分化很明显，有的视为降本手段，有的视为重新定义组织结构的契机，哪种倾向最终占上风，现在还说不准。
>
> 需要特别说明的是，上述观点大多建立在少数企业的访谈和公开报道上，样本有限，不能据此推广。如果后续有更大样本的实证，很可能会修正其中若干判断。

### 合格输出

```markdown
# 关于“组织是否适应 AI 协作”的一点思考（草稿）

我认为，组织对 AI 协作的适应速度，可能比多数人预想的要慢，但也可能比预想得要快——这两个方向目前都缺乏足够证据，暂待验证。有几个观察点能说明一些趋势：一是，新工具在落地时普遍会遇到“已有的流程已经跑顺了，凭什么改”的惯性；二是，越是信息密集型的工作，越可能先被 AI 渗透，但这只是我的初步印象，尚存争议；三是，领导者对 AI 的态度分化很明显，有的视为降本手段，有的视为重新定义组织结构的契机，哪种倾向最终占上风，现在还说不准。

需要特别说明的是，上述观点大多建立在少数企业的访谈和公开报道上，样本有限，不能据此推广。如果后续有更大样本的实证，很可能会修正其中若干判断。
```

### 核验重点

- “我认为”“可能”“初步印象”“尚存争议”“暂待验证”“现在还说不准”“很可能”等标记全部保留。
- “样本有限，不能据此推广”没有被删掉或改成更强的结论。
- 唯一改动是把“也可能比预想快”顺成“也可能比预想得要快”，属于不改变语义的通顺修补。

## 示例三：演进型材料的取舍边界

### 用户任务

> 把上面这场命名讨论整理成正式文档。要求：只保留最终被确认有效的方案和理由，被否定/被替代的轮次只做极简衔接标注，但不要把它总结成几句要点——被保留的部分仍是完整的。

### 输入材料

> # 命名方案的讨论记录（原始）
>
> 第 1 轮：A 提议叫“军师”。理由是贴合“指导用户做决策”的定位。B 说太泛，听起来像所有决策都管，其实我们只做学业相关的。这轮没通过。
>
> 第 2 轮：B 提议叫“学业参谋”。A 觉得“参谋”有点军事味，和学业语境不太搭。又被否。
>
> 第 3 轮：C 提议叫“学业军师”。A、B 都觉得这个既点明了学业范围，又保留了“军师”那种贴身出主意的感觉，通过。
>
> 最后：C 补充了一个规则，说正式场合首用要加一句定义，避免和游戏“军师”混。A、B 认可。

### 合格输出

```markdown
# 命名方案（定稿）

## 最终确认的方案：学业军师

第 3 轮通过。C 提议叫“学业军师”。A、B 都觉得这个既点明了学业范围，又保留了“军师”那种贴身出主意的感觉。

C 又补充了一个规则，正式场合首用要加一句定义，避免和游戏“军师”混。A、B 认可。

---

## 讨论中未采用的轮次（仅作衔接标注）

- 第 1 轮提议“军师”，理由是贴合“指导用户做决策”的定位。此意见在讨论后被否定。
- 第 2 轮提议“学业参谋”。此意见在讨论后被否定。
```

### 边界说明

该次试跑中，第 1 轮衔接标注仍带有原始理由；如果用户明确要求“只做极简衔接标注”，更严格的合格写法应改为：

```markdown
- 第 1 轮意见未被采用。
- 第 2 轮意见未被采用。
```

这条边界很重要：当用户授权删除淘汰轮次正文时，不应把淘汰理由重新压缩成新的小结；当用户要求保留淘汰理由时，才保留它们。不要自行决定两种取舍中的一种。

## 使用边界

1. **保真不是扩写。** 原文没有写出的理由、背景或结论不能补入。
2. **保真不是逐字拒绝任何修改。** 错别字、明显语病、断裂排版和必要的衔接可以修，但要能说明它不改变语义。
3. **保真不是把不确定内容变成事实。** 语气、限定词、争议和待核验状态属于原文信息，必须保留。
4. **结构服务于定位，不服务于压缩。** 可以增加必要标题和分段，但不要为了“更好扫描”而新增摘要、结论先行、要点清单或执行表。
5. **用户明确的取舍优先。** “近乎全量保留”与“只保留最终确认内容”会产生不同结果；先识别用户授权的取舍范围，再在范围内尽量保全。
