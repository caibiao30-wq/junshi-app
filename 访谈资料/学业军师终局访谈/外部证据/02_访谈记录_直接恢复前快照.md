### 问题 0-2：元文件与专业领域文件之间的派生、继承、覆盖、冲突、回溯、版本关系如何定义

**问题**：

**回应**：

*受访者确认后的最终判断（[确认采纳]）*：
采纳"元文件为主导 + 冲突可上报 + 由受访者裁决 + 仅受访者可改元文件"的框架，并采纳"上报须有实质证据且给出不改的后果"的门槛。受访者明确表示：不是元文件主导一切，而是元文件是当前最高权威，但保留受控反馈通道。

*最终判断内容*：
1. 元文件是当前最高权威，专业领域文件受它约束、不得越权修改它。
2. 当派生文件发现元文件某条根级决策与现实（工程/学生/学校）冲突时，它有权停止并上报，附理由与证据。
3. 冲突裁决权始终在受访者（人）手里：由受访者决定修改元文件、驳回上报，或把问题留在派生层处理。
4. Agent/派生文件只有上报权，没有改元文件的权力；修改元文件根级决策是人的专属权力。
5. 上报门槛：必须提供实质证据（工程失败、学生伤害、明确无法满足的验收），并给出"若不修改的后果"；不得以"我觉得这样更好"为由随意上报，以防稀释元文件权威。
6. 派生关系五规则：派生→受约束→冲突上报→回溯核验→版本衔接。专业领域文件从元文件继承根级责任、角色责任、统一状态/接口/权限/验收原则、完成定义与回溯链；只能缩小或细化根级边界，不能扩大、回避或改写根级责任；元文件根级变更须版本化、可追溯、可回退，并触发下游重新核验与验收；专业领域文件可替换/弃用/迭代但不能脱离元文件版本约束，须标注所依据的元文件版本。

### 问题 0-5：元文件变更后的影响传播与重新核验

**问题**：
元文件发生根级变更后，如何识别受影响的专业领域文件、触发重新核验、处理新旧版本与暂停工程实现？（主持人代拟，受访者确认采纳，并新增阶段写入要求。）

**回应**：

*主持人代拟稿（[专业建议·代拟]，供受访者确认）*：

（一）会触发重新核验的变更：产品本体/核心责任/非责任变更；判断引擎专项范围、判断原则或证据要求变更；自生长/自进化允许范围、停止条件或控制边界变更；角色责任或权限变更；证据/状态/接口/权限/审计/验收原则变更；首版边界、专业领域派生规则或技术自持边界变更；任何可能影响多个专业领域文件的根级事实、约束或完成定义变更。仅错别字、排版或不改变语义的格式修改可不触发语义重验，但仍须记录。

（二）只重验受影响文件，但不得漏掉间接依赖：直接引用被修改决策/接口/状态/权限/验收标准的文件必须重验；依赖直接受影响文件输出的下游文件也必须检查间接影响；无法判断是否受影响时按受影响处理；重大根级变更可由受访者决定扩大为全量重验；影响范围必须形成清单，不能只凭 Agent 主观判断。

（三）识别受影响文件的依据：元文件锚点头中的根级责任引用；决策 ID、问题节点 ID 和版本引用；责任对象登记表；输入/输出接口引用；状态、权限和验收标准引用；文件间横向依赖；共享领域对象与共同数据模型；代码、测试或配置的反向引用。每个派生文件必须能回答：依赖哪个元文件版本、引用了哪些决策/责任/接口/状态/权限/验收、这些引用中哪些变化、变化是否影响本文件或其下游。

（四）重验期间新旧版本共存：旧版本保留不覆盖不删除；新版本作为待核验版本建立；新旧版本必须标明版本号、变更原因、生效状态和影响范围；受影响文件完成重验并获得放行前，旧版本可作为当前有效依据继续维持，但不得把新版本内容提前混入实现；新版本未放行前不得宣称其已生效；新版本放行后旧版本转历史版本但仍保留回溯与回退能力。

（五）未完成重验时的工程限制：不受影响的工作可继续；受影响文件及其下游依赖不得继续新增实现；涉及共享接口/状态/权限/判断引擎/自生长/根级责任的工作按受影响处理；影响范围无法判定时相关工作暂停，不得以"应该没影响"放行；已完成但依赖旧版本的实现须标记为待复核，不能直接视为符合新版本。

（六）执行分工：受访者决定元文件是否变更、确认变更理由、裁决冲突、批准新版本生效；Claude Code 主要执行影响分析、派生文件核验、代码与测试影响分析；pi、Codex 可按任务分工执行独立复核、局部比对或测试核验；coding agent 可提出影响范围和重验建议，但不得自行批准元文件或宣布根级变更生效；记录校验 fork 只读检查记录完整性、结构、状态、授权、定位和门禁结果，不修改访谈记录。

（七）每个阶段的记录写入与校验要求（受访者明确要求）：每个访谈阶段完成后，主会话必须把该阶段完整访谈内容一次性写入 `02_访谈记录.md`；不得只写摘要、零散片段或由支线代理自行补写。写入完成后交由 fork 代理统一全量只读校验。阶段写入流程：主会话主持该阶段全部问题并保留完整原答/代拟/复述/修正/确认状态/定位 → 阶段结束时主会话一次性完整写入 → fork 读取整份记录 → fork 核对结构/保真/状态/授权/定位/重复/冲突 → fork 运行 record_gate.py --full → fork 回报通过项、人工复核项和阻塞项 → 存在阻塞时主会话只修正明确问题不改变已确认含义 → fork 再次校验通过后该阶段记录才算固化完成 → 阶段记录未通过校验不放行下一阶段。这里"完整写入"是按阶段完整写入，不是等整场访谈结束才写，也不是每答一个问题就让支线代理写入，以保证主会话掌握完整上下文避免记录被阉割、阶段结束即形成可恢复节点、fork 独立结构核对不干扰主线、记录门控仍然有效。

**问题**：学业军师到底是什么；它是工具、系统还是陪伴者；学生视角与产品开发者视角分别如何理解；什么使它区别于普通 AI 辅导工具？

**回应**：

*主持人代拟稿（[专业建议·代拟]，供受访者确认）*：学业军师不是只回答问题、生成资料或陪学生聊天的 AI 工具，而是以学业规划为最高产品责任、以判断引擎和术业有专攻 Agent 体系为规划认知结构、以证据为事实基础、以学业资产为长期沉淀、以受控自生长/自进化为长期演进机制，并由教与授、任务、反馈和底层确定性设施共同承接的长期学业规划系统。

学业规划是产品最高责任；规划不是一张计划表，而是基于学生真实位置、阶段目标、约束和可核验证据，持续形成、执行、检验和修正可理解、可行动、可调整的路径。规划承担位置判断、目标确定、差距分析、路径设计、任务部署、资源安排、执行监测、结果检验、动态修正和阶段衔接。教与授是服务规划、使规划得以执行和检验的手段。

分层关系：

```text
                    学业规划
          （产品最高责任 / 上层建筑）
                         │
       ┌─────────────────┼─────────────────┐
       │                 │                 │
    路径任务          教与授执行        反馈修正
                         │
          判断引擎 + 术业有专攻 Agent
                  （规划认知结构）
                         │
       证据 ── 学业资产 ── 自生长/自进化
             （事实基础与长期演进）
                         │
    状态 / 权限 / 会话 / 记忆 / 审计 / 回滚
       技术栈 / 运行 / 监管 / 外部反馈
                  （经济基础）
```

判断引擎将通用 LLM 限定为学业规划专项能力；专项 Agent 服从统一规划；证据支撑事实，学业资产沉淀可复用认识，自生长/自进化支撑长期适配；底层设施保障可靠运行。学生端必须简单直白，内部复杂性由产品吸收。

*受访者修正与确认（[用户明确判断]）*：学业规划是一切执行的上层建筑；教与授是服务规划的手段；学业军师最突出的部分包括证据、自生长/自进化、术业有专攻的 Agent 体系、判断引擎、学业资产。此前把这些能力平面并列为“必要组合”的表述被修正为上层建筑、规划执行、规划认知结构、事实基础/长期演进和经济基础的分层。

### 问题 1-11：学业军师成立与不成立的最终边界

**问题**：何时学业军师成立，何时即使有许多功能仍不是学业军师。

**回应**：

*主持人代拟稿（[专业建议·代拟]）*：成立需同时具备：规划最高责任；判断引擎专项化；专项 Agent 服从统一规划；规划基于可追溯证据；规划进入任务/教与授、行动、检验；结果反馈修正规划；学业资产受控沉淀；长期自生长/自进化受控；学生低负担；确定性设施保护权限/状态/证据/资产；能处理失败、冲突、拒绝、沉默和超范围。能聊天无规划、能生成计划无行动修正、Agent 各自为政、有记忆无证据和资产边界、自生长自动积累错误、判断不能服务规划、题库讲解无统一责任、材料无法区分来源、界面虽简单但不可追溯、依赖底座不可替换、模块存在但无贯通闭环，均不成立。
