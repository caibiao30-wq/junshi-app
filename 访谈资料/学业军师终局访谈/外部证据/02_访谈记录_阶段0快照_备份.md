### 问题 0-2：元文件与专业领域文件之间的派生、继承、覆盖、冲突、回溯、版本关系如何定义

**问题**：
元文件与专业领域文件之间的派生、继承、覆盖、冲突、回溯、版本关系如何定义？（主持人先代拟，受访者澄清后确认。）

**回应**：

*主持人代拟初稿（[专业建议·代拟]，初稿曾把"元文件主导一切"与"带受控反馈通道的权威"两种框架混写，后经澄清修正）*：
初稿含 A/B 两种表述混写：A 为元文件主导一切；B 为元文件是当前最高权威但保留受控反馈通道。

*受访者追问（原话，关键）*：
"你的意思是……还是说元文件主导一切？"

*主持人澄清（[已被修正]）*：
主持人确认"不是我表述失误"，初稿将 A 与 B 混写是表述不清，予以修正；明确不是元文件主导一切，而是元文件是当前最高权威、但保留受控反馈通道。

*受访者确认后的最终判断（[确认采纳]）*：
采纳"元文件为主导 + 冲突可上报 + 由受访者裁决 + 仅受访者可改元文件"的框架，并采纳"上报须有实质证据且给出不改的后果"的门槛。受访者明确表示：不是元文件主导一切，而是元文件是当前最高权威，但保留受控反馈通道。

*最终判断内容*：
1. 元文件是当前最高权威，专业领域文件受它约束、不得越权修改它。
2. 当派生文件发现元文件某条根级决策与现实（工程/学生/学校）冲突时，它有权停止并上报，附理由与证据。
3. 冲突裁决权始终在受访者（人）手里：由受访者决定修改元文件、驳回上报，或把问题留在派生层处理。
4. Agent/派生文件只有上报权，没有改元文件的权力；修改元文件根级决策是人的专属权力。
5. 上报门槛：必须提供实质证据（工程失败、学生伤害、明确无法满足的验收），并给出"若不修改的后果"；不得以"我觉得这样更好"为由随意上报，以防稀释元文件权威。
6. 派生关系五规则：派生→受约束→冲突上报→回溯核验→版本衔接。专业领域文件从元文件继承根级责任、角色责任、统一状态/接口/权限/验收原则、完成定义与回溯链；只能缩小或细化根级边界，不能扩大、回避或改写根级责任；元文件根级变更须版本化、可追溯、可回退，并触发下游重新核验与验收；专业领域文件可替换/弃用/迭代但不能脱离元文件版本约束，须标注所依据的元文件版本。

### 问题 0-3：一个专业领域文件从元文件派生时，最低必须继承哪些内容

**问题**：
一个专业领域文件从元文件派生时，最低必须继承哪些内容？（主持人代拟，受访者确认采纳。）

**回应**：

*主持人代拟稿（[专业建议·代拟]，供受访者确认）*：
每个派生文件必须携带"元文件锚点头"，含以下字段：
1. 根级责任锚：对应哪项根级/产品责任、主责任；
2. 适用范围：产品、学段/学科、角色；
3. 排除范围；
4. 继承的根级边界：证据纪律、学生控制、权限、判断引擎原则、自生长边界、不可逆操作、审计可追溯；
5. 统一规则：状态、接口、权限、验收，不另造平行体系；
6. 完成定义与验收判据；
7. 上游引用：元文件版本、决策节点、证据与访谈定位；
8. 新增内容清单；
9. 未定项；
10. 派生执行者：coding agent（Claude Code 主 / pi / Codex 辅）；
11. 回溯与控制：元文件变更触发重新核验；
12. 版本状态：自身版本、依赖的元文件版本、替换/弃用/演进。

锚点头缺任一字段即未完成派生；派生文件只能缩小或细化根级边界，不能扩大、回避或改写根级责任。

*受访者确认*：回复"确认采纳"，确认上述字段与规则。

### 问题 0-4：多个专业领域文件重叠、边界、责任归属与协调

**问题**：
多个专业领域文件发生重叠时，边界、责任归属与协调关系如何定义？（主持人代拟，受访者确认采纳。）

**回应**：

*主持人代拟稿（[专业建议·代拟]，供受访者确认）*：
1. 专业领域文件不形成平行权威。
2. 每个可验收对象只有一个唯一主责文件，可有协作文件。
3. 共同依赖的根级内容归元文件。
4. 跨域内容指定主责，并以稳定接口/版本引用，避免重复定义。
5. 允许横向引用，但不得绕过或改写元文件/主责；循环依赖必须上报。
6. 冲突对象处理：先冻结，核对锚点与主责；越界则撤回/改写；接口不清则修订接口；触及根级则按 Q0-2 上报由受访者裁决；之后更新并触发受影响文件重新验证。
7. 责任登记表为强制检查项，包含：责任对象、唯一主责、协作、输入输出、根级来源、冲突状态、验收责任、受影响文件。

*受访者确认*：回复"确认采纳"。
