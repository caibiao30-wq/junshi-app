## 3.1　问题 3-1：底层设施与 Agent 的正式接口契约

**标准化问题**：在底层负责确定性硬约束、Agent 负责受控范围内的管理与协调、Agent 输出默认是候选这一前提下，底层设施与 Agent 之间应当定义怎样的正式接口契约，使产品责任可落地、Agent 无法绕过底层约束、状态/证据/权限/追溯可解释，并支撑一个可独立运行与验证的学业支持闭环？

### 一、为什么要定义接口契约

前两阶段已经确认：

- 底层负责确定性硬约束；
- Agent 负责受控范围内的管理、分析和协调；
- Agent 输出默认是候选，需经底层校验、确认和状态迁移才成为正式状态。

但如果这个边界没有可执行的接口，就仍然只是概念。因此需要定义：

> **Agent 何时、以什么输入、生成什么输出、在什么权限和状态下运行、如何被校验、如何确认、如何审计、如何回滚。**

接口契约不是为了技术化而技术化，而是为了确保：

- 产品责任可落地；
- Agent 无法绕过底层约束；
- 状态、证据、权限和追溯可解释；
- 一个完整的学业支持闭环可以独立运行并被验证。

### 二、接口契约的总体原则

> **Agent 的所有读写都必须经过底层设施定义的接口；接口强制校验对象、来源、权限、状态、证据、影响和审计。Agent 不能通过非结构化文本或自行访问绕过接口。**

一套可运行的接口契约至少应满足：

1. 输入最小必要；
2. 输出结构化、可校验；
3. 对象和状态明确；
4. 权限显式授予；
5. 证据和来源可追溯；
6. 高影响操作需确认；
7. 调用和结果被审计；
8. 失败可降级、重试或回滚。

### 三、Agent 的输入契约

#### 1. 输入组成

Agent 一次受控调用应获得：

- **调用目标**：本次要完成什么责任（诊断、任务生成、反馈分析、资产提炼、监察等）；
- **责任域与会话标识**：在哪个会话、哪个责任域内运行；
- **授权读取范围**：明确允许读取哪些对象、证据和来源；
- **当前任务/状态上下文**：与该调用相关的任务、规划、学科状态；
- **可用的证据及来源**：证据 ID、类型、来源、支持范围、确定性；
- **允许的输出类型**：本次调用可以输出什么（候选判断、任务候选、风险提示等）；
- **状态字段要求**：输出的确定性、适用范围、影响范围等字段；
- **禁止访问内容**：明确不得读取的私人信息、未授权范围、其他学生/机构数据；
- **版本信息**：本次运行使用的模型、内容包、规则版本；
- **调用者与目标**：谁在调用，为什么调用；
- **预期影响**：本次输出可能改变哪些状态。

#### 2. 输入是否最小必要

输入应采用**最小必要**原则：

- Agent 只能读取完成任务所需的最小范围；
- 不是所有 Agent 都能读取所有历史会话或全部材料；
- 跨会话、跨学科读取必须显式授权；
- Agent 应能说明为什么需要某项输入。

#### 3. 谁决定 Agent 能读取什么

读取范围由**底层权限模型**决定，不依赖 Agent 的提示词自律。Agent 可以根据任务提出读取申请，但能否读取由底层在授权范围内决定。

#### 4. 输入是否可追溯

是。每次输入分配、读取和限制都应有记录，以支持后续判断、审计和回滚的解释。

### 四、Agent 的输出契约

#### 1. 统一输出结构

Agent 的结构化输出至少应包含以下字段：

```text
输出类型          # 事实提取/分析/判断候选/任务候选/规划候选/资产候选/风险提示/确认请求
目标对象          # 作用于哪个对象（材料/任务/规划/资产/记忆/反馈）
建议状态          # 建议进入什么状态（仍为候选，不直接生效）
来源与证据定位     # 引用了哪些证据及其位置
确定性等级        # 高/中/低/待核实/冲突
适用范围          # 哪个学科/任务/阶段/条件
影响范围          # 会影响任务/学科/全学科/资产/记忆/传播中的哪些
需要的确认        # 需要学生/教师/机构确认什么
后续验证方式      # 需要什么行动或现实反馈
模型与规则版本     # 使用了什么版本
失败或异常信息     # 是否无法完成，原因是什么
```

#### 2. 结构化输出 vs 自然语言

- 所有会产生状态影响的输出，应带结构化字段；
- 面向学生或机构的解释，可以同时提供自然语言；
- 自然语言不能替代结构化字段，不能用于绕过契约；
- 底层校验以结构化字段为准。

#### 3. 如何保证不能绕过契约

底层应：

- 校验输出是否符合契约；
- 校验来源是否存在；
- 校验目标对象是否合法；
- 校验权限；
- 校验建议状态是否为合法迁移；
- 校验影响范围；
- 阻断缺少必填字段或来源的输出；
- 记录校验结果；
- 对高风险输出要求确认。

Agent 不能仅凭一段文本声明“这已经是确认的资产”或“这是学校结果”，底层必须校验其来源和状态。

### 五、状态与权限校验

Agent 输出进入正式状态前，底层至少应检查：

1. **对象存在且合法**；
2. **当前状态允许该迁移**；
3. **调用者有权限**（读/写/升级/传播）；
4. **证据充分**（来源、确定性、适用）；
5. **无冲突或已登记冲突**；
6. **是否需要学生或其他角色确认**；
7. **不超出影响范围**；
8. **可回滚**；
9. **已记录审计**。

其中：

- 权限和状态检查由底层强制执行；
- 证据充分性由证据设施判断；
- 高影响操作必须阻断或请求确认；
- 不能由 Agent 自行宣布通过检查。

### 六、确认与审计

#### 1. 谁可以确认状态迁移

- **学生**：重大方向、资产确认、记忆、传播、阶段交接等；
- **教师/机构**：在授权范围内提供专业确认、反馈、复核请求；
- **底层规则**：自动触发的保护性确认或降级；
- **监察**：对关键判断和迁移发起复核；
- **运维**：在纠错、恢复、回滚场景受控介入。

Agent 可以：

- 发起确认请求；
- 解释需要确认的内容和理由；
- 组织学生或机构完成确认；
- 报告确认结果。

Agent 不能：

- 替学生或机构完成确认；
- 在缺少确认时把结果当成已确认；
- 绕过确认流程直接升级。

#### 2. 确认后的记录

每次确认都应记录：

- 确认者；
- 确认对象；
- 确认内容；
- 确认范围；
- 确认版本；
- 确认时间；
- 确认前的状态；
- 确认后的状态；
- 是否存在强迫、误导或信息不足。

#### 3. Agent 能否发起、解释但不能完成确认

能。Agent 可以发起和解释，但确认动作和状态结果由底层在真实主体的参与下完成，不能由 Agent 伪造。

#### 4. 审计字段与追溯链

审计至少应包含：

```text
事件ID
时间
调用者（Agent/学生/教师/机构/规则/运维）
责任域与会话
动作类型
输入摘要
输出摘要
使用的证据
建议状态
目标对象
确认者与确认内容
状态迁移前后
模型/内容/规则版本
结果
失败原因
回滚信息
```

追溯链要能从最终状态回到最初来源。

#### 5. 回滚如何执行

回滚应：

- 定位受影响的对象和下游；
- 保留原版本；
- 撤销或修正非法/错误状态迁移；
- 更新受影响的下游引用；
- 记录回滚原因、执行者和时间；
- 如需学生或其他角色知情，进行必要说明；
- 避免留下半更新状态。

Agent 可以建议回滚，但回滚的一致性和审计由底层负责。

### 七、接口的分层

#### 1. Agent → 底层设施接口

- Agent 提交输入请求；
- 底层返回授权数据；
- Agent 提交结构化输出；
- 底层返回校验、确认、状态迁移和审计结果。

#### 2. 底层设施之间的内部接口

- 证据、状态、权限、审计、任务等设施之间通过受控接口交换，不绕过责任边界。

#### 3. Agent → Agent 的受控协作

- 主军师/整体协调向学科 Agent 分派任务；
- 学科 Agent 向整体协调反馈结果；
- Agent 之间交接必须：
  - 明确责任；
  - 传递最小必要信息；
  - 记录交接；
  - 不共享无边界的全局上下文；
  - 不把推断当事实传递。

#### 4. 学生、教师、机构的交互接口

- 学生确认、纠正、拒绝、退出；
- 教师/机构反馈、复核、协作；
- 所有交互都通过权限、确认、审计设施落地，不绕过产品规则。

#### 5. 配置与内容版本接口

- 学业阶段、学科、内容包、任务模板、评价规则；
- 配置修改受控、版本化；
- 不能修改底层硬规则。

#### 6. 监察与审计接口

- 读取审计、运行记录、状态历史；
- 发起复核、阻断、回滚；
- 监察自身操作也被审计。

### 八、最低可运行契约

进入实现前，至少需要定义以下契约，才能让一个学业军师能力闭环可靠运行，而不是无法解释的 Agent 拼接：

1. **输入契约**：Agent 能读取什么、在什么范围、带什么标识；
2. **输出契约**：Agent 输出什么结构、带什么字段、是否候选；
3. **对象契约**：对象类型、状态、来源、归属；
4. **权限契约**：谁能读、写、确认、升级、传播、撤回；
5. **证据契约**：来源、强度、适用范围、冲突；
6. **状态契约**：合法状态迁移、触发条件、确认要求；
7. **确认契约**：谁确认、确认什么、如何记录；
8. **审计契约**：事件、调用者、依据、版本、回滚；
9. **回滚契约**：定位、撤销、下游更新、记录；
10. **失败契约**：Agent 失败时如何降级、重试、终止、通知；
11. **交接契约**：Agent 之间责任、信息、记录如何传递；
12. **交互契约**：学生/教师/机构的确认、反馈和协作。

这 12 项契约是“学业军师能力闭环可独立运行并验证”的最低接口条件。它们可以被进一步设计为具体的 API、数据结构或服务边界，但先要在产品语义层确定。

### 九、专业结论

> **底层设施与 Agent 之间必须通过受控接口契约协作。Agent 的输入遵循最小必要和权限控制；输出采用带来源、确定性、适用范围、影响和审计字段的结构化契约；Agent 输出默认是候选，只有经过底层对象、权限、证据、状态和确认校验，才能进入正式状态。**
>
> **Agent 可以发起和解释确认，但不能替学生或机构完成确认；Agent 可以建议回滚，但不能绕过底层一致性和审计。接口应分层：Agent→底层、底层内部、Agent→Agent 受控协作、学生/教师/机构交互、配置内容版本、监察审计。**
>
> **进入实现前，至少需要定义输入、输出、对象、权限、证据、状态、确认、审计、回滚、失败、交接和交互十二类契约，否则一个学业支持闭环就无法独立可靠运行并验证。**

## 3.2　问题 3-2：会话、责任域与多 Agent 协作编排

**标准化问题**：在统一证据、会话、权限和监察约束下，整体协调、学科、任务部署、教与授、证据、资产、监察如何被编排为可协作、可追溯、不碎片化的整体？涉及责任域与会话的区别、“一个会话只解决一件事”如何落地、责任域间如何受控交接、Agent 能否跨域读取、前端是否替代底层隔离；是否需要顶层主军师编排及其权限边界、专业 Agent 分工与协作、Agent 间是否能直接调用、任务分发与结果回收、失败/超时/重试/终止处理、统一约束、学生体验与底层结构对应，以及最低可运行协作闭环。

### 一、核心结论

学业军师不应采用“多个 Agent 自由对话、最后由一个 Agent 总结”的协作方式，而应采用：

> **责任域隔离、底层统一约束、主军师统一编排、专业 Agent 分工执行、所有交接可追溯的受控协作结构。**

其基本关系为：

```text
学生统一入口
        ↓
主军师 / 整体协调
        ↓
任务部署与责任域编排
 ┌──────┼────────┬────────┐
学科域  证据域   教与授域  资产域
 └──────┼────────┴────────┘
        ↓
结果、风险、证据与状态回传
        ↓
主军师重新协调
        ↓
监察、确认、状态迁移与审计
```

这里的“主军师”是产品责任上的顶层协调者，不是拥有无限权限的超级 Agent；“专业 Agent”是局部责任的执行者，不是彼此自由决定的平等系统。

### 二、责任域与会话不是同一概念

#### 1. 责任域

责任域回答：

> **谁对哪类工作负责，能够读取什么，能够产生什么输出，不能越过哪些边界？**

候选责任域包括：

- 全学科学业协调；
- 学科协调与专业判断；
- 证据治理；
- 任务部署；
- 教与授；
- 学业资产；
- 监察与审计。

责任域是产品和权限边界，必须由底层确定性设施定义和强制。

#### 2. 会话

会话回答：

> **某项具体工作在什么范围内开始、持续、暂停、结束和恢复？**

一个会话至少应绑定：

- 责任域；
- 学生和机构范围；
- 当前学业阶段；
- 目标任务；
- 可读取对象；
- 可写入对象；
- 完成条件；
- 交接出口；
- 暂停与恢复位置；
- 审计标识。

因此：

- 一个责任域可以产生多个会话；
- 一个会话不能随意跨越多个责任域；
- 会话不是无限上下文；
- 会话结束不等于所有内容自动进入记忆；
- 前端窗口不是责任域本身。

### 三、“一个会话只解决一件事”的专业含义

这句话不意味着学生只能问一个问题，也不意味着系统必须把每次对话截成极短片段。它意味着：

> **一个会话必须围绕一个明确的工作目标和责任边界运行，不能在不受控制的情况下混合不同学科、不同用途、不同权限和不同状态。**

底层应能够识别：

- 当前会话的目标是否改变；
- 责任对象是否改变；
- 读取范围是否需要扩大；
- 是否发生学科或阶段切换；
- 是否从分析转为规划、从规划转为资产处理；
- 是否出现新的高影响操作。

出现重大变化时，底层可以：

- 结束当前会话；
- 创建新会话；
- 生成受控交接；
- 保存未完成状态；
- 请求学生知情；
- 阻止旧上下文继续影响新责任域。

技术上的自动切换不应被当作任务完成，也不应把未完成状态写成学生同意。

### 四、责任域之间如何交接

责任域之间不应共享无边界的完整上下文，而应通过**结构化交接包**协作。

一个交接包至少应包含：

- 交接来源责任域；
- 接收责任域；
- 交接目标；
- 输入对象 ID；
- 必要证据及来源定位；
- 当前判断及其状态；
- 确定性和限制；
- 未知、冲突和待确认项；
- 建议动作；
- 允许接收方执行的范围；
- 禁止接收方执行的范围；
- 交接版本和时间；
- 审计标识。

例如，学科 Agent 向整体协调提交的不是一句“数学存在严重问题”，而应是：

- 哪些任务产生了该判断；
- 使用了哪些材料；
- 判断处于什么状态；
- 是否存在其他解释；
- 对时间和资源有什么影响；
- 建议整体层考虑什么；
- 哪些结论尚不能作出。

接收方不得把交接包中的“候选判断”当成“已确认事实”。

### 五、主军师的职责与权限

#### 1. 主军师负责什么

主军师或整体协调 Agent 负责：

- 理解整体协调目标；
- 决定需要调用哪些责任域；
- 分发任务；
- 汇总专业结果；
- 比较不同方案；
- 识别跨学科冲突；
- 请求补证或复核；
- 形成整体安排候选；
- 向学生解释整体安排；
- 将高影响变化提交底层确认流程。

这落实了“顶层拍板、调控、编排”的产品方向，但“拍板”应理解为**在合法权限内形成顶层候选决策**，不意味着可以绕过学生确认或底层规则直接改变正式状态。

#### 2. 主军师不能做什么

主军师不能：

- 绕过证据设施直接读取全部材料；
- 自行改变对象类型；
- 自行确认学生意愿；
- 直接把候选规划写成正式规划；
- 直接把学科 Agent 的判断改写为事实；
- 跳过监察和审计；
- 授予自己或其他 Agent 新权限；
- 自行批准自己的高影响输出；
- 以“整体最优”为由覆盖学生对重大方向的确认权。

因此，主军师是**最高层协调责任者**，但不是底层权限的最高豁免者。

### 六、专业 Agent 的职责

专业 Agent 负责各自明确的局部责任：

| Agent/责任域 | 主要职责 | 不拥有的权力 |
|---|---|---|
| 学科 Agent | 学科诊断、教与授、练习、检验、学科结果反馈 | 改变全局优先级 |
| 证据 Agent | 登记、归类、提取、冲突识别、来源追溯 | 自行形成最终学业结论 |
| 任务部署 Agent | 把已批准方向转为任务候选 | 伪造学生接受或完成 |
| 教与授 Agent | 讲解、示范、练习、检验编排 | 直接宣布学生已掌握 |
| 资产 Agent | 提出资产候选、解释来源、跟踪复验 | 自行确认正式资产 |
| 监察 Agent | 检查依据、权限、状态、交接和风险 | 自行成为不可审查的最终权威 |
| 阶段管理 Agent | 生成阶段总结、交接候选 | 自行结束或延长阶段 |
| 主军师 | 整体编排、比较、提出安排 | 绕过底层和学生确认 |

Agent 的职责边界应由输入、输出、状态、权限和后果定义，而不是只由人格名称定义。

### 七、Agent 之间是否可以直接调用

原则上不允许任意 Agent 直接自由调用。

#### 允许的调用方式

- 调用关系由底层注册；
- 调用者和被调用者均有明确责任域；
- 输入范围和输出类型预先定义；
- 调用带有目标、来源和权限；
- 结果经过底层记录；
- 失败、超时和重试可控；
- 重要状态变化仍需回到状态与确认设施。

#### 不允许的调用方式

- Agent 通过自然语言自行发现并调用任意其他 Agent；
- 直接共享全部会话上下文；
- 直接修改另一个责任域的状态；
- 以 Agent 间口头确认代替学生或机构确认；
- 通过中间 Agent 链条绕过权限检查；
- 调用者同时拥有请求、批准和审计同一高影响操作的全部权限。

### 八、任务分发与结果回收

标准流程应为：

```text
1. 主军师识别当前整体目标
2. 底层检查主军师可调用的责任域
3. 主军师提交结构化任务分派
4. 底层授予最小必要输入和权限
5. 专业 Agent 在责任域内执行
6. 专业 Agent 返回结构化结果、依据、限制和建议
7. 底层校验结果和状态影响
8. 主军师汇总、比较并发现冲突
9. 必要时请求补证、复核或监察
10. 形成整体安排候选
11. 必要时请求学生确认
12. 底层执行合法状态迁移并审计
```

结果回收不能只接收 Agent 的自然语言总结，至少应接收：

- 任务 ID；
- 责任域；
- 输入证据；
- 输出类型；
- 当前状态；
- 确定性；
- 适用范围；
- 未知和冲突；
- 建议下一步；
- 是否需要确认；
- 版本与审计信息。

### 九、失败、超时、重试和终止

#### 1. Agent 失败

底层应区分：

- Agent 没有返回；
- 返回格式非法；
- 输入不足；
- 工具失败；
- 证据冲突；
- 权限不足；
- 输出无法验证；
- 超过时间或资源限制。

失败不能被包装成“没有问题”或“任务完成”。

#### 2. 重试

重试必须有：

- 次数上限；
- 原因记录；
- 是否更换模型或 Agent；
- 是否使用相同输入；
- 是否产生重复副作用；
- 何时转人工或暂停。

对已经产生状态变化的调用，不应简单重复执行而不做幂等检查。

#### 3. 超时

超时后：

- 保留未完成状态；
- 不把未返回当作成功；
- 通知主军师和必要的用户；
- 可以提供低确定性替代路径；
- 高影响操作保持暂停。

#### 4. 终止

终止条件可包括：

- 任务完成；
- 输出已交接；
- 输入不足；
- 冲突无法裁决；
- 权限不足；
- 风险超过门槛；
- 学生拒绝或退出；
- 阶段结束。

终止只结束当前工作单元，不自动删除证据、资产、审计和历史版本。

### 十、如何防止碎片化和各自为政

#### 底层必须强制

- 统一对象模型；
- 统一证据来源和状态；
- 统一权限；
- 统一会话责任域；
- 统一交接格式；
- 统一状态机；
- 统一审计；
- 统一监察与回滚；
- Agent 调用注册；
- 输入输出契约；
- 版本兼容。

#### 主军师负责管理

- 统一整体目标；
- 分配专业任务；
- 比较结果；
- 调整协作顺序；
- 处理冲突；
- 识别是否需要上升到整体层；
- 维持学生可理解的统一结果。

#### 专业 Agent 负责执行

- 不跨越自己的责任域；
- 不自行扩大输入；
- 不自行改写其他域状态；
- 不把局部判断包装成全局结论；
- 不隐藏不确定性和冲突。

### 十一、学生体验与底层结构

#### 1. 学生是否只能面对一个入口

建议：

- 学生默认面对一个统一入口，即主军师；
- 主军师将复杂工作分派给专业 Agent；
- 学生不必学习 Agent 编排和底层接口；
- 学生仍可以看到足以理解当前安排的依据、状态、未知和控制选项。

统一入口不是把所有责任混在一个会话中，而是：

> **前端统一体验，底层责任分域。**

#### 2. 学生是否能接触责任域

学生不必直接操作所有责任域，但应能：

- 看到当前任务由哪类专业能力支持；
- 查看影响当前安排的依据；
- 看到未决和冲突；
- 纠正事实；
- 确认、拒绝、暂停和退出；
- 查看资产和阶段内认识；
- 知道信息如何被使用。

不应展示会增加无意义负担的内部技术细节，也不能以隐藏全部过程为由遮蔽会影响学生判断的事实和限制。

#### 3. 前端能否代替底层隔离

不能。

分栏、标签、多个窗口只能帮助学生理解和操作，不能代替：

- 权限隔离；
- 状态隔离；
- 会话隔离；
- 审计；
- 责任交接；
- 版本与回滚。

### 十二、最低可运行的多 Agent 协作闭环

至少需要：

1. 一个主军师或整体协调责任域；
2. 一个学科专业责任域；
3. 一个任务部署责任域；
4. 一个教与授责任域；
5. 一个证据治理责任域；
6. 一个监察或质量检查责任域；
7. 底层对象、证据、状态、权限和审计设施；
8. 结构化任务分派协议；
9. 结构化结果回收协议；
10. 责任域交接协议；
11. 失败、超时、重试和终止机制；
12. 学生确认、拒绝和暂停机制；
13. 至少一个可追溯的规划—任务—行动—检验闭环；
14. 对高影响状态的阻断和回滚能力。

这不表示第一版必须实现所有学科和所有专业 Agent，而是表示进入工程实现前，协作骨架和硬约束必须被定义。

### 十三、底层与 Agent 的最终分工

| 领域 | 底层基础设施 | Agent 管理层 |
|---|---|---|
| 会话 | 定义边界、隔离、暂停、恢复、结束 | 在会话内完成专业工作 |
| 调用 | 注册、授权、参数、超时、重试、终止 | 选择允许的专业能力 |
| 交接 | 格式、权限、记录、版本 | 组织任务和反馈传递 |
| 状态 | 合法迁移、确认、审计、回滚 | 提出候选变更 |
| 证据 | 来源、范围、冲突、权限 | 分析和解释 |
| 冲突 | 标记、升级和阻断规则 | 解释、比较和提出解决方案 |
| 监察 | 质量门槛、审计、阻断、回滚 | 风险分析和复核建议 |
| 学生体验 | 可见性、控制权、确认记录 | 引导、解释和沟通 |
| 整体协调 | 权限和状态边界 | 汇总、比较、编排和提出整体安排 |

### 十四、专业结论

> **学业军师应采用“前端统一入口、底层责任分域、主军师统一编排、专业 Agent 分工执行、底层统一约束和审计”的多 Agent 协作结构。**
>
> **责任域决定谁对哪类工作负责，会话决定某项工作在什么范围内运行；二者不能混同。Agent 之间不得自由共享上下文或任意直接调用，所有任务分派、结果回收和跨域交接都必须经过底层契约、权限和审计。主军师负责整体编排和方案比较，但不拥有绕过底层或学生确认的超级权限。**
>
> **多 Agent 协作是否成立，不由 Agent 数量或前端是否像一个聊天窗口决定，而由“分派—执行—回收—复核—确认—状态迁移—审计”的完整闭环决定。**

## 3.3　问题 3-3：教与授的产品机制

**标准化问题**：教与授作为学业军师将“判断与规划”转化为学生真实学习行动的核心承接机制，其产品机制应当如何设计——包括产品定位、讲解/练习/检验的责任分工、与任务的绑定方式、学生真实学习行动的底层保护、任务完成/理解/能力形成的三级区分、结果回流、教师/机构/学生参与边界，以及底层与 Agent 的分工？

**回应与论证**：

### 一、产品定位：教与授是核心责任，不是内容附加

教与授不能被理解为把题库、讲解模型或学习内容接入规划之后的附加功能。它是学业军师将“判断与规划”转化为学生真实学习行动的核心承接机制。

> **没有与当前问题、任务和检验相连接的教与授，规划就可能停留在文字建议；没有学生行动和结果检验，教与授也可能退化为内容消费。**

因此，教与授应形成：

```text
学业判断
  → 教与授目标
  → 讲解/示范
  → 练习/作答
  → 检验
  → 反馈与复盘
  → 任务或规划修正
```

教与授可以复用外部内容引擎、题库、模型或运行能力，但以下内容必须由学业军师自持：

- 为什么此时需要教与授；
- 教与授承接哪个问题和任务；
- 教什么、练什么、如何检验；
- 检验结果如何影响后续安排；
- 什么能记录为学习证据；
- 什么不能被解释为已掌握。

### 二、讲解、练习与检验的责任分工

#### 1. 讲解与示范

**目标**：帮助学生理解当前问题、概念、方法或任务要求。

**输入**：

- 当前任务；
- 相关学科和阶段内容；
- 已授权的证据；
- 学生已确认的学习目标；
- 已知困难和待核实事项；
- 适用的课程与内容版本。

**触发条件**：

- 诊断显示存在理解缺口；
- 学生请求解释；
- 任务执行前需要建立必要理解；
- 练习或检验暴露出新的误解。

**输出**：

- 讲解内容；
- 示例或示范；
- 关键步骤；
- 常见误区；
- 学生需要完成的后续行动；
- 对理解仍不确定的部分。

**底层必须保证**：

- 内容来源、学段和版本可追溯；
- 讲解对象与当前任务关联；
- Agent 不能把“已展示”写成“学生已理解”；
- 学生不能完成作答的讲解内容，不得被记录为学生成果。

**Agent 可以负责**：

- 选择讲解方式；
- 组织表达顺序；
- 生成示例；
- 根据学生反馈调整解释；
- 提出后续练习。

#### 2. 练习与作答

**目标**：让学生把理解转化为实际操作，产生可观察的学习行为和结果。

**输入**：

- 当前教与授目标；
- 诊断出的困难；
- 学科内容和任务规则；
- 练习难度与范围；
- 已有但仍适用的学生认识。

**触发条件**：

- 讲解需要通过行动检验；
- 学生需要巩固或迁移；
- 既有结果显示某种方法尚未稳定；
- 需要为学校任务准备可验证的行为。

**输出**：

- 练习任务；
- 学生作答；
- 操作过程或步骤；
- 订正和复盘材料；
- 可检查的练习结果。

**底层必须保证**：

- 练习由系统生成不等于学生完成；
- 学生作答与 Agent 生成内容分开保存；
- 学生声称完成与存在可检查结果分开；
- 代写、自动填答或系统生成结果不能冒充学生行为；
- 作答、订正和复盘均可追溯。

**Agent 可以负责**：

- 生成练习候选；
- 调整难度和顺序；
- 提供提示；
- 分析作答；
- 设计订正和复盘；
- 提出下一轮练习。

#### 3. 检验

**目标**：检查学生是否理解、能否应用、是否能够迁移，而不是只确认学生看过内容。

**输入**：

- 讲解内容；
- 学生练习与作答；
- 当前任务完成条件；
- 适用的评价规则；
- 必要的学校任务或现实反馈。

**触发条件**：

- 任务要求验证完成；
- 练习结果显示需要复核；
- 学生表示已经掌握；
- 需要判断是否进入下一阶段任务；
- 需要复验某项学业认识。

**输出**：

- 检验任务；
- 学生真实作答或行动；
- 结果解释；
- 仍存在的缺口；
- 是否需要补充教与授；
- 下一步建议；
- 当前验证状态。

**底层必须保证**：

- 检验结果有来源、对象和时间；
- 检验规则和内容版本可追溯；
- Agent 不能自行宣布“已掌握”；
- 内部检验不能自动写成学校现实结果；
- 单次正确不能自动升级为稳定能力；
- 检验结果进入资产或记忆前必须经过相应状态流程。

**Agent 可以负责**：

- 设计检验形式；
- 生成检验材料；
- 分析学生作答；
- 解释结果；
- 提出补充检验或复验；
- 建议是否进入下一步。

### 三、教与授必须与任务绑定，但不必机械线性

教与授不能脱离学业问题，成为独立的内容消费；但也不要求所有流程严格按照“讲解一次—练习一次—检验一次”的固定顺序运行。

更准确的关系是：

> **教与授服务于当前任务和学习问题，并根据学生的行动、结果和反馈动态循环。**

可能的路径包括：

```text
诊断 → 讲解 → 练习 → 检验
             ↘
              检验发现新问题 → 补充讲解
```

也可能是：

```text
学校任务
  → 学生尝试
  → 发现障碍
  → 针对性讲解
  → 重新练习
  → 现实任务复验
```

因此：

- 教与授可以被 Agent 动态触发；
- 触发必须能说明服务哪个任务或问题；
- 结果必须回到任务、证据和后续规划；
- 不应把教与授设计成无目标的内容流。

### 四、学生真实学习行动的底层保护

产品至少要区分：

```text
系统提供讲解
→ 学生查看
→ 学生理解的自述
→ 学生练习/作答
→ 结果待检验
→ 已检验结果
→ 后续任务中的迁移表现
```

这些状态不能合并。

#### “看过讲解”不等于“掌握”

因为：

- 查看不等于理解；
- 理解不等于能够作答；
- 一次作答正确不等于能够迁移；
- 内部练习有效不等于学校任务中有效；
- 学生自述“会了”是重要线索，但不是充分证明。

底层应记录：

- 内容是否提供；
- 学生是否查看；
- 学生是否作答；
- 作答是否来自学生；
- 结果是否可检查；
- 是否完成即时检验；
- 是否完成延迟或迁移检验；
- 是否存在学校现实反馈。

Agent 可以解释这些状态，但不能把低强度状态升级为高强度能力结论。

### 五、任务完成、理解和能力形成的三级区分

#### 1. 内容提供

系统已经讲解、示范或提供练习。

这只能证明：

> 产品提供了支持。

不能证明学生已经理解。

#### 2. 任务完成

学生完成了约定的练习、作答或行动，并产生了可检查结果。

这可以证明：

> 某项任务在特定条件下完成，结果可供分析。

不能直接证明稳定能力。

#### 3. 能力形成

学生能够在不同但相关的任务和现实环境中持续、相对稳定地应用方法。

通常需要：

- 多次任务；
- 不同情境；
- 延迟复验；
- 迁移表现；
- 学校现实反馈；
- 对失败和修正的持续观察。

因此，教与授的输出应使用分层状态，不应只有“已完成/未完成”或“掌握/未掌握”。

### 六、教与授结果如何回流

每次教与授活动结束后，至少应回流：

- 使用了什么内容和版本；
- 学生完成了什么；
- 产生了什么结果；
- 哪些困难仍存在；
- 哪些判断得到支持或受到质疑；
- 是否需要补证；
- 是否需要调整任务；
- 是否形成资产候选；
- 是否需要现实学校复验。

回流路径为：

```text
教与授结果
  → 任务状态更新
  → 证据登记
  → 学科判断修正
  → 整体协调重新评估
  → 下一步任务或规划候选
```

回流不意味着自动状态升级。底层仍须检查：

- 来源；
- 真实性；
- 适用范围；
- 权限；
- 冲突；
- 所需确认；
- 状态迁移条件。

### 七、教师、机构与学生的参与边界

#### 学生

学生是实际学习行动的完成者，负责：

- 理解或提出不理解；
- 练习和作答；
- 参与检验；
- 提供反馈；
- 纠正事实；
- 确认或拒绝重要安排。

#### 教师和机构

在授权范围内可以：

- 提供课程、作业和评价材料；
- 提供专业反馈；
- 协助教与授；
- 解释学校任务和课程进度；
- 对结果提出复核意见。

他们不能替代学生完成学习行动，也不能绕过底层规则把自己的判断直接写成学生资产或能力结论。

#### Agent

Agent 可以组织、解释、编排和提出候选，但不能：

- 代写作答；
- 伪造行动结果；
- 代替学生确认；
- 直接宣布掌握；
- 将内部结果伪装为学校结果。

### 八、底层与 Agent 的明确分工

| 环节 | 底层基础设施必须保证 | Agent 可以执行 |
|---|---|---|
| 教与授目标 | 目标对象、来源、学段和任务关联 | 提出目标与讲解方案 |
| 讲解 | 内容版本、来源、展示记录 | 组织解释和示范 |
| 练习 | 学生作答真实性、原始结果 | 生成练习和提示 |
| 检验 | 检验规则、结果来源、状态迁移 | 设计和解释检验 |
| 任务状态 | 接受、执行、完成、待检验 | 推进和调整任务候选 |
| 反馈 | 来源、时间、完整性、冲突 | 分析和解释反馈 |
| 资产/记忆 | 准入、确认、复验和生命周期 | 提出候选 |
| 能力判断 | 禁止单次结果自动升级 | 提出有限判断和复验建议 |
| 规划回流 | 权限、影响范围、审计、回滚 | 建议下一轮规划 |

### 九、专业结论

> **教与授是学业军师将规划转化为真实学习行动的核心产品责任。它必须与当前问题、任务和检验关联，但可以根据学生行动和反馈动态循环。讲解负责建立理解，练习负责产生实际行动，检验负责区分任务完成、即时表现与可迁移能力；任何一个环节都不能被系统生成或学生查看记录冒充为学生已经掌握。**
>
> **底层基础设施负责内容版本、学生行动真实性、作答和检验来源、任务状态、证据回流、资产准入和状态迁移；Agent 负责讲解编排、练习生成、检验设计、结果解释和后续建议。**
>
> **教与授结果必须回到任务、证据、学科判断和整体协调，但不能绕过底层校验和确认流程直接形成资产、记忆、能力或教育效果结论。**

## 3.4　问题 3-4：证据、记忆与会话的持续治理

**标准化问题**：在长期、持续的使用中，为遵循“证据＞记忆＞上下文”原则并防止系统把历史判断当作当前事实、把未确认推断当作已确认结论、把一次错误传播到后续规划，证据、记忆与会话应如何被持续治理——包括三者的区分与转换、什么进入记忆、记忆的准入/权限/生命周期、会话的边界与恢复、污染防治与错误传播阻断、撤回/修正/失效的底层保证，以及底层与 Agent 的分工？

**回应与论证**：

以下为记录中本单元完整回应正文（记录标注为 [专业建议·代拟]）。原始底稿仅作参考，用于校准“证据＞记忆＞上下文”“会话结束受控蒸馏”“记忆可见可纠正可删除”“三态缓存/封存”等概念，不覆盖本次代拟，历史“已确认”不升级为当前决定。用户随后回复“确认”。

### 一、核心原则

> **在长期、持续的使用中，若证据、记忆和会话的边界不清晰，系统会把历史判断当作当前事实、把未确认推断当作已确认结论、把一次错误传播到后续规划，最终出现“证据＞记忆＞上下文”原则被违背、学生状态被污染的局面。**

因此，证据、记忆和会话必须满足三组条件：

1. **具备明确来源**：每个进入判断的对象都能追溯来源和适用范围；
2. **具有可控生命周期**：能创建、暂停、失效、封存、交接或删除；
3. **可撤回和阻断**：错误或过时内容一旦被识别，能阻断其下游使用。

### 二、证据、记忆、会话、资产如何区分和转换

#### 1. 原始材料 → 证据

原始材料只有在被登记来源、类型、支持范围和授权用途之后，才成为证据。材料本身不等于证据。

#### 2. 证据 → 判断

证据可以支持某个判断，但证据不能自动变成事实。证据的作用是决定一个判断只能达到什么确定性、需要哪些确认。

#### 3. 会话上下文

会话是有限工作上下文，保存当前工作所需的部分信息。它不自动成为证据、记忆或资产。

#### 4. 记忆

记忆是跨会话、受控制地保留的持续理解信息。它有助于“越用越懂学生”，但不是所有工作信息都必须进入记忆。

#### 5. 资产

资产是经过提炼、学生理解和确认后，可在明确范围内复用的个人学业认识。不是所有记忆都能成为资产。

#### 6. 转换原则

```text
原始材料 → 证据（登记后）
证据 → 支持有限判断（不自动成事实）
当前工作信息 → 会话上下文（会话内）
持续价值信息 → 记忆候选 → 记忆（满足准入）
可复用认识 → 资产候选 → 资产（学生确认+底层状态）
```

不存在“只要进入系统就自动变成记忆和资产”的转换。每一步都必须有明确的准入、来源和状态。

### 三、什么进入记忆、什么不进入

#### 可以进入阶段内记忆的候选

满足以下条件时可作为记忆候选：

- 与当前及可预期的后续学习相关；
- 有明确来源（材料、行动、反馈、确认）；
- 具有持续使用价值；
- 能够说明适用范围和期限；
- 不包含不必要的敏感隐私；
- 学生可见、可纠正、可撤回或删除；
- 有助于“越用越懂学生”但不操纵学生。

例如：

- 学生稳定的学习偏好；
- 已确认的阶段性目标；
- 长期有效的学习规律；
- 学生反复达到的稳定绩效区间；
- 需要跨会话持续跟踪的当前任务和未决项。

#### 不应进入记忆的内容

- 未确认的推断；
- 单次练习的偶然状态；
- 已过时的规划；
- 与学习支持无关的私人信息；
- 相关度有限的临时上下文；
- 缺乏来源或权限的内容；
- 已被撤回、删除或失效的内容；
- 仅在某个任务短暂有效、不再需要持续跟踪的信息；
- 学生不希望保留的内容（在满足规则情况下）。

### 四、记忆的准入、权限和生命周期

#### 1. 准入

进入记忆须通过：

- 来源检查；
- 范围说明；
- 用途说明；
- 期限判断；
- 敏感或权限边界检查；
- 学生可见性和可控性检查；
- 是否符合记忆规则。

Agent 可以提出记忆候选，但不能自行写入。底层决定准入，必要时由学生确认。

#### 2. 作用范围

记忆应限定适用范围：

- 当前学业阶段；
- 相关学科；
- 相关任务；
- 特定用途；
- 可跨会话引用但不跨责任域滥用的范围。

记忆不应自动进入所有会话的后台。

#### 3. 学生可见性与控制权

学生应能：

- 查看关于自己的记忆内容；
- 纠正不正确的认识；
- 拒绝保留某条记忆；
- 撤回某条记忆的使用；
- 删除某些可删除内容或限制用途；
- 看到记忆形成的时间、来源和证据链。

产品不应对学生的长期理解不可见。绝大多数影响学习安排和判断的认识应可见、可纠正、可删除。

#### 4. 生命周期

记忆具有从创建到失效、封存或删除的生命周期：

```text
记忆候选
→ 待确认（如需要）
→ 阶段内有效
→ 待复核
→ 修订版有效
→ 降级
→ 失效
→ 封存 / 归档 / 删除
```

阶段结束时，记忆默认不能自动进入下一阶段，需按交接规则处理。

### 五、会话的边界与恢复

#### 1. 何时结束会话并保存恢复线索

可在以下情况结束或切换会话：

- 任务完成；
- 责任域或主题变化；
- 需要重新确认目标；
- 达到技术或安全边界；
- 长时间无操作；
- 出现证据冲突或重大变化；
- 发生难以回滚的高影响操作。

结束会话时，应保存恢复线索，而不是直接丢弃所有工作内容。恢复线索包括必要的当前状态、未决项和可续接位置。未完成的工作不能自动视为已确认或已完成。

#### 2. 恢复时哪些内容回到上下文

恢复只带回必要的当前状态和受控的未决项，不能：

- 把旧会话的全部记忆无差别带回；
- 把未确认判断当作已确认事实；
- 把过时规划当作当前最优；
- 把错误判断继续当作上下文。

恢复前应重新校验：

- 目标是否仍相关；
- 判断是否仍有效；
- 证据是否过期；
- 是否存在已失效记忆；
- 是否需要学生重新确认。

#### 3. 会话结束是否自动产生记忆或资产

不自动产生。

会话结束应进行受控蒸馏，把工作内容分类为：

- 仅本次任务需要的临时上下文；
- 需要成为过程证据的内容；
- 可作为记忆候选的内容；
- 可作为资产候选的内容；
- 未决和待确认项；
- 需要销毁或降级的内容。

蒸馏只是候选项，不自动写入记忆或资产，仍需经过准入和确认。

### 六、如何防止上下文污染与错误传播

#### 1. 学科、任务与会话隔离

- 不同学科、不同责任域、不同任务默认隔离；
- 跨学科读取必须显式授权；
- 任务之间不能共享无边界的上下文；
- Agent 之间不能仅凭对话历史获得其他域的内容。

#### 2. 未确认判断不作为事实

- 未确认的推断默认只是候选；
- 不将其升级为已确认；
- 不向其赋予与事实相同的权重；
- 传递时保留“待确认/推断/限定”。

#### 3. 错误判断不能无限传播

- 判断、记忆、资产有来源和时间；
- 发现错误后能阻断下游使用；
- 撤回或修正能识别受影响对象；
- 旧版本能停止被引用；
- 审计能追溯错误链条并阻止错误扩大。

#### 4. 避免长期过时内容影响新判断

- 新判断应优先参考当前证据，而非历史记忆；
- 历史记忆应带时间和适用范围；
- 过期记忆应标记为待复核或失效；
- Agent 不能默认历史记忆为“当前最相关”。

#### 5. 传递时保留来源和限定

- Agent 之间传递判断必须保留来源、确定性和限制；
- 不能把“A Agent 的推断”传成“已确认事实”；
- 接收方必须知道信息的对象、来源和状态；
- 解释“依据什么”比“给出什么结论”同等重要。

### 七、撤回、修正和失效的底层保证

底层必须支持：

- 撤回一篇证据、记忆或资产；
- 标记为错误；
- 识别依赖该对象的下游判断和任务；
- 阻断这些下游继续使用；
- 更新受影响的版本或状态；
- 保存撤回或修正的审计；
- 在必要时通知学生或相关角色；
- 避免留下半更新状态。

下游引用不应在被阻断前继续依赖已失效来源。

### 八、底层与 Agent 分工

| 领域 | 底层基础设施 | Agent 管理层 |
|---|---|---|
| 来源 | 登记、版本、授权、冲突 | 识别和关联 |
| 证据 | 状态、范围、撤回、追溯 | 分析和解释 |
| 记忆 | 准入、范围、生命周期、删除 | 提出记忆候选 |
| 会话 | 边界、隔离、恢复、结束、蒸馏 | 在会话内工作并请求交接 |
| 上下文 | 隔离、阻断污染、版本 | 组织和解释当前工作 |
| 资产 | 确认、复验、生命周期、复用 | 提炼候选 |
| 错误传播 | 阻断、回滚、下游影响识别 | 风险和复核建议 |
| 学生控制 | 记忆可见、纠正、撤回、删除 | 引导和解释 |

Agent 不能：

- 自行扩大会话上下文；
- 自行写入记忆；
- 自行把会话内容变成资产；
- 自行结束会话并宣称已完成；
- 自行删除或覆盖证据；
- 在未确认时把推断当事实传递。

### 九、专业结论

> **学业军师必须对证据、记忆、会话和资产实施持续治理。对象必须先有来源、范围和状态，才能在系统中具备作用；未确认推断不能自动成为事实，错误和过时内容必须能被阻断、撤回或失效，防止跨会话、跨学科和跨 Agent 的错误传播。**
>
> **记忆只保留有助于持续理解和当前学习的受控信息，必须满足准入规则，且学生对其可见、可纠正、可撤回、可删除。会话有边界和恢复线索，结束只产生受控蒸馏候选，不自动生成记忆或资产。**
>
> **底层负责来源、范围、生命周期、隔离、阻断、撤回、审计和回滚；Agent 负责分析、解释、提出记忆与资产候选、组织和推进当前学习，但不得自行扩大上下文或写入记忆。**

## 3.5　问题 3-5：模拟评测与真实验证的边界

**标准化问题**：产品成立与否必须用可验证的方式证明，但不能用错误的方式证明。模拟评测与真实长期验证分别能证明什么、不能证明什么？验证应如何分层，模拟场景如何构造，机制验证与教育价值验证如何分离，长期自生长的机制与价值分别如何验证，以及底层/Agent/监察在验证中的分工与通过门槛由谁定义？

**回应与论证**：

### 一、核心原则

> **产品成立与否，必须用可验证的方式证明，但不能用错误的方式证明。**

学业军师需要区分两类完全不同的结论：

- **机制验证**：产品是否按设计运行、底层是否可靠、Agent 是否遵守契约；
- **教育价值验证**：产品是否真实帮助了学生、是否改善学校结果、是否形成学生能力。

模拟评测可以支持第一类，但不能宣称第二类。真实学生和学校现实反馈是第二类不可替代的证据来源。

> **模拟评测证明“系统能不能按设计工作”；真实长期使用证明“产品有没有教育价值”。二者不能互相替代。**

### 二、模拟评测能证明什么

#### 可以证明

在开发阶段，模拟评测（使用准备好的材料、构造的场景和模拟学生）可以验证：

- 产品机制是否按设计运行；
- 底层对象、状态、权限和审计是否正确；
- Agent 是否遵守输入输出契约；
- 多 Agent 编排是否形成闭环；
- 证据、记忆、会话、资产的区分和转换是否正确；
- 状态迁移、确认、撤回和回滚是否可用；
- 责任域隔离和防污染是否有效；
- 监察是否能发现异常、越权和缺证；
- 跨学科、跨会话和阶段交接是否可追溯；
- 边界、失败、未知和冲突场景是否被覆盖；
- 能否生成可用于开发和审查的运行证据。

这些是**机制和工程层面的证明**。

#### 不能证明

模拟评测不能证明：

- 学生真实理解；
- 学生真实行动发生；
- 学生形成可迁移能力；
- 学校现实结果改善；
- 教育效果由产品造成；
- 学生对产品的理解、接受和信任；
- 长期使用后学生真正的自主能力提升；
- 产品在真实学校环境和机构场景中的可行性。

如果使用模拟数据宣称“产品已证明能提升学生”，属于自欺，也与学业军师“不把未验证的事当事实”的原则冲突。

### 三、真实验证的层次

需要区分至少五层，不能全部混为一谈。

#### 1. 产品机制验证

通过模拟或受控运行，证明：

- 系统能按契约运行；
- 底层可靠；
- Agent 不越权；
- 状态可追溯；
- 无伪证据、伪记忆。

这不证明教育效果。

#### 2. 真实学生小样本验证

在获得授权的前提下，用少数真实学生观察：

- 学生能否理解产品；
- 是否愿意使用；
- 能否按建议完成行动；
- 产品是否造成认知负担或困惑；
- 纠正、确认、拒绝机制是否可用；
- 前端和沟通是否有效；
- 学生在真实学习过程中的行为变化。

这是产品可用性和机制在真实主体上的早期检验，但仍不能据此断言教育效果。

#### 3. 学校现实反馈验证

通过真实学校任务、作业、考试、教师反馈，检验：

- 内部判断是否经受现实任务；
- 方法能否迁移；
- 规划与学校要求是否一致；
- 学生的学校结果和表现；
- 现实反馈是否能回流并修正产品。

这能提供重要的现实有效性证据，但仍需长期、多来源、可追溯。

#### 4. 长期能力形成验证

通过持续至少数月的真实使用，观察：

- 学生是否逐步形成“看清问题—决定行动—依据结果修正”的自主能力；
- 产品是否随使用更好地理解学生；
- 是否造成依赖、操纵或反向作用；
- 长期规律和绩效区间是否稳定。

这是真正指向学业军师第一性价值——学生形成自己走路径能力——的验证。

#### 5. 教育效果归因验证

要判断“教育效果由产品造成”，需要区分：

- 教师、课程、家长、学生自身等混杂因素；
- 是否采用对照或基线；
- 结果是否可重复；
- 是否存在选择偏差；
- 是否存在其他解释；
- 归因是否符合伦理和授权。

这是最严格的验证，通常需要真实研究和长期观察，不能由模拟评测或单次成绩得出。

### 四、模拟场景的构造要求

模拟评测要作为可靠机制证据，必须覆盖真实运行会遇到的关键情况，而不只是顺利路径。

至少应构造：

1. **正常路径**：材料→证据→判断→任务→教与授→检验→反馈；
2. **边界条件**：缺少必需字段、权限不足、状态非法；
3. **失败与未知**：Agent 超时、无返回、格式错误、证据不足；
4. **冲突**：学生自述与学校反馈冲突、单次与长期冲突；
5. **学生拒绝、暂停、撤回**；
6. **会话切换与阶段交接**；
7. **Agent 之间越权或污染**；
8. **错误传播与阻断、回滚**；
9. **高影响操作的确认和审计**；
10. **跨学段、跨机构的不同配置**。

模拟应记录可核对的：

- 预期结果；
- 实际结果；
- 依据的证据链；
- 状态迁移；
- 权限和审计；
- 失败与处理；
- 是否需要补证、确认或复核。

只有当模拟能系统地覆盖这些情况并产生可追溯证据时，它才能作为产品机制的可靠性证据。

### 五、验证与开发的分离

#### 1. 机制验证通过 ≠ 教育价值成立

机制验证通过只能说明系统按设计工作，不能说明学生因此受益。产品不能因“模拟评测通过”而宣称教育效果成立。

#### 2. 必须明确界限

产品对外呈现和内部决策都应当区分：

- “机制验证通过”与“教育价值成立”；
- “任务完成”与“能力形成”；
- “内部练习有效”与“学校现实改善”；
- “模拟场景通过”与“真实长期有效”。

#### 3. 何时进入真实学生小样本

应满足：

- 机制、底层、权限和监察已通过模拟验证；
- 最小能力闭环已可运行；
- 已获得学生和监护人的授权；
- 已明确数据范围和隐私边界；
- 已建立纠错、撤回和投诉机制；
- 具备观察、记录和分析真实行为的能力。

#### 4. 真实验证的隐私与授权

真实学生、机构和学校数据必须：

- 获得明确授权；
- 限定用途；
- 最小化收集；
- 可撤回；
- 可删除；
- 建立安全边界；
- 接受监察和审计。

不能为了“验证效果”而无限制收集或传播学生和学校数据。

### 六、长期自生长的验证边界

#### 1. 自生长的机制可以模拟验证

例如：

- 产品能否在模拟长期使用中逐步建立稳定的学生认识；
- 能否正确增长对学生的理解；
- 能否阻断错误记忆；
- 能否在权限和确认范围内更新；
- 能否撤回、修正和删除；
- 是否遵守“只增长对学生的理解、不改变产品规则与边界”。

这些是机制层面的自生长验证。

#### 2. 自生长的价值必须真实长期验证

只有真实学生长期使用，才能验证：

- “越用越懂学生”是否真的带来更好判断；
- 增长的认识是否真的支持而非操纵学生；
- 长期稳定规律是否真的可靠；
- 学生是否因长期使用而获得自主能力；
- 是否存在副作用（依赖、误导、过度画像）。

因此：

> **自生长的机制可用模拟验证；自生长的价值只能由真实长期使用验证。**

#### 3. 至少多长时间

学业军师定位为长期产品，至少数月起。“越用越懂学生”的价值通常需要足够长的真实使用周期才能观察，具体期限和样本需要根据验证设计确定，不能仅凭“六个月”口号下结论。

### 七、底层与 Agent 在验证中的分工

#### 底层负责

- 提供可重复的评测数据；
- 支持构造模拟场景；
- 记录完整的证据链和状态迁移；
- 提供监察证据；
- 支持回滚和重复运行；
- 在真实使用时保证授权、隐私和安全；
- 让机制验证与教育价值验证分开记录；
- 提供可核对的门槛和结果。

#### Agent 负责

- 在评测中执行专业判断和编排；
- 提供判断、分析和建议；
- 暴露失败、冲突和不确定性；
- 协助解释评测结果；
- 不把模拟评测结果伪装成教育价值。

#### 监察负责

- 检查评测过程是否符合规则；
- 检查是否越权、伪造、缺证；
- 提供独立的质量证据；
- 对通过门槛进行独立核验；
- 防止“监察自身不可审查”。

#### 谁定义通过门槛

通过门槛应由产品责任方结合产品目标、证据标准和风险确定，并接受监察和必要的用户确认。不能由评测者或 Agent 自行宣布“通过”。

### 八、模拟评测不能替代真实学校反馈

即使模拟评测非常完备，也不能替代真实学校现实反馈，因为：

- 模拟无法证明学生在真实学校任务中的表现；
- 模拟无法反映真实教师、课程和评价环境；
- 模拟无法提供学生真实行动和长期成长；
- 模拟无法验证教育效果归因；
- 模拟无法反映学生在真实约束下的使用意愿和负担。

因此：

> **模拟评测是开发和机制的可靠工具，不是教育价值的证明。学业军师的“学校现实检验”必须由真实学生、真实学校任务和现实反馈支撑。**

### 九、专业结论

> **学业军师的成立必须分别通过机制验证与教育价值验证来证明。模拟评测可以验证产品机制是否按设计运行、底层是否可靠、Agent 是否守契约、能否防伪证和错误传播；但不能证明学生理解、行动、能力或学校结果改善。**
>
> **教育价值需要真实学生和学校现实反馈，并经长期使用观察其是否帮助学生形成自主能力。验证应区分机制、真实小样本、学校现实反馈、长期能力形成和教育效果归因等层次，不能把任一模拟或单次结果当作教育价值已成立的证明。**
>
> **底层、Agent 和监察为验证提供可追溯证据和独立检查；通过门槛由产品责任方结合证据和风险定义，并接受监察与必要的用户确认。模拟评测与真实学校反馈相互补充，但不能互相替代。**

## 3.6　问题 3-6：监察、质量门槛与回滚

**标准化问题**：为让学业军师的可靠性可被证明而非自称可靠，监察与回滚机制应如何设计——包括监察的专业定位、监察对象、监察机制（底层自动化检查、风险分级、抽样与全量、独立复核、人工兜底、审计追溯）、质量门槛与阻断、回滚与恢复、监察自身的监督，以及底层与 Agent 的分工和对外诚实地呈现验证状态？

**回应与论证**：

### 一、监察的专业定位

监察不是给产品“增加一个审核人格”，也不是让某个 Agent 拥有最终决定权。监察的目的是：

> **让学业军师的可靠性可被证明，而不是自称可靠；让“AI 不自证、规则守底线”落到实处。**

监察回答两个问题：

1. **依据是什么**：判断是否真实依据了证据、来源和规则；
2. **谁做了什么、是否合规、是否可靠**：Agent 是否越权、是否污染、状态是否合法、结果是否可追溯。

监察分为两部分，必须分开：

- **证据设施**：回答“某个判断依据了什么证据”；
- **监察设施**：回答“谁做了什么、是否符合产品规则、结果是否可靠”。

监察设施不取代证据设施，也不取代 Agent 的专业判断；它负责核验和把关。

### 二、监察的对象

监察至少需要覆盖：

1. **判断的依据**：是否真实、有来源、带确定性；
2. **Agent 行为**：是否越权、是否污染、是否伪造；
3. **状态迁移**：是否合法、是否经过确认、是否可追溯；
4. **证据使用**：是否伪证、是否误用、是否冲突；
5. **输出契约**：是否带来源、确定性、适用范围和影响；
6. **责任交接**：是否明确、可追溯、不丢限定；
7. **权限**：是否越权读取、越权写入、越权传播；
8. **高影响操作**：是否被阻断或强制确认；
9. **错误与回滚**：是否识别、是否阻断下游、是否恢复；
10. **边界遵守**：是否仍在学生主体、证据和权限边界内。

监察不负责替 Agent 作学业判断，而是检查 Agent 的判断和操作是否符合产品规则。

### 三、监察的机制

监察不应是单一的“事后抽检”，而应由多种机制配合。

#### 1. 底层自动化检查

由确定性设施自动执行：

- 对象和来源校验；
- 状态机合法性；
- 权限校验；
- 证据充分性；
- 冲突检测；
- 输出契约校验；
- 高影响操作阻断；
- 调用和审计记录。

自动检查是监察的基础，速度快、可重复、不依赖模型判断。

#### 2. 风险分级

对不同风险采用不同深度检查：

- **低风险**（可逆、临时、不影响长期状态）：轻量检查或抽样；
- **中风险**（影响当前任务、学科安排）：结构化和证据检查；
- **高风险**（影响规划、资产、记忆、传播、跨阶段）：强制复核、必要确认、全程审计；
- **临界风险**（重大方向、阶段结束、可能越权）：强制阻断或人工/独立复核。

风险分级不是“风险高的就禁止”，而是“风险越高、需要越强的证据和把关”。

#### 3. 抽样与全量检查

- **全量**：对产生状态迁移、影响证据、或属于高风险的操作，应全量检查；
- **抽样**：对低风险、大量重复的常规操作，可抽样检查，但抽样结果要可统计、可审计；
- **重点**：对主军师、关键专业 Agent、监察自身、影响长期规划或资产的操作，重点检查。

不能对所有操作都做最严格全量检查（成本和延迟过高），也不能只靠抽样就宣称全部可靠。

#### 4. 独立复核

- 重要判断、冲突、越权、异常应由独立于产生该输出的责任域进行复核；
- 复核不能由同一次输出直接自我批准；
- 独立复核要有来源、理由和结论。

#### 5. 人工介入和兜底

- 高影响、高风险、模糊或无法自动判定时，应允许人工介入；
- 人工介入要有授权、记录和可回退；
- 对监察自身的异常、冲突和严重误判，提供人工或更高层兜底；
- 兜底不能成为随意扩大权限的入口，需受审计。

#### 6. 审计与追溯

- 监察操作本身可审计；
- 复核结论可追溯；
- 能够回答“谁在何时、依据什么、作出了什么判定”。

### 四、质量门槛与阻断

#### 1. 最低通过标准

应定义“合格”的最低条件，至少包括：

- 有来源和依据；
- 输出带确定性和适用范围；
- 权限合法；
- 状态迁移合法；
- 无未登记的冲突或伪证；
- 符合学生主体和证据边界；
- 高影响操作有确认；
- 有审计记录。

#### 2. 阻断条件

出现以下情况应阻断：

- 无来源的高确定性结论；
- 越权读取或写入；
- 未确认的重大迁移；
- 伪证据、伪记忆；
- 缺少必要审计；
- 状态机非法迁移；
- 冲突未解决的高影响操作；
- Agent 试图绕过契约；
- 结果不符合最低门槛。

阻断不是“惩罚”，而是防止错误进入正式状态和下游。

#### 3. 未通过时的处理

- 阻断相关操作；
- 标记为待补证、待复核或需人工介入；
- 降级或暂停高影响判断；
- 记录失败原因；
- 通知相关 Agent 和必要的用户；
- 不把未通过结果当作已完成或已确认。

#### 4. 错误传播的判断

- 识别错误是否已经影响其他判断、任务、资产、记忆或传播；
- 评估受影响范围；
- 决定是否需要阻断下游、撤回或回滚；
- 记录错误链条和影响。

### 五、回滚与恢复

#### 1. 什么错误需要回滚

- 非法状态迁移；
- 越权或污染；
- 伪证或错误证据进入判断；
- 未经确认的重大变更；
- 错误写入资产或记忆；
- 传播或交接错误；
- 状态一致性被破坏。

#### 2. 回滚范围

回滚可以覆盖：

- 判断；
- 任务；
- 规划；
- 学业资产；
- 阶段内记忆；
- 对外传播；
- 责任交接；
- 学生可见的控制状态。

回滚范围应与错误影响范围一致，不能过度回滚，也不能只回滚表面状态而遗留下游错误。

#### 3. 回滚由谁发起和批准

- **底层**：对可自动判定的非法或一致性错误，可自动发起回滚或阻断；
- **监察**：对发现的高风险、越权、伪证错误，提出回滚申请或复核；
- **学生/机构**：对涉及自身重大状态或传播的错误，可以要求回滚或撤回；
- **运维/人工**：对复杂、需判断的回滚，可受控介入。

关键的回滚应记录发起者、理由和批准路径，不能由同一 Agent 单方面判定“我错了并已回滚”。

#### 4. 回滚前是否保留快照

是。回滚应保留回滚前的快照和版本，以便：

- 回溯；
- 比较；
- 必要恢复；
- 审计；
- 防止重复错误。

不能因回滚而丢失可追溯的历史。

#### 5. 下游引用处理

回滚后：

- 识别依赖该对象的下游判断、任务、资产、记忆和传播；
- 阻断或修正受影响的下游；
- 不让被回滚的错误继续传播；
- 更新受影响的版本和状态；
- 必要时通知相关角色。

#### 6. 学生是否需要知情

对影响学生重大状态、资产、记忆、规划或传播的回滚，应让学生知情并看到原因；必要时提供纠错和确认入口。

#### 7. 防止回滚后再传播

回滚后应：

- 标记相关对象为已修正或已失效；
- 阻断旧版本被继续引用；
- 更新下游；
- 记录防止再次传播的规则；
- 在审计中留下完整过程。

#### 8. 审计记录

回滚的全过程（触发、范围、快照、下游处理、执行者、时间）都应被审计，不能只记录“已回滚”。

### 六、监察自身如何被监督

监察如果不受监督，就可能成为新的“不可审查权威”。

#### 1. 监察有责任域和权限边界

监察 Agent 也有输入、输出、权限、状态和审计要求，不能无边界读取或操作。

#### 2. 监察不能独立审查自身

监察不能既当选手又当裁判，不能自行宣布“我已通过、无需复核”。

#### 3. 谁监督监察

- **更高层抽样或独立复核**：对监察的判定进行抽样审查；
- **人工或更高层兜底**：对严重误判、冲突和越权提供兜底；
- **底层硬规则**：监察本身的操作受底层权限、状态、审计约束；
- **审计公开性和可追溯**：监察过程可被追溯，异常可被识别；
- **不设绝对最高豁免者**：任何监察判断都不是不可质疑的最终权威。

#### 4. 防止监察滥用

- 监察不得自行扩大权限；
- 监察不得替代学生确认；
- 监察不得无限制阻断合理操作；
- 监察不得成为外部可见内容的首发者（除非明确允许）；
- 监察的误判应可申诉、可复核、可修正。

### 七、底层与 Agent 的分工

| 职责 | 底层基础设施 | Agent / 监察 |
|---|---|---|
| 自动检查 | 状态机、权限、证据、契约、审计 | 遵守并接收校验结果 |
| 风险分级 | 按规则识别风险级别 | 按级别运行和检查 |
| 独立复核 | 提供复核所需的来源和权限 | 监察/独立角色进行复核 |
| 阻断 | 拦截非法/越权/伪证操作 | 提出风险、申请复核 |
| 质量门槛 | 定义最低通过条件 | 达到并接受判定 |
| 回滚 | 快照、一致性、下游处理、审计 | 提出回滚申请和建议 |
| 监察自监督 | 权限、抽样、兜底、审计 | 接受监督 |
| 对外诚实 | 标记已验证/未验证状态 | 呈现依据和限制 |

Agent 可以参与自检、风险分析和复核，但不能最终自我批准高影响操作；监察 Agent 可以提出阻断、复核和回滚，但自身也受底层和更高级别监督。

### 八、对外诚实地呈现验证状态

产品不应把自己伪装成“已验证、可靠、有教育效果”。至少应诚实标记：

- 已验证的机制部分；
- 尚未验证的教育效果部分；
- 本次判断的依据和确定性；
- 无法验证或需要补证的内容；
- 机制验证与教育价值验证的区分；
- 模拟评测与真实学校反馈的区分；
- 任何未经验证的结果都不得对外宣称成立。

### 九、专业结论

> **监察的目的是让学业军师可靠可证明，而不是自称可靠。它通过底层自动化检查、风险分级、抽样与重点检查、独立复核、人工兜底和审计追溯，回答“判断依据了什么、谁做了什么、是否合规可靠”。**
>
> **质量门槛定义合格条件，阻断伪证、越权、非法状态和缺证；未通过时暂停、降级、补证或人工复核。回滚需要保留快照、处理下游、防止再传播并完整审计。**
>
> **监察自身也必须被监督：有责任域和权限边界，不能独立审查自身，由更高层抽样、人工兜底、底层硬规则和审计约束。任何监察判断都不是不可质疑的最终权威。**
>
> **产品对外必须诚实地区分“已验证”与“未验证”，不能把机制验证或模拟评测冒充教育价值或可靠性的最终证明。**

### 一、前端呈现的产品定位（[专业建议·代拟]）

学业军师是一个长期、复杂、证据驱动的系统，但使用者学生通常不具备 Agent 基础，也难以一眼看清整体学业。前端呈现不应只被当作“界面美观”，而应被定义为：

> **“学生主体”在产品和现实之间的最终落点：让学生能够理解自己在哪里、应做什么、为什么做、做完如何检验、下一步怎么办，以及自己产生的材料、认识和资产存在哪里、如何查看和控制。**

目标：

- 降低理解负担；
- 让学生能质疑、纠正、确认、拒绝和退出；
- 把复杂机制呈现为可理解、可控制的结果；
- 同时不隐瞒会影响学生判断的事实、依据和限制。

### 二、学生第一性问题（[专业建议·代拟]）

前端应始终能回答以下第一性问题：

1. **我在哪里**：当前学业阶段中的位置、学科状态、当前任务；
2. **当前最应做什么**：现在最重要的一步任务，而非无穷列表；
3. **为什么做**：这一步承接什么、依据什么；
4. **做完如何判断是否有效**：完成标准、检验方式、现实结果如何看；
5. **下一步怎么办**：完成后进入什么；
6. **我做的东西存在哪里、如何查看**：学业资产、阶段内认识、过程和结果；
7. **谁在为我判断、依据是什么**：产品给出了什么判断、依据哪些证据；
8. **我能如何控制**：确认、纠正、拒绝、暂停、退出、撤回、管理资产与记忆。

这 8 项覆盖“现状—行动—理由—检验—下一步—沉淀—依据—控制”。是否需要增加取决于真实学生反馈，不能只靠抽象设计定死。

### 三、可见与不可见的边界（[专业建议·代拟]）

**学生应能看见**：

- 当前状态与位置；
- 当前任务及其理由；
- 完成条件和检验方式；
- 支持判断的依据与证据来源；
- 确定性程度；
- 未知、冲突和待确认事项；
- 学业资产及范围、来源、验证状态；
- 军师对学生的认识（可见、可纠正）；
- 控制与反馈入口；
- 哪些结论仍无法判断或需补证。

**不应默认展示或应简化**：

- 完整内部 Agent 对话；
- 完整内部思维链；
- 底层技术细节（模型、规则、接口、凭证）；
- 与当前决策无关的内部过程；
- 不必要的技术术语。

**平衡原则**（代拟）：不显示完整思维链，不等于隐瞒影响判断的关键事实。呈现应达到“不误导、不隐瞒关键事实、可理解、可控制”；需要保留的只是必要证据与依据，而非全部内部机制。学生可以不知道是哪几个 Agent 协作，但必须知道他该做什么、为什么、依据什么；可以不知道用了哪个模型，但必须知道某项判断仍有不确定性；必须能纠正事实、拒绝安排、查看关键状态。

### 四、战场总框架与分级学科窗口（[用户明确判断] + [确认采纳]）

用户明确修正（[用户明确判断]）：

> **前端仍呈现为前线与后方的战场总框架；在此基础上，按不同学科设立不同窗口作为操作组织方式。第一级窗口展示全学科内容；下设多个窗口，点击进入即可查看对应专业学科的内容。**

这一做法是在前线与后方的基础上加以新内容：**以“前线—后方”呈现学业的战况与趋势，以分级学科窗口提供更利于操作使用的具体入口。**

据此修订的四层前端结构（[专业建议·代拟]）：

```text
战场总框架
├── 前线：当前学业战况、趋势与紧要行动
│   ├── 第一级：全学科总览窗口
│   └── 第二级：各学科专业窗口
└── 后方：阶段内资产、认识与长期积累
    ├── 第一级：全局资产与趋势总览窗口
    └── 第二级：各学科资产专业窗口
```

- **战场总框架负责整体理解和战况/趋势呈现**（哪里、整体如何）；
- **分级学科窗口负责具体操作和进入专业学科**（这门学科现在做什么、如何推进）。

两层解决不同问题：战场视图理解全局，学科窗口进入行动。

**前线（战场视图）**：当前最紧要的学业行动——当前整体战况、阶段最重要方向、各学科状态、当前优先级、当前最应推进任务、学科冲突或失衡、近期趋势、需确认/补证/调整事项。回答“我现在整体在哪、当前最重要战况、接下来推进什么”。前线不是简单待办列表，而是将全学科协调结果转化为可理解的当前行动视图。

**后方**：阶段内积累——学业资产、已确认阶段内认识、学习过程与历史结果、可复用方法、已验证或待复核认识、证据与反馈形成的长期趋势、阶段性总结、可供调用的历史资源。回答“过去积累了什么、哪些仍有效、如何支持现在和后续”。后方不是静态档案库，而是受证据、状态、确认与复验约束的阶段内资源区。

**前线与后方闭环**：后方积累的证据/资产/趋势 → 支持前线当前判断与任务 → 学生完成前线行动并取得结果 → 结果回流后方形成新证据、修订认识和趋势。没有前线，后方退化为静态资料仓库；没有后方，前线退化为无历史依据的临时待办。

**第一级：全学科总览窗口**：展示各学科当前状态、学科间优先级、当前整体战况与趋势、当前最应推进方向、各学科待处理事项概览、需进入具体学科处理的问题、整体层面冲突/风险/待确认。它不承担全部学科细节，而是提供“从整体战况进入具体学科行动的导航与决策入口”。

**第二级：学科专业窗口**：点击某学科后进入，展示学科当前状态、学科内任务、任务理由与完成标准、讲解/练习/检验、学科证据与反馈、学科资产与阶段内认识、学科趋势、返回全学科总览入口。承担把全学科协调方向转化为该学科内可理解、可执行、可检验的操作。各学科窗口可采用不同专业内容，但共享底层证据、权限、状态、会话与监察约束。

### 五、战况、趋势、资产、规划的区别（[专业建议·代拟]）

用户指出“前线与后方呈现学业的战况与趋势”，需进一步区分（不能混为一张图或一个分数）：

| 内容 | 时间尺度 | 作用 |
|---|---|---|
| 战况 | 当前/近期 | 决定眼下做什么 |
| 趋势 | 一段时间 | 判断是否持续变化 |
| 资产 | 阶段内可复用 | 支持后续学习 |
| 规划 | 未来安排 | 组织任务和资源 |

前端可关联展示，但底层必须保留不同对象、来源与状态。

### 六、控制入口（[专业建议·代拟]）

学生端至少应具备并能够使用：

1. **确认、拒绝、暂停、退出**：确认/拒绝重大方向或当前任务；暂停、恢复、退出当前工作；明确退出产品或阶段协作。
2. **纠正事实**：纠正产品关于学生的判断或记录；提出新的或不同材料；指出事实错误；纠正后生效并受审计。
3. **撤回用途**：撤回某条证据、记忆或资产的使用；撤回某些用途；撤回后底层阻断下游使用。
4. **查看和管理资产**：查看资产及其来源、范围、验证状态；确认/修改范围内内容；标记不再需要的内容。
5. **查看和控制记忆**：查看关于自己的记忆；纠正不正确认识；拒绝保留某条记忆；撤回或删除可删除内容。
6. **向教师/机构/家长反馈边界**：了解哪些信息会提供到何种范围；在规则允许内控制传播边界；提出越界或错误的纠正。
7. **求助与人工介入**：提供解释、帮助、反馈困难的入口；开启人工介入或复核；申诉监察误判或错误判断。
8. **无障碍与首次使用**：首次引导让不熟悉的学生三步上手；降低术语和输入负担；支持跨能力学生的理解和操作；满足无障碍合理访问需求。

### 七、学生控制权与底层记录保证（[专业建议·代拟]）

前端提供控制入口，但真正保证学生控制权的是底层：

- 底层确认、拒绝、撤回、暂停、退出记录是**强制状态**，不是界面提示；
- 前端点击“确认”后，底层必须校验并记录对象、范围、时间和后果；
- 前端点击“纠正”后，底层必须让纠正生效并阻断下游错误使用；
- 前端隐藏或显示内容，必须与底层权限和状态一致，不能只改界面；
- 学生沉默不能被界面解释为“已同意”；
- 学生拒绝不能被界面记录为“已完成”。

前端是让学生能发起和控制；底层记录是让学生控制真正生效。

### 八、前端不伪装成单一对话（[专业建议·代拟]）

前端可给统一入口，但不应把不同责任域、不同状态混成一句“最终答案”：

- 学生面对的是责任域编排后形成的清晰结果，而非混在一起的内部对话；
- 当前任务来自哪类判断、依据哪些证据，应有可追溯说明；
- 尚未决定或需确认的内容应明确标注，而非包装成“已确定”；
- 前端分栏、状态、资产展示应与底层责任域隔离一致。

即：**前端统一体验，底层责任分域；前端呈现清楚的结果与依据，不伪装成一次没有责任归属的聊天。**

### 九、底层与 Agent 分工

| 事项 | 底层基础设施 | Agent/前端 |
|---|---|---|
| 内容一致性 | 保证呈现状态与真实状态一致 | 生成可理解表达 |
| 权限边界 | 决定谁能看到什么、控制什么 | 呈现必需且允许的内容 |
| 控制生效 | 确认/拒绝/撤回/暂停强制记录 | 提供操作入口和反馈 |
| 不隐瞒关键事实 | 保证不隐藏影响判断的依据与限制 | 用易理解语言说明依据 |
| 责任域隔离 | 防止前端伪装成单一对话 | 组织并解释结果 |
| 学生认识 | 保证可见、可纠正、可撤回 | 呈现对学生的认识 |
| 遗漏/冲突 | 保留未知、冲突和待确认 | 说明并请求确认 |
| 无障碍 | 支持跨能力访问 | 首次引导和简化表达 |

### 十、专业结论

> **学业军师前端采用“战场总框架（前线—后方）+ 分级学科操作窗口”的双层结构。战场总框架以“前线—后方”组织学生对整体学业的理解：前线呈现当前学业战况、趋势和紧要行动，后方呈现阶段内积累的证据、资产、认识和长期资源；前线与后方内部再分别设置全局总览窗口和学科专业窗口：总览用于掌握全局和导航，学科窗口用于进入具体学科、任务、教与授和资产操作。**
>
> **这种结构同时解决两个问题：前线与后方提供整体战况和趋势的理解框架，分级窗口提供具体学科的操作路径。前端的分级视图不改变底层责任域、权限、证据、会话和监察结构；它只是将复杂的学业管理机制转换为学生能够理解、质疑和操作的呈现方式。**

## 3.8　问题 3-8：0.5→1 开发路径与首版开发边界

**标准化问题**：学业军师应如何走通 0.5→1 开发路径，首版开发边界如何划定——包括 0.5→1 的准确含义、首版是否以底层设施为优先并清单化、底层设施全闭合与全量业务功能不首版一次补齐的区分、首版需跑通的核心闭环、第二版及以后的节奏、拿来主义与产品自持的边界，以及开发节奏与验收标准？

**回应与论证**：

以下为记录中本单元完整回应正文。用户回复“专业代拟”，要求针对 0.5→1 开发路径与首版开发边界给出专业方案。主技能先给出 [专业建议·代拟]；随后用户提出首版应以底层设施为优先并清单化（记 [用户明确判断]），并表达“首版尽可能完善绝大部分功能、后续版本升级优化”的观点；主技能对该观点做批判性应用，明确“底层设施全闭合”与“全量业务功能不首版一次补齐”的区分（记 [专业建议·代拟]），用户随后确认采纳。全部待确认/待验证项保持原状态。用户首版边界观点与主技能批判性应用必须分层保留：[用户明确判断] 与 [专业建议·代拟] 不得混淆。

### 一、0.5→1 的准确含义

> **以已有成熟能力为起点减少从零建设；同时以学业军师的产品本体为筛选与约束标准，控制整合方向。**

优先级：

```text
复用 > 改造 > 受控整合 > 必要重构 > 最后自建
```

两个硬限定：

1. **复用不等于照搬**：外部项目必须先被理解，再被复用；
2. **复用不等于改造无限优先**：改造成本过高、破坏边界或失去优势时，应停止改造，改为隔离、替换、放弃或自建。

开发采用“本体先定最小边界、候选并行审查、验证后受控整合”。

### 二、[用户明确判断]：首版应以底层设施为优先，并以清单化指引

用户观点：

> **首版开发应优先完成学业军师产品的底层设施工作，必须把底层设施全部做好；没有明确清单，开发会顾此失彼，风险高。基于 0.5→1 路径，首版应尽可能完善绝大部分功能，第二、三版为升级优化。**

批判性吸收：这一观点有两个合理内核——(a) 底层设施是地基，0.5→1 决定了首版要把地基一次做扎实；(b) 清单化是降低遗漏风险的正确手段。

[专业建议·代拟]：对观点做一处修正——**“首版补齐全部底层设施”与“首版补齐全部业务功能”是两件事，不能混为一谈。** 底层设施应一次闭合；全量业务功能不应在首版一次全部补齐。

### 三、首版边界：底层设施全闭合 + 一个核心闭环跑通

#### 1. 首版必须完成的底层设施完整清单（一次性闭合）

基于已确认的底层确定性设施，首版把以下四组 15 项**全部**做好：

**清单 A：核心对象与事实设施（必须自持）**
- A1 对象与来源设施：对象定义、来源、归属、类型、完整性、授权；
- A2 证据治理设施：类型、强度、支持范围、来源、冲突、缺失、撤回、追溯；
- A3 状态与生命周期设施：状态机、合法迁移、版本、失效、归档、封存；
- A4 权限与责任设施：角色矩阵、读写确认传播撤回边界、最小必要、高影响拦截；
- A5 审计与追溯设施：谁/何时/依据/改了什么、规则版本、错误链、回滚链。

**清单 B：过程与运行设施（底层支撑）**
- B1 任务过程设施：任务状态机、接受/执行/完成/检验、行动真实性、完成证据；
- B2 会话与责任域设施：责任域、会话边界、隔离、交接、恢复、结束、受控蒸馏；
- B3 质量门槛与阻断设施：缺证/越权/伪证/非法迁移阻断、最低通过标准、暂停/降级；
- B4 回滚与一致性设施：快照、下游影响、撤回/修正一致性、再传播阻断、审计。

**清单 C：产品边界设施（学生主体与阶段结构）**
- C1 学生主体与控制设施：确认/拒绝/暂停/退出/纠正/撤回强制记录、沉默≠同意、对象化确认；
- C2 阶段生命周期设施：创建/配置/运行/结束/封存/交接/重置、跨阶段不静默延续；
- C3 B 端机构与角色隔离设施：机构身份、学生归属、角色权限、数据隔离、配置不越硬规则。

**清单 D：治理与管理设施（防碎片化）**
- D1 监察与自监督设施：判断依据核验、Agent 越权/污染检查、独立复核、人工兜底、监察受监督；
- D2 Agent 运行控制设施：调用注册、输入输出契约、工具权限、超时/重试/终止、记录；
- D3 配置与内容版本设施：阶段/学科/内容包/任务模板/规则版本、配置与硬规则隔离。

> 首版判定：以上 **A/B/C/D 四组 15 项全部闭合**，底层设施方为首版就绪。

#### 2. 首版还需跑通一个核心能力闭环

底层设施之外，首版应打通并验证一个完整闭环：

```text
证据 → 判断 → 路径与任务 → 教与授 → 学生行动 → 检验 → 学校反馈（雏形） → 修正
```

作用：

- 证明“证据驱动、学生主体、学校检验”这一学业军师核心可以成立；
- 让底层设施不是空壳，而是被真实业务调用；
- 为首版之后的功能扩充提供已验证的运行骨架。

#### 3. 全量业务功能不在首版一次补齐

[专业建议·代拟]：

- **底层设施**首版全部闭合（✔）；
- **一个核心闭环**首版跑通（✔）；
- **全量业务功能**（全学科、全场景、全部机构形态、丰富前端）**不在首版一次补齐**。

原因：

- 未经真实使用验证就“全部补齐”，会变成“什么都有一点、但什么都没验证”；
- 与已确认的“模拟验证机制、真实学生验证效果”原则冲突；
- 反而会陷入“慌不择路、无法验证”的风险，违背清单化的初衷。

首版完整定位：

> **首版 = 底层设施全部闭合 + 一个可验证的核心闭环跑通；**第二版起，在坚实地基上通过复用/改造做功能扩充与组件替换。

### 四、第二版及以后

在首版完整地基之上：

- **第二版（2.0）**：多学科规模化、复杂机构协同、更完整家长机制、更多外部能力复用/改造接入——基于首版底层设施；
- **第三版及以后（3.x）**：长期自生长价值的真实验证、更深的学科专业能力、教育效果归因优化、组件替换与升级。

关键：**后续版本都建立在首版已闭合的底层设施之上，而不是在首版地基未闭合时不断追加功能。**

### 五、拿来主义与产品自持的边界

用户的“拿来主义”判断（复用、重构、直接使用成熟产品做独属修改）是有效的 0.5→1 手段，但必须受以下限定：

1. **拿来的是通用实现能力**：Agent 运行时、检索、状态存储、权限库、前端组件、测试部署等；
2. **产品本体必须自持**：证据定义、状态规则、权限矩阵、学生控制、阶段边界、验收标准不能由外部项目反向决定；
3. **未经验证的外部能力不能直接当“已完成”纳入首版**：拿来后仍需核对输入、输出、状态、权限、生命周期、依赖、许可证、运行证据、回退；
4. **不能拼接出参差不齐的产品**：复用导致多套记忆、权限、状态不可控时，应隔离、替换或自建。

复用最终标准：

> **接入后能否更可靠承接学业军师的产品责任。**

### 六、开发节奏与验收

底层设施全部闭合是首版验收前提；开发顺序可以分先后（先证据、再会话、再任务、再监察），但验收时 15 项必须全部到位、核心闭环可运行、可追溯、可回滚。

### 七、专业结论

> **学业军师采用“本体先定、候选并行、验证后受控整合”的 0.5→1 开发。首版以底层设施为优先，必须一次性闭合对象/证据/状态/权限/审计（A）、任务/会话/质量/回滚（B）、学生主体/阶段/机构（C）、监察/Agent控制/配置（D）四组共 15 项底层设施，并跑通一个可验证的核心能力闭环，证明“证据驱动、学生主体、学校检验”的核心成立。**
>
> **全量业务功能不在首版一次补齐，而在坚实地基上通过复用、改造、迭代逐步扩充；第二版起进入功能完善、组件替换与升级优化。拿来主义有效，但只适用于通用实现能力，产品本体必须自持，未经验证的外部能力不能直接当已完成。首版验收以底层设施全部闭合和核心闭环可运行为标准。**
